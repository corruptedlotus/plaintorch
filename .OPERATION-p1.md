# OPERATION P1

## Phase Goal
- [ ] Transition PLAINTORCH from a console-driven local tool into a hosted, single-vault, background-first service.

## Core Objectives
- [x] Switch to the ASP.NET Core SDK.
- [x] Introduce dependency injection and replace manual composition.
- [x] Separate host/runtime concerns from application-core concerns.

## Persistence
- [x] Move from `EnsureCreated()` to EF Core migrations.
- [x] Establish migration-driven database startup/update flow.

## Temporal Retention
- [x] Add temporal graveyard foundations for deleted database and file-backed data.
- [x] Add audit-log foundations with soft entity references.
- [ ] Add retention policy and cleanup flow for graveyard and audit data.

## Vault Ownership
- [x] Enforce single active vault ownership.
- [x] Introduce vault lock / ownership tracking.
- [x] Refuse service startup when another owner is active.

## Service Runtime
- [x] Build a long-running background service host.
- [x] Support graceful startup and shutdown.
- [~] Make systems more async- and background-friendly.

## Synchronisation and Discovery
- [x] Implement file watchers for the active vault.
- [x] Build a sync/discovery coordinator.
- [ ] Support reconciliation of markdown, database, and vault state.
- [ ] Implement delete/recreate behavior for relation-protected file-backed entities.

## API and Applications
- [x] Build the service API layer.
- [x] Expose service actions through a UNIX socket endpoint.
- [ ] Reposition the CLI as an API client over the service.
- [ ] Prepare for future Obsidian plugin and SIPA integration.

## Operational State
- [ ] Add an operational state engine.
- [ ] Process time/date-driven state changes.
- [ ] Track onrush status, tasks, and related operational progression.

## Logging and Observability
- [ ] Add clean structured logging.
- [ ] Expose machine-readable service status and diagnostics.

## Suggested Build Order
- [x] Hosting conversion and DI
- [x] Migrations workflow
- [x] Single-vault enforcement
- [x] Service runtime
- [x] Sync/discovery coordinator
- [x] File watchers
- [ ] Reconciliation flows
- [ ] API transport
- [ ] CLI as client
- [ ] Operational state engine
- [ ] Expanded logging and diagnostics

## Notes
- Watcher/discovery now covers startup scanning, path-only model detection, markdown validation, provisional sync-action decisioning, debounced filesystem events, and self-write suppression.
- Reconciliation execution is still pending; discovery can classify and queue action intent, but it does not yet apply the final database/file mutations.
- Objective markdown storage is now treated as synced, including directive-contained objective files and standalone files under the `Objectives` root.

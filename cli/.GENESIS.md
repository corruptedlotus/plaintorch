# PLAINTORCH CLI Genesis Log

## Purpose
This package is the beginning of the dedicated PLAINTORCH command-line application. Its job is to become the primary user-facing shell over the hosted core instead of continuing to grow the legacy direct-entry console surface inside the core package.

## What Was Added

### CLI project foundation
Created a dedicated .NET console project in [plaintorch.cli.csproj](plaintorch.cli.csproj) that references the core package.

Added the CLI entrypoint in [Program.cs](Program.cs), which:
- builds the DI container
- discovers command modules
- constructs the command registry
- runs the command engine

### Command engine
Added a custom modular command framework under [Cli](Cli):
- [Cli/CliAttributes.cs](Cli/CliAttributes.cs) for command metadata, option metadata, default-command markers, and help-switch markers
- [Cli/CliCommandRegistry.cs](Cli/CliCommandRegistry.cs) for modular command registration and command-tree construction
- [Cli/CliArgumentParser.cs](Cli/CliArgumentParser.cs) for raw switch and positional parsing
- [Cli/CliOptionsBinder.cs](Cli/CliOptionsBinder.cs) for mapping parsed arguments into typed semantic option objects
- [Cli/CliHelpTextRenderer.cs](Cli/CliHelpTextRenderer.cs) for root and command help rendering
- [Cli/CliCommandEngine.cs](Cli/CliCommandEngine.cs) for command-path resolution, DI activation, option binding, and command-method execution

Current supported engine behaviors:
- root commands mapped to classes
- optional default command methods
- explicit help-switch methods
- command-class-owned subcommand registration through a static registration method
- dependency injection for command instances and services
- generated help output for root and nested commands

### First concrete commands
Added the first command module under [Commands/Core](Commands/Core):
- [Commands/Core/CoreCommandsModule.cs](Commands/Core/CoreCommandsModule.cs)
- [Commands/Core/CoreCommand.cs](Commands/Core/CoreCommand.cs)
- [Commands/Core/InitCommand.cs](Commands/Core/InitCommand.cs)
- [Commands/Core/ActivateCommand.cs](Commands/Core/ActivateCommand.cs)
- [Commands/Core/ServeCommand.cs](Commands/Core/ServeCommand.cs)
- [Commands/Core/BootstrapServiceCommand.cs](Commands/Core/BootstrapServiceCommand.cs)

These commands currently expose the existing lifecycle verbs:
- `init`
- `activate`
- `serve`
- `bootstrap-service`

The grouped `core` command exists as a command-class-owned subcommand container and demonstrates the intended extensibility model.

### Transitional forwarding layer
Added [Commands/Core/CoreCommandForwarder.cs](Commands/Core/CoreCommandForwarder.cs) so the new CLI can already invoke the existing core lifecycle flows while the service-oriented API-client layer is still being built.

## Current Architectural Direction
- The CLI package should own user-facing command parsing and UX.
- The core package should remain focused on runtime, service, storage, API, and orchestration concerns.
- Transitional direct forwarding is acceptable only until the hosted API-client command surface replaces it.
- Commands should remain modular and class-oriented so future domains can register themselves cleanly.

## Intentional Scope Limits For This Pass
The following are not yet complete in this package:
- full API-client transport usage for commands
- richer diagnostics and machine-readable output modes
- domain-specific CRUD/query commands over the hosted service
- plugin-facing command symmetry with future Obsidian and SIPA surfaces

## Validation Note
The CLI project builds successfully, and help output has been smoke-tested for both the root command surface and grouped subcommands.

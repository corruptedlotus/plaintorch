# PUCK Genesis

## Purpose
The `Pleiades.Puck` domain is responsible for identity generation and notation parsing.

## Main Parts
- `PuckFormatAttribute`: declares PUCK notation on CLR types
- `PuckNotation*`: models parsed PUCK syntax
- `PuckNotationParser`: parses declaration strings like `J{S:8}` or `X{D}`
- `PuckIdService`: issues concrete IDs and records them in persistence
- `PuckTokenizer`: derives baseline PUCK tokens from the original declaration and a concrete PUCK value
- `PuckRuntimeCompilationCatalog`: compiles and caches per-entity PUCK declarations/notations for the active vault runtime
- `PuckDateStampCodec`: centralized formatter/parser for date-stamp PUCK numerators across supported calendar variants
- `PuckSemanticProjector`: maps baseline PUCK tokens into higher-level semantic views without competing with the declaration
- `PuckEntityResolutionService`: resolves a PUCK into its owning entity and associated note when present
- `PuckRegistryEntry`: EF entity for already-issued IDs
- `PuckSequence`: EF entity for incremental counters

## How It Works
- A declaration string is parsed into segment patterns
- At vault startup, PUCK declarations are compiled and cached in-memory for all `PuckFormatAttribute` types
- During compilation, declaration signatures are validated for uniqueness and sibling shared-table discriminators must use explicit boundaries like `(x){I:4}`
- Each segment chooses a numerator strategy: manual, spiritgem, incremental, or date-stamp
- Date-stamp notation now supports optional calendar variants: `{D}`/`{D:g}` for Gregorian `yyyyMMdd`, and `{D:p}` for Pleiadean `yyyMdd`
- The generated segments are joined with telescope or filesystem separators
- Generated IDs are recorded so uniqueness and counters can be enforced
- CLR types decorated with `PuckFormatAttribute` can now receive centrally managed identifiers through type-based issuance, so PUCK notation remains executable behavior rather than passive metadata
- Concrete PUCK values can now be tokenized back through the original notation into baseline segment tokens
- Higher-level semantic extraction is now a second projection layer built on top of those baseline tokens, preventing generation/extraction drift
- Central reverse resolution is now supported through registry-first and notation fallback matching, then entity existence lookup by resolved type

## Current Canonical Notations (PEP082)
- `Directive` -> `{S:6}`
- `Objective` -> `j{S:8}`
- `OnrushSprint` -> `x{I:4:100}`
- `ExecutiveOrder` -> `x{?}-o{I:2:1}` (manual segment carries the owning onrush's trimmed numeric part, PEP099)
- `PolarisCycle` -> `{D:p}`
- `LorePage` -> `Era{?}/Cha{?}/Act{?}/p{?}`

## Incremental Sequence Scoping
Incremental counters are persisted in `PuckSequence`. A first-segment incremental keeps its historical key
(the declaration alone), while an incremental appearing after other segments is additionally scoped by the
already-rendered leading segments. This lets composite declarations count independently per parent — executive
orders restart at `o01` for each owning onrush — without disturbing pre-existing first-segment sequences.

## Persistence Notes
PUCK no longer talks to SQLite directly. It works through `PlainfraContext`, which makes identity issuance part of the same EF-backed persistence layer as the rest of the application.

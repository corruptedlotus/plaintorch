# Watcher Genesis

## Philosophy — a passive interface onto the user's vault

The watcher is a **passive interface** for the core, not an owner of the vault. The vault is the user's
knowledge base — journal, documentation, personal notes — and its files are theirs: doodles and passing poems
sit beside life-and-business decisions and full directive definitions. That overlap is exactly why the vault is
the right host for the PLAINTORCH database interface: a note can be the base for a directive, a journal can be
tracked within one, anything with content can control an entity, and any entity can reflect back onto a file.

The watcher exists to be **instructed by files** and to **reflect information back onto them** — through
mechanisms like note banners — so the database is *passively intertwined* with the vault. The watcher **does**
have the capacity for aggressive inference and enforcement, and that capacity is the danger: unchecked, it is
**destructive to the user's property**. So it must be **controlled and confined**. The vault is not PLAINTORCH's;
it is the user's. PLAINTORCH holds authority only where the user granted it:

- **By policy, in specific roots** — the user agrees that entity roots such as `Journal` (Polaris) and `Onrush`
  are PLAINTORCH's to manage, under that entity's declared storage policy.
- **By explicit act, everywhere else** — the user turns a note into an entity through **initialization**; until
  then, the file is theirs and untouchable.

The mindset to encode: an **effective, conservative bureaucracy**. The watcher carefully understands what files
*imply* — strictly through PUCK policy in the core — and reflects the core's state back onto files just as
carefully, all through **declarative protocols**, never ad-hoc inference.

## The two directions

1. **Files instruct the core (inference).** Does a change in a file mean a change in the database? Do a file's
   location, name, and frontmatter imply specific data to reflect onto the core? Inference is **conservative and
   PUCK-policy-gated**: a prefix is an identity only if it *tokenizes against the entity's declared PUCK*; a file
   belongs to an entity only if policy says so.
2. **The core reflects onto files (sync).** A change in the database may mean a change to a file's name, location,
   or frontmatter. Database validation may have corrected a mistake or invalidated an entity entirely — and that
   must be reflected onto the vault **per policy and per the state of entities and files**. You do not reflect
   anything for an entity that has no note; you do not mutilate a valid nested hierarchy over invalid frontmatter;
   you surgically remove an unknown PUCK from a stray note **without aftershock**.

## Policy philosophy

Storage is policy assigned to an entity (`VaultStorageAttribute`), and each policy encodes *how much authority the
user has ceded* in that entity's territory:

- **Synced / Optional / FileFirst** — a straightforward **two-way interface confined to an entity root**. They
  differ only in *which side may create or delete*: FileFirst is file-originated, Synced is bidirectional, Optional
  never creates new entities from standalone files (it only tracks ones it already owns).
- **Enforced** — the entity folder is a **clean "outward" interface** for the database: the core coins and controls
  the entities (e.g. Polaris cycles), so the root is PLAINTORCH's to keep clean, purging non-entity notes — while
  still letting the user add content *to* each entity's note (cycle journaling is the live use). Enforcement is
  authority the user granted for that root; it is not licence to misclassify a stray note as an invalid entity.
- **Freeform & Implicit** — the most Obsidian-style interface: the user turns **any note, anywhere** into an entity.
  Belonging is identity-driven (frontmatter PUCK), and the declared location is only a write-time default.
  **Freeform** suits significant, sparse, documentation-heavy entities that are worth their space (Directives).
  **Implicit** suits entities that usually have no content and are created often, so auto-materializing them as
  notes would clutter the vault (Incentives — Objective/Decree/Fate); they exist database-first and only begin
  syncing a file once a boundary is explicitly begun.
- **Index PUCK** (vs Quiet) — used when the PUCK *itself signals something* about the entity and lets files sort
  numerically (Polaris/Onrush journal files carry their identity in the filename).
- **Self-Named directory shape** (and Indexed, not yet implemented) — lets **entity nesting be reflected in the
  filesystem** and lets **extra, non-entity files coexist** in the folder (assets, media, sketches, extended notes).
  It suits large-scale entities with children and their own knowledge base (Directives, Onrushes).

## Engineering principles (the actionable translation)

1. **Identity is notation-gated, never string-shaped.** A filename prefix or frontmatter value becomes a PUCK only
   if it tokenizes against the entity's declared notation (as `VaultFamilyInstantiationResolver` does). A raw
   `" - "` split is not an identity.
2. **No entity is born without policy saying so.** Freeform/Implicit require identity + (for Implicit) a begun
   boundary; nothing outside a granted root becomes an entity, and no stray note is adopted as another entity's note.
3. **Removal is surgical and aftershock-free.** An unknown PUCK, or a non-entity note an enforced root rejects, is
   removed cleanly — it never first becomes an invalid entity that propagates a bogus PUCK into the database.
4. **Reflection is state-aware.** The core never reflects onto a note that does not exist, and never mutilates a
   valid nested hierarchy because of invalid frontmatter — validation corrects, it does not cascade destruction.
5. **Authority is confined to declared territory.** Outside granted roots the user is sovereign; the watcher reads,
   it does not enforce. Everything is decided by declarative policy, not by where the code happens to look.
6. **Startup and runtime agree.** A change made while the daemon is offline must reconcile at startup to the same
   state it would have reached as a live event — including deletions (which a file-driven scan misses today).

## Known violations (were pinned as skipped repro tests, steering phases 4 & PEP108-D)

These were the gaps between the code and the philosophy above, each captured as a skipped repro. **All are now closed
and green — the watcher suite carries zero skips.**

- **Loose-PUCK misparse** ✅ (`LoosePuckClassificationBugRepros`, `PathClassificationTests`): un-gated `" - "`
  parsing turned ordinary notes into invalid-PUCK entities (principles 1, 3). Fixed by the `PuckIdentityGate`
  notation gate — also stopped note-resolution binding to unrelated files.
- **Enforced self-named root misclassification** ✅ (`PathClassificationTests`): a directory event on an enforced
  root synthesized a `<root>/<root>.md` candidate (principle 5). Fixed by shape-gating the self-named fallback.
- **Redundant issue classification** ✅ (`WatcherStatusTests`): one cause raised three issues (bureaucratic noise).
  Fixed by the phase-D typed `VaultSyncConcern` — one root cause, one classified reason.
- **Offline-deletion parity gap** ✅ (`StartupRuntimeParityTests`): a deleted begun file left an orphan entity at
  startup (principle 6). Fixed by `ScanAsync`'s orphan pass, which now finds the note by identity rather than by a
  recorded path.
- **Unrecognised identity assertion in a non-exclusive root → Error, left in place** ✅ (`WatcherStatusTests`): the
  identity-driven, non-exclusive modes (Freeform/Implicit) decide an unrecognised-PUCK file to **`Ignore` (left in
  place, NOT purged) + `VaultSyncConcern.ForeignFile`**. A file that merely carries no identity is the user's own note
  and is left alone silently; but a file *asserting* a PUCK the vault does not recognise is illegal — a `foreign-file`
  **Error** demanding manual resolution (correct the identity, initialise it, or remove the assertion), not a silent
  warning. The core still does not destroy it (the alternative — surgically removing the PUCK — is deliberately deferred
  in favour of manual user action). **Enforced** — the core's granted territory — still purges as an Error. The
  `foreign-file` error is a *standing* status: a successful (no-op) sync does not clear it (leaving the file IS the
  outcome), only a clean re-inspection (file gone or now managed) or a user dismissal does. Pairs with the PEP108
  dismiss feature via `p7t-popover`.
- **Startup consistency pass stripped non-entity prefixes** ✅ (`NonEntityFileIsolationTests`,
  `NonEntityFileParityTests`): the startup auto-generated-PUCK consistency pass
  (`VaultAutoGeneratedPuckConsistencyService`) renamed `prefix - title.md` → `title.md` for *any* file the loose
  incentive candidate predicate reached — and that predicate's "hosted by a directive" branch resolved a containing
  directive by loose-parsing **any** dashed filename in the folder (the note's own included), with no notation gate
  and no DB-existence check. So a user's `Projects/2024-01 - Roadmap.md` was renamed at startup (principles 1, 5, 6 —
  the runtime watcher never did this, so startup and runtime diverged). Fixed by gating the pass twice, both
  policy-level and model-agnostic: the resolved prefix must **tokenize against the entity's declared PUCK**
  (`PuckIdentityGate`), and the file must sit in **declared territory** — a specific (non-vault-root) scan root, or
  a folder hosted by a parent entity that exists in the database. The hosting types are derived from the catalog
  (every declared `ParentEntityType`), never hard-coded, so the rule holds for any entity, not just directives.
  Outside that, the file is the user's own and is left alone. `AutoGeneratedPuckConsistencyTests` pins that the
  pass still normalizes/purges *within* granted territory. The same territory confinement was then applied to the
  **migration loader** (`VaultLoader`): the v1→v2 objective migration reads objectives under the legacy Index
  filename convention, and a PUCK-shaped prefix in a non-owned folder passed the notation gate and was migrated
  (prefix stripped) — the loader now trusts a filename-embedded identity only inside a specific scan root or a
  database-known hosting parent's folder (`NonEntityFileMigrationTests`).

- **Polymorphic family invisible to the watcher / duplicated on save** ✅ (`DirectiveOutOfRootDuplicationTests`): a
  directive is a Freeform family (`Directive` → `Stellar`/`Lunar`), but PUCK resolution reports the CONCRETE type name
  (`StellarDirective`) while the path-sync model is the abstract `Directive`. Two sites compared the two by string
  equality and mishandled every directive (principles 1, 5): **read** — Freeform `BelongsToModelAsync` compared the
  resolved concrete type to the abstract model name, so belonging failed and discovery **ignored every directive file**
  — never adopting an edit, never noticing a duplicate (this is why the watcher "took no issue" with a stray copy);
  **write** — `PlaintorchMarkdownStorageService` did an exact-type model lookup that missed the family model and fell
  back to scanning only the canonical `Directives` root, so editing a directive kept elsewhere wrote a **second** copy
  at the canonical location and orphaned the real file. Fixed by making both sides family-aware — `IsFamilyMember` on
  read; `IsAssignableFrom` + a territory-wide `VaultStoragePolicyEngine.EnumerateCandidateMarkdownPaths(model)` on write,
  so **write-side file location mirrors read-side discovery** for identity-driven entities. Directives are now
  reconciled two-way by the watcher, as Freeform intends.
- **Two files, one identity, no issue** ✅ (`DirectiveOutOfRootDuplicationTests`): an identity-driven entity may live
  anywhere, so two files can assert the same PUCK — and nothing detected the ambiguity; each file synced independently.
  The reconciler now raises a `duplicate-identity` **Error** on the `watcher.identity` operation, keyed on the
  **identity** (not a path) and naming the conflicting files, and clears it once only one file asserts the identity
  again. Detection is shared by the sweep (grouping the scanned candidates, O(n)) and a live reconcile (a targeted
  territory scan), so both emit the one same issue — sweep/runtime parity (principle 6). Left in place for manual
  resolution, like the foreign-file advisory.

- **A refused delete looped forever, one graveyard entry a minute** ✅ (`WatcherBlockedDeleteTests`,
  `WatcherIssueEmissionParityTests`, `WatcherRetrySchedulerTests`): a begun objective's note was deleted while executive
  records still referenced it (a restricting foreign key). The file-driven delete archived the objective to the database
  graveyard in its **own** `SaveChanges`, then the removal was refused — the entry was committed, the row stayed, the path
  was flagged `sync-failed`, and the retry sweep re-attempted it at the capped 60s cadence **forever** (the sandbox vault
  collected 1,936 graveyard entries for one objective). Worse, the startup sweep reconciles every candidate in one scope,
  so the refused removal stayed tracked and the next candidate's save re-flushed it and failed too. Fixed three ways:
  (1) **atomic archive** — `VaultTemporalDataService.StageEntityArchive` only *stages* the graveyard entry, committed by the
  caller's one save that removes the entity (the API deletes use it too), so a refused removal leaves no entry;
  (2) **blocked is not failed** — before a file-driven delete, `VaultEntityGateway.FindDeleteBlockersAsync` reads the
  model's restricting relationships (a foreign key that neither cascades nor nulls — the same rows the API refuses to
  orphan: an objective's executives, a directive's children) and, if any rows still reference the entity, writes
  nothing and throws `VaultEntityDeleteBlockedException`, which the reporter raises as a **`delete-blocked` Error** — a
  *standing* status like `foreign-file`: never re-queued by `WatcherRetryScheduler`, re-evaluated by a file event at the
  path (restoring the note resolves it) and by every sweep (which completes the removal once nothing references the
  entity), fingerprinted on the entity + blocking relationships so a dismissal holds across restarts. A blocked and a
  generic sync failure are one outcome per attempt — each supersedes the other; (3) **a failed candidate leaves nothing
  staged** — `VaultWatcherSyncService.ExecuteAsync` clears the change tracker when a candidate throws, so it can never
  fail the rest of a sweep. The watcher still never deletes more than the API would: it does not cascade or detach
  referencing rows to force the removal through.
- **A deleted file's content error outlived it, re-inspected every two seconds** ✅ (`StorageModeDecisionMatrixTests`,
  `WatcherStatusTests`, `WatcherRetrySchedulerTests`, `StartupRuntimeParityTests`): the sandbox's hand-made "Evanesca"
  executive order (a title-only note, whose PUCK needs caller-provided input) stood as a `puck-violation`. Once the user
  deleted it, the inspection of the missing path still reached the path-bound policies' identity-less branch — a
  conflict, purge or create verdict for a file that no longer existed — so the error stood; and the vanished-file
  re-check, which re-queued every non-retryable path status whose file was gone, re-inspected it every maintenance pass
  (1,021 times in 36 minutes). The same re-check re-ran a `delete-blocked` delete every 2 s, since its path is missing
  by definition. Fixed four ways: (1) every path-bound mode ignores a missing, identity-less path — which also stops the
  "purge" of the `<dir>/<dir>.md` primary a folder event synthesizes for a self-named model when that file never
  existed; (2) a missing file carries no content concern, so the inspection of a deleted file resolves its content
  flags; (3) the vanished-file re-check covers the content reasons only (`WatcherRetryScheduler.IsContentStatus`), once
  per appearance; (4) the orphan pass skips a begun boundary whose entity is already gone — boundaries are audit entries
  and outlive the delete they enabled, so dead ones were re-inspected at a vanished path on every sweep.
- **A boundary remembered its note's path** ✅ (`ImplicitBoundaryTests`, `StartupRuntimeParityTests`): an implicit
  boundary recorded where its note was, and a quiet note's deletion was read against that path. A note (or its folder)
  that moved and was then deleted left its entity behind, and a boundary outlived its entity. Implicit notes, like
  freeform ones, carry their identity inside the file (principle: identity is notation-gated, never positional), so a
  boundary is now an identity only, ends with its entity (`BoundaryEnd`), and a deleted note is found by identity: a
  standing boundary whose identity no note in the vault asserts any more
  (`VaultMarkdownDiscoveryService.FindVanishedNoteCandidatesAsync`), for the sweep and for a live delete event that
  names no identity alike. See `core/.DISCUSSION.md`, "Implicit boundaries are identities".
- **A withdrawn identity was only seen at startup; a deleted directive's note never** ✅ (`StartupRuntimeParityTests`,
  `WatcherBlockedDeleteTests`, `WatcherIssueEmissionParityTests`): the running watcher checked for vanished notes only
  after a delete that named no identity, so a stripped `puck` (an edit) waited for the next startup — a parity breach
  the parity tests missed because their runtime leg called a harness copy of the reconcile logic. A folder that was
  deleted or moved into `.trash` raised one event the watcher dropped for not being a note. And a freeform directive
  whose note was gone was never deleted at all. Fixed: the drain runs the vanished-note check (the sweep's own) after
  every batch that may have withdrawn an identity (`VaultWatcherReconciler.MayWithdrawIdentity`); gone paths are
  queued; freeform entities join the check (skipping writes pending in the outbox, dependents first); vanished-note
  issues are keyed on the identity (`watcher.identity`) and retried by re-running the check; and every leg of the
  parity tests now drives the production reconciler.
  Merging the blocked-delete fix with the severity regrade had also dropped `delete-blocked` from the reasons a
  successful sync clears, so neither restoring the note nor the unblocked delete resolved it; it is operational again.

The isolation and parity suites (`WatcherIsolationTests`, `StartupRuntimeParityTests`, `NonEntityFileIsolationTests`,
`NonEntityFileParityTests`) are the green counterpart: they pin the guarantees the philosophy promises where the code
already keeps them.

## Severity and standby (PEP108, regraded 2026-09-26)
Every reason the watcher raises carries **one** severity, whatever stage meets it, graded by what it means for the
watcher (`WatcherOperations` holds the table; `WatcherStatusReporter` applies it):

| Reason (operation) | Severity | Why | What the watcher does |
|---|---|---|---|
| `scan-failed` (startup-scan) | **fatal** | without its sweep it cannot trust what it observes (a broken database fails every reconcile alike) | sleeps on standby, retries the span on a 5 s → 60 s backoff |
| `vault-inaccessible` (vault-access) | **fatal** | the vault or an entity root cannot be reached | sleeps on standby, re-probes every 5 s |
| `roots-unresolved` (root, `*`) | **fatal** | no roots, no live observation at all | sleeps on standby, retries the span on the backoff |
| `fatal` (process) | **fatal** | a session fell through every guard | stays down until the next activation |
| `tick-failed` (drain-tick) | critical | a drain tick threw | carries on; clears on the next good tick |
| `discovery-failed` / `sync-failed` (reconcile) | critical | a file could not be inspected / a change could not be applied | retried per path, 2 s → 60 s |
| `permission-denied` (reconcile) | critical | the file may not be read or written | retried per path |
| `root-init-failed` (root) | critical | one root is not observed | the other roots carry on |
| `root-error` (root) | critical | an observer errored (events may be lost) | an overflow re-sweeps the vault, then resolves; any other error killed the observer, so the span restarts with a sweep and fresh observers (backing off if it keeps dying) |
| `markdown-invalid` / `puck-violation` / `policy-violation` (reconcile) | error, or **warning** when the watcher enforced it (rewrote or purged the file) | invalid content left in the user's file | stands until the user's edit re-inspects the file (never retried on a timer) |
| `foreign-file` (reconcile) | error | an identity the vault does not recognise, left in place | stands until the file is gone or managed, or is dismissed |
| `duplicate-identity` (identity) | error | two files assert one identity | stands until one file asserts it |
| `delete-blocked` (reconcile, or identity for a note found gone) | error | a deleted note's entity is still referenced (a directive's subdirectives or incentives, an incentive's child incentives; never its executives, which the delete releases) | stands, never retried; each sweep and each vanished-note check re-evaluates it, and a note asserting the identity again resolves it |
| `file-in-use` (reconcile) | warning | locked by another process | retried per path until it frees up |
| `relocation-failed` (relocation) | warning | the move fast path threw | logged only: both paths are re-inspected the plain way, which reports what stands |
| unknown reason | critical | unclassified means technical | — |

- **Fatal means asleep.** `VaultWatcherService` sleeps whenever a fatal condition stands — re-probing structural
  access, or retrying the live span on a backoff when the span could not start — and forces `Standby` health while it
  does. There is no "degraded startup mode" any more: a failed sweep is a sleep like the others.
- **Content stands until the user acts.** A successful sync clears the content reasons only when the watcher enforced
  them (rewrite/purge); a conflict leaves them standing, and the retry scheduler never re-checks them on a timer (the
  user's edit re-inspects the path). Operational reasons (locked, forbidden, failed) are retried per path.
- **Lost events are caught up.** An observer error flags its root (critical). An overflow is re-swept at the next
  maintenance step; any other error restarts the live span (sweep + fresh observers). A sweep that fails mid-span ends
  the span like a failed startup sweep. Content statuses whose file has vanished are re-inspected once, since no edit
  will ever arrive for them; a missing file has no content, so that inspection resolves them. A relocation carries its
  statuses to the new path.
- **Sessions start clean.** The status set is reset when a session starts and ends.

## Main parts

- `VaultWatcherService`: debounced filesystem-watcher host, session-gated to the active vault (idle when none)
- `VaultMarkdownDiscoveryService`: startup and on-change discovery, validation, and candidate construction
- `VaultWatcherSyncService`: executes a candidate's reconciliation action (create/update/delete/purge/rewrite). A
  file-driven delete is refused up front (`delete-blocked`) when rows still reference the entity, and otherwise commits
  its graveyard entry and the removal in one save; a candidate that throws discards whatever it staged.
- `VaultPathSyncModelCatalog`: the path-sync model set, a validated projection of `VaultEntityModelCatalog`
- `VaultFamilyInstantiationResolver`: identity-driven concrete-type selection for polymorphic families
- `Pleiades.Vault.Policy.*`: the storage-mode policy objects (`VaultStorageModePolicyRouter` + per-mode services)
  and `VaultSyncDecisionService`. Phase 4 gave these the pipeline's **semantic question set** — `IsIdentityDriven`,
  `MaterializesOnCreate`, `BeginsSyncBoundaryOnFirstFile`, `PurgesDesyncedFiles`, and the `ResolveWriteTargetPath`
  behaviour — so discovery, sync, storage, and consistency ask the protocol (`VaultStoragePolicyEngine.PolicyFor`)
  instead of testing the mode enum. A new mode is one policy object; a mode's behaviour change edits that object.
- `VaultWatcherReconciler`: the one reconcile-and-report path shared by the startup sweep and live runtime (inspect →
  report concerns → sync → report outcome), so both emit identical issues for an identical problem. It also raises the
  cross-file `watcher.identity` / `duplicate-identity` status (an identity asserted by more than one file), from a
  duplicate map the sweep builds by grouping candidates and a live reconcile builds by a targeted territory scan.
- `WatcherStatusReporter` / `WatcherOperations`: the watcher's adapter onto the PEP108 operation-status core.
  Classification is structural (PEP108 phase D): the reporter reads the decision's typed `VaultSyncConcern` — never
  the reason prose — so one root cause raises one classified reason. The reason string is human-readable detail only.
  The `duplicate-identity` reason is keyed on the entity identity rather than a path, so the one conflict yields one
  issue regardless of which file triggered its discovery. A failing check carries **only its specific detail** (the
  policy's reason, an exception message, a composed line) — never the reason's descriptor message, which is a function
  of the reason code and is resolved per request by the system API. The wire (`WatcherIssueRecord.Message` +
  `Detail`) therefore carries the two halves apart, so a client can show, fold, or hide the detail independently. Neither
  half is ever matched on: what identifies *this* problem for an Instance dismissal is `OperationStatus.Fingerprint`, a
  structural, culture-invariant string the reporter composes from facts (classified concern + action + offending field
  paths/values; entity id + files for a duplicate identity; the path for an access failure; the exception type for a
  sync/inspect failure), so a reworded or translated message never lifts or breaks a snooze.
- `Pleiades.Resources.WatcherMessages` / `MarkdownMessages` (`core/Resources/*.resx`): the **message sheets**. No
  pipeline component hardcodes operator-facing prose any more — a `WatcherOperations` descriptor names a `Reasons.*`
  entry, each mode policy's `VaultSyncDecision.Reason` comes from `Decisions.*`, the reporter's/reconciler's/service's
  composed detail lines from `Details.*`, `VaultWatcherPathPolicy`'s freeform ownership-boundary rejections from
  `PathViolations.*`, and every `MarkdownValidationIssue` message from the markdown sheet. Text resolves at raise time
  against `CultureInfo.CurrentUICulture` (the neutral sheet is English; a `<Sheet>.<culture>.resx` beside it localises)
  and a missing entry resolves to the bare key rather than throwing — a lookup can never take a run down. Because the
  text is now localisable it must never be classified on: the one place that did (`VaultEntityLifecycleService`
  recognising the missing-required-PUCK-input issue for manual init) now reads the structural
  `MarkdownValidationIssue.Code` (`MarkdownValidationCodes`). `MessageSheetCatalogTests` pins accessors ↔ sheet entries
  one-to-one, every reason code ↔ a `Reasons.*` entry, and each template's placeholders ↔ its accessor's arity.

## Known coupling constraint (phase 4)

The **Freeform policy depends on `PuckEntityResolutionService`** — its `BelongsToModelAsync` does full PUCK
resolution (registry + notation + DB existence) to confirm a file's frontmatter identity belongs to the model. That
makes `resolution → policy` a **DI cycle**, so two Freeform-specific behaviours cannot move onto the policy and stay
as documented, self-named helpers where they are: `PuckEntityResolutionService`'s self-named enumeration for freeform
notes, and (API-level, and domain rather than watcher policy) `DirectiveApiService.ShouldTreatAsManualFreeformInit`.
Breaking the cycle would mean reimplementing resolution inside the policy — a net loss — so it is left recorded here
rather than forced. Everything else in the core pipeline is de-leaked.

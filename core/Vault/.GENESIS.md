# Vault Genesis

## Purpose
The `Pleiades.Vault` domain bridges the application to the Obsidian vault and the SQLite database inside it.

## Subdomains
- `Pleiades.Vault`: vault-level settings, layout, and bootstrap operations
- `Pleiades.Vault.Markdown`: markdown metadata, frontmatter serialization, and file location rules
- `Pleiades.Vault.Database`: EF Core context, initialization, and repository access

## Main Parts
- `VaultOptions`: vault-level configuration
- `VaultLayout`: canonical filesystem paths
- `VaultStorageAttribute`: per-type file-backing policy, shape, PUCK storage form, dynamic parent composition metadata, and `RequiresParent` (fail-fast when an entity's path is only meaningful beneath a resolved owner, e.g. executive orders)
- `VaultImplicitBoundaryService`: tracks `BoundaryBegin` audit entries that gate implicit-entity synchronization boundaries
- `MarkdownFieldAttribute`: marks properties that should be reflected into markdown
- `MarkdownFrontMatterSerializer`: writes YAML frontmatter for markdown-backed entities and validates/reads typed frontmatter back into CLR models
- `MarkdownFileLocator`: computes canonical markdown file paths and reconstructs path-derived hierarchy. Forward path composition is now a thin façade over `VaultStoragePathComposer` (REFACTOR Alpha phase 2): the per-entity `Get*FilePath` switch is retired in favour of per-shape `IVaultStorageStrategy` objects driven entirely by declared `VaultStorageAttribute` policy (base name from `PuckStorage`, container from resolved parent + `PartitionUnder`, else the location root), with lore pages kept as an explicit per-type strategy for their RelativePath-authoritative placement
- `VaultStoragePathComposer` / `IVaultStorageStrategy`: declaration-driven canonical path composition per storage shape (`SelfNamedDirectory`, `SingleFile`), resolving effective policy through `VaultEntityModelCatalog`
- `LoreIndexer`: scans saga markdown files and stores a lightweight lore chronology index
- `PlainfraContext`: EF Core context for the vault database
- `PlainfraContextFactory`: creates design-time EF contexts for migrations
- `PlainfraContextInitializer`: applies migrations at startup
- `PlaintorchRepository`: application-facing persistence operations
- `VaultBootstrapper`: ensures required directories and database bootstrap
- `VaultTemporalDataService`: archives deleted entities and files into graveyards
- `VaultAuditLogService`: records soft-reference audit entries for application, discovery, and sync activity
- `VaultStorageTopologyValidator`: rejects ambiguous shared-root file-storage layouts before activation
- `VaultSchema` / `VaultVersionService`: declare and read/advance the vault schema version stored in `.plaintorch`
- `Pleiades.Vault.Migration`: the vault migration system (`VaultConventionSet`, `VaultLoader`, `VaultMigrationRunner`, `IVaultMigration`)
- `VaultPathSyncModelCatalog`: path-only sync model catalog for watcher/discovery logic
- `VaultMarkdownDiscoveryService`: startup and on-change markdown discovery, validation, and candidate construction
- `VaultWatcherService`: debounced filesystem watcher host for vault-backed markdown

## How It Works
- The vault root is resolved from options
- The `.plaintorch` file stores vault-local PLAINTORCH settings, including logical location key overrides
- The `.plaintorch-data` metadata folder contains the SQLite database by default
- The `.plaintorch-data/graveyard/files` tree preserves archived file-backed data after deletion while database tables preserve temporal metadata and serialized entity snapshots
- EF Core maps the current CLR model set into that database and now initializes it through migrations
- Only types explicitly marked with `VaultStorageAttribute` receive markdown file backing; all other types are database-only by default
- File-backed types now declare an explicit storage shape so self-named markdown directories and single-file entities can coexist safely under watcher roots
- Dynamic parent composition is now supported for file-backed entities such as nested directives and directive-contained objectives
- PUCK identity storage is now an explicit per-type policy (`VaultStorageAttribute.PuckStorage`, PEP091) decoupled from the storage mode:
  - `Quiet` (the default) stores identity as a `puck` frontmatter field and keeps a title-only filename
  - `Index` stores identity in the filename using the `{Puck token} - {Title}` convention
  - `PolarisCycle`, `OnrushSprint`, `ExecutiveOrder`, and `LorePage` are explicitly `Index`; `Directive` and `Objective` are `Quiet`
- `ExecutiveOrder` (PEP099) is `Synced`, single-file, and partitioned under its owning onrush sprint's `ExecutiveOrders` folder; its owning-sprint relation is path-derived and required, so order files under unknown sprint directories surface as conflicts instead of creating entities
- `VaultStorageMode.Implicit` (PEP091) behaves like `Freeform` (identity-driven ownership) but does not initially materialize a file. An implicit entity begins syncing only once its file starts existing through any means (an API `begin` prompt, a canonical rewrite, or a user-authored file), at which point a `BoundaryBegin` audit entry is recorded once. From then on, deleting the file authoritatively removes the database entity. The `AuditLogEntry.Action` column is indexed so these boundary checks stay cheap. `Objective` is the first implicit entity; deletions of its quiet (title-only) file recover identity from the boundary entry's recorded path.
- Path-derived relations are mirrored into frontmatter for readability, but discovery and sync treat the path as authoritative
- Canonical markdown rewrites now preserve existing markdown body content verbatim; vault storage authority is limited to metadata normalization and canonical file identity
- Canonical metadata rewrites now preserve unknown frontmatter keys while still normalizing authoritative fields declared through `MarkdownField` metadata and `puck`
- Saga lore remains file-first, but a lightweight database index is rebuilt from canonical saga markdown paths so chronology can be queried without moving lore authority out of the vault files
- The vault root is now protected by `.plaintorch.lock` while the active service instance owns it
- The watcher/discovery layer now scans the configured vault roots, resolves candidate model type from path only, validates frontmatter into CLR models, and emits provisional sync decisions while suppressing service-originated write loops
- Parent-composed canonical storage paths can now be resolved generically from `VaultStorageAttribute` metadata rather than requiring each application caller to hand-assemble domain-specific save logic
- The vault now carries a schema version in `.plaintorch` (`SchemaVersion`) that tracks its on-disk conventions independently of the EF database schema (PEP092). Missing ⇒ baseline (pre-PEP091). A fresh vault is stamped at the current version.
- Vault migrations run at initialization, after the database is migrated and before the consistency reconcile, through `VaultMigrationRunner`. They follow a load-then-re-canonicalise model: a `VaultLoader` reads the vault under the `VaultConventionSet` for the version it is stored at (identity from filename for `Index`, from `puck` frontmatter for `Quiet`), and each entity is re-emitted under the current conventions via `PlaintorchMarkdownStorageService.RecanonicalizeAsync`, which preserves the markdown body. Legacy files are snapshotted to `graveyard/files/migration-v{from}-to-v{to}` before rewrite, and each applied migration is recorded in `VaultMigrationHistory`.
- Only the loader is convention-parameterised; the writer always emits current conventions, since migrations only ever move a vault forward. This keeps the hot watcher/write pipeline on a single code path.
- The first migration (v1→v2) re-canonicalises pre-PEP091 objective files (`{id} - Title.md`, no `puck`) into the quiet form (`Title.md` + `puck`) and begins each objective's implicit synchronization boundary.

## PEP100 Persistence Notes
- The `Objectives` table was renamed to `Incentives` and now hosts the TPH incentive family
  (`Objective`/`Fate`/`Decree`) through a `Discriminator` column; `Directives` hosts the directive family
  through a discriminator over the abstract `Directive` base and its `StellarDirective`/`LunarDirective`
  siblings. The `LunarStellarDirectiveSiblings` migration makes the shared `Status` column nullable (it now
  holds only stellar state) and rewrites legacy concrete `Directive` rows to `StellarDirective`; lunar state
  keeps its own `LunarStatus` column.
- Fates and decrees follow the same vault policy as objectives: `Implicit` mode, single-file shape, quiet
  PUCK storage, with their own standalone roots (`Fates/`, `Decrees/`) and directive partition folders
  (`Fates/`, `Decrees/` under a directive). Creation does not materialize a file; `POST /api/fates/{id}/begin`
  (or `/api/decrees/{id}/begin`, or a user-authored file with matching `puck` frontmatter) begins the
  synchronization boundary, after which file deletion is authoritative. Identity-driven belonging (frontmatter
  puck tokenized per declaration: `j`/`e`/`r`) keeps the three incentive kinds path-distinguishable even
  though they share the vault-root scan space.
- The incentive parent relation (`ParentIncentiveId`) is deliberately not markdown-mapped; watcher file syncs
  preserve it from original values so frontmatter rewrites can never clear parenting.
- A declarative's orbit notation IS markdown-mapped (`orbit`); when a file sync changes it, the persisted
  `OrbitScheduleState` row is reset so the schedule re-anchors. Engine state itself lives in its own table,
  never in frontmatter or API payload surfaces.
- Attentives, eventives, timeframes, and orbit schedule states are database-only dependent records like
  executives.
- Stellar and lunar directives keep freeform file backing but store in different locations: stellar under the
  `Directives` root, lunar under a dedicated `Moonlight` root (default `./Moonlight`, declared by
  `LunarDirective`'s own `VaultStorage`). Because the base `Directive` is abstract, the directive path-sync
  model carries a concrete instantiation type (`StellarDirective`) so path composition and vault loading never
  attempt to construct the abstract base; the directive family is otherwise resolved only through explicit
  init (`POST /api/directives/init`) and the API. Each kind's `status` is markdown-mapped and mutated through
  its own workflow shift. Unknown `LUNA` puck assertions in files follow the existing unknown-freeform-puck
  purge policy rather than creating entities.

## Dependency System Persistence (PEP101)
- `Dependencies` and `Checkpoints` are new database-only tables. `Dependency` has an autoincrement `long` key
  and flat endpoint columns (`Source*`/`Target*` kind, id, and optional recurrence date/time), enum-as-string
  `SourceKind`/`TargetKind`/`Trigger`/`Constraint`, and indexes on `SourceId`/`TargetId`. Endpoints are loose
  references (no FK), like `CelestronTransaction.SourcePuck`.
- `Checkpoint` is a PUCK-addressable entity (`c{S:4}`) with **no** `VaultStorage`, so it is valid against the
  entity-model-catalog rules (a PUCK entity needs no vault file) and is database-only.
- `Eventive` gained a stable `RecurrenceId` (`RecurrenceDate` + optional `RecurrenceTime`) capturing the
  occurrence's original slot; the `AddDependencySystem` migration adds it with a best-effort backfill from the
  current `Date`/`StartTime`. Materialization and orbit dedup now key on the recurrence slot, not the mutable
  `Date`.
- A checkpoint toll is a negative `CelestronTransaction` (no schema change); the banked balance stays the live
  ledger sum.

## Entity Model Catalog & Gateway (glue thinning, phases 0–1)
- `VaultEntityModelCatalog` (singleton) reflects every type declaring `PuckEntity`/`PuckFormat`/`VaultStorage`
  into one declarative registry: own kind and PUCK declaration, plus the *effective* storage policy and the
  type in the hierarchy that declares it (stellar anchors on the abstract `Directive`; lunar declares its own
  `Moonlight` policy). Storage entries are policies to interpret — identity-driven modes (Freeform/Implicit)
  deliberately do not bind an entity to its declared location; the location is only the canonical default.
- `VaultBootstrapper` validates the catalog at activation (fail fast): PUCK formats require kinds, kinds are
  unique, storage-bearing entities are PUCK-named, abstract anchors have concrete members, and concrete
  entries are registered in the EF model.
- `VaultEntityGateway` (scoped) replaces the per-type `typeof`/DbSet dispatch chains with declaration-driven
  data access: id lookups over `Set<T>()` (abstract anchors span their whole discriminated family — identity
  discipline comes from PUCK tokenization upstream, and multi-declaration ambiguity is rejected by the
  resolution layer), known-id loading for path-sync models, and generic previous-state snapshots covering all
  mapped scalars plus owned references (e.g. the Polaris forecast).
- Consumers thinned onto the gateway: `PuckEntityResolutionService` (entity-by-id chain), watcher
  `LoadExistingAsync`/`CloneEntity`, the path-sync catalog's known-id loaders, and the directive API's
  previous-snapshot clone.

## EF Mapping Approach
- Table and column naming now mostly follows EF Core conventions, so the physical schema defaults to implicit `PascalCase` names
- `PlainfraContext` is kept for the pieces annotations do not express well: enum conversions and JSON conversion for directive tags
- Predefined tag metadata lives in `TagDefinitions`, while directives keep only assigned tag ids in their tag list
- Lore indexing stores only lightweight references and extracted chronology tokens, not canonical lore body content
- Audit and graveyard tables intentionally use soft references and standalone archival keys so temporal history survives duplicate lifecycles and later retention cleanup
- Navigation properties are preferred so aggregate shape is visible in the CLR model instead of being inferred only from Fluent API
- `Executive` and `Reflective` are mapped through navigation properties from `PolarisCycle`, so they do not need top-level `DbSet` properties to participate in persistence
- Shared scan roots are only allowed when path-discriminability and storage-topology validation can still distinguish model identity without consulting the database

## Design Note
This domain owns persistence and vault I/O. It should stay infrastructure-facing, while orchestration and PUCK stay focused on domain behavior.

Recent boundary clarification:
- watcher and canonical storage code must not synthesize markdown bodies or default headings
- any future note templating belongs in explicit higher-level authoring flows, not in vault persistence infrastructure
- frontmatter validity and authority are now scoped to explicit markdown field mappings, which avoids deleting or invalidating unrelated custom frontmatter data

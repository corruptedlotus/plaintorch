# PLAINTORCH Genesis Log

## Rules of Engagement
This part is written by Susu, the original creator. Machines and humans who are contributing to this project please make sure you follow these simple conventions while working on the project:
- Make sure you add XML documentation (and other forms of in-code documentation for other languages) to keep the components of the system identifiable and clarified.
- Check the latest .OPERATION file in root for the current project heading objectives. If you complete any of those objectives, mark them.
- Check .ORIGIN for the ideas behind the project.
- Keep .GENESIS files in every domain updated with information on what has been developed in there, what they do, and briefly on how they work.
- Update the root .DISCUSSION file to include your concerns, uncertainties and requirements for the project. Remove them when they're no longer relevant.
- DO NOT, I repeat, do not run `serve` with project root as a vault. Use `./_sandbox` as your test vault.

## Purpose
Initial foundation for PLAINTORCH based on the blueprint in the introduction document, with an Obsidian-vault-first layout and managed SQLite persistence.

- Per-user host configuration now lives outside the vault so a single active vault can be selected per user profile and future socket transport can live alongside that shared config
- A dedicated application API contract layer now exists under [Plaintorch/Api](Plaintorch/Api) and mirrors the blueprint action taxonomy for directives, objectives, onrush, Polaris, and system actions
- The application API is now implemented through distinct action-area modules and services under [Plaintorch/Api](Plaintorch/Api), with a shared aggregate `IPlaintorchApi` façade and reusable state/markdown helpers
- The API surface is now physically mirrored into `Abstractions`, `Contracts`, `Transport`, `Services`, and `Endpoints`, while non-API helpers have been moved into dedicated markdown and state domains

- The application shell now includes a hosted core worker and cross-platform service bootstrap asset generation for Windows Service and systemd-style user service installation
- The hosted service now listens on the per-user PLAINTORCH socket path and exposes HTTP API endpoints over that unix domain socket transport
- The hosted service also exposes a fixed local loopback HTTP endpoint for desktop integrations such as the Obsidian plugin, which avoids platform friction when socket clients are unreliable on Windows
- Onrush and Polaris API routes have now been normalized to the shorter `/api/onrush/*` and `/api/polaris/*` forms instead of pluralized long-form route groups
- The system API now also supports PUCK reverse resolution through `/api/system/resolve/{id}` and `/system/resolve/{id}`
- System note-resolution now includes a freeform fallback that reads markdown frontmatter `puck` and resolves associated entities when path-shape catalog detection does not classify the note
- Directive API now also supports file-driven initialization through `/api/directives/init`, reusing watcher create-from-file policy logic for manual freeform onboarding
- Directive init now strictly applies watcher reconciliation policy for PEP090 freeform onboarding: only valid `CreateFromFile` candidates are initialized, while policy/validation violations are rejected with concrete path-boundary reasons
- Directive init now explicitly supports manual onboarding of freeform markdown files with no PUCK frontmatter by upgrading the watcher `Ignore` no-PUCK case into `CreateFromFile` for API-initiated init only
- Core startup, migration application, lore reindexing, and markdown writes now have async-capable paths for service execution
- Deleted entities and deleted file-backed artifacts can now be archived into temporal graveyards, with audit entries capturing soft entity references and temporal entry keys
- The vault watcher runtime now exists under [Vault/Watcher](Vault/Watcher): startup discovery scans, path-only model detection, markdown validation, reconciliation decisioning, debounced filesystem watches, self-write suppression, and execution of supported create/update/rewrite/purge sync actions are now implemented
- Watcher rename handling now performs relocation-first reconciliation so parent-folder moves are applied as relocation updates before falling back to standalone path handling
- Watcher path policy has been centralized through `VaultWatcherPathPolicy`: live events and startup scans now exclude hidden/underscore-prefixed folder segments and Obsidian attachment folders configured via `.obsidian/app.json`
- Watcher startup sweep now runs with deterministic reconciliation ordering (existing-entity update/rewrite pass before creation/purge/conflict actions), aligning behavior with the watcher blueprint's startup sequencing intent
- Watcher runtime observability now runs on the PEP108 operation-status core (`Pleiades.Diagnostics`): each pipeline stage reports a full check-set per run through `WatcherStatusReporter` (over the `WatcherOperations` catalog), and the `OperationStatusRegistry` diffs it into raise/escalate/de-escalate/resolve transitions keyed `(operation, scope, reason)` on a graded severity scale (`Info/Warning/Suspended/Error/Critical`) with a suspension-aware health rollup. Transitions persist durably to `OperationStatusEvent`. The system API maps this onto the unchanged `WatcherIssueReport`/`SystemBriefing` wire contract (health → `ok/standby/issues/offline`); a locked file now surfaces as a first-class suspension (`standby`). This replaced the earlier hand-marked `VaultWatcherIssue*` registry/signal/type system.
- Watcher issue typing now includes concrete major failure classes for user-facing diagnostics (filesystem permission denials, file-in-use lockouts, markdown validation/parsing failures, PUCK identity violations, storage policy violations) in addition to runtime-stage issues
- `SystemBriefing` now also includes watcher criterion totals (`WatcherCriteriaCount`, `WatcherFailedCriteriaCount`) to reflect runtime criteria coverage beyond raw issue counts
- System API now provides full watcher diagnostics endpoints: `/api/system/watcher/issues` and path-scoped `/api/system/watcher/issues-for?path=...`, returning typed issue + criterion records with criticality, descriptions, criteria metadata, and originating path information
- Path-model detection now treats storage partition folders as explicit non-entity containers, preventing partition index files/directories from being promoted to directive candidates
- Objective detection inside directive trees now respects configured partition naming (`PartitionUnder`) when classifying directive-root objective notes
- Freeform directive ownership boundaries are now enforced in discovery and aligned with markdown storage assertion rules, blocking freeform assertions in non-directive managed roots while preserving canonical/default directive locations
- Freeform boundary enforcement now also rejects attempts to assert ownership of key directories (vault root, entity roots, partition folders), aligning directive freeform placement with PEP090 root-node rules
- Self-named model candidate detection now excludes root-level same-name files under entity roots (for example `Onrush/Onrush.md`), preventing startup sweep false-positive creations
- Directive parent-id path inference now falls back to frontmatter `puck` when filename identity is absent, allowing objective files in directive-local partition folders to be discovered and linked under freeform directive naming
- Containing-directive inference now also resolves freeform parent directories where the directive anchor note is not self-named with the folder (for example `Nooo/Mewo!.md`), preserving watcher pickup for nested partition objectives
- Watcher policy decisioning is now split into mode-specific services (`FreeformVaultStorageModePolicyService`, `EnforcedVaultStorageModePolicyService`, `OptionalVaultStorageModePolicyService`, `SyncedVaultStorageModePolicyService`, `FileFirstVaultStorageModePolicyService`) routed through a mode-policy router/engine
- Freeform watcher model ownership is now identity-driven (frontmatter `puck` + PUCK resolution) instead of path-shape matching, and freeform files without PUCK are excluded from automatic watcher initialization
- Containing-directive inference now uses centralized watcher ownership-boundary policy so root folders (vault root/entity roots/partition folders) cannot be treated as directive-owned containers
- The hosted core's composition root moved into `Plaintorch/Hosting` (`PlaintorchHostFactory`), `serve` gained launch modes (interactive / `--daemon` / `--spawn`) with file logging and a spawn-mode stdout status protocol, and the earlier PowerShell splash popup was replaced by an observable `PlaintorchHostState` that the desktop shell under `../standalone` renders; see `Plaintorch/.GENESIS.md`
- Centralized operational state policy enforcement now exists under [Plaintorch/State](Plaintorch/State): reusable state-policy processing is executed through EF Core save hooks so onrush/polaris exclusivity, objective settlement ledger updates, and superseded Polaris-forecast cleanup are applied consistently across write pathways

## Current Architectural Direction
- Obsidian vault is the filesystem source for human-authored content.
- SQLite inside the vault is the structured source for indexed state and relations.
- EF Core is now the sole persistence access layer; direct SQLite command usage has been removed from application services.
- The application shell now composes its DI graph through A11d modules instead of wiring each service directly in `Program`.
- Markdown files are generated in an Obsidian-friendly layout.
- Source layout is domain-driven rather than split by technical categories.
- `Operations` has been folded into `Orchestration` to keep work-execution concepts in a single domain.
- Objective colleges now align with the updated action-college list: `Swords`, `Creation`, `Lore`, `Eloquence`, `Glamour`.
- Tags can now be defined ahead of time through `TagDefinition`, with semantic palette names stored separately from eventual UI colour values.
- Table and column names now rely on EF Core conventions instead of explicit overrides, keeping the schema aligned with CLR `PascalCase` names unless conventions require otherwise.
- XML documentation comments are being added across the created code surface so the domain model and infrastructure APIs remain self-describing.
- Current implementation prioritizes bootstrap, persistence, and identity scaffolding.
- User-level host state is now beginning to form around active-vault selection and future socket placement.
- The next transport/runtime work can now target a stable implemented application layer instead of inventing ad hoc command shapes.
- Sync model detection is now explicitly path-only, and file sync policy is driven by `VaultStorageAttribute.Mode` rather than inferred from CLR type usage sites.
- The hosted runtime now has first-pass reconciliation execution for watcher-discovered file changes, including canonical markdown sync-back, file purging, and file-originated creation/update flows for supported file-backed models.
- Canonical markdown storage is now deliberately domain-independent at the write-path level, with parent hierarchy resolution and canonical path composition driven by storage metadata rather than per-entity save logic.
- Parent-reassignment path changes for self-named entities (including `FileFirst`) now relocate the full entity directory tree (including children) instead of only rewriting/deleting the primary markdown file.
- Markdown body preservation is now an explicit system rule: watcher and API storage flows may normalize frontmatter, filename, and path, but must not synthesize or mutate user-authored markdown body content.
- The repository is now a monorepo container rather than a single-package root, and a dedicated CLI package exists under `../cli` with its own command-engine foundation.
- State-transition invariants are now treated as persistence-time policy rather than endpoint-local etiquette, so the same rules can be reused and enforced wherever tracked entities are saved.
- PUCK identity storage form is now decoupled from storage mode via `VaultStorageAttribute.PuckStorage` (PEP091): `Quiet` frontmatter identity is the default, and `Index` filename identity is opt-in for `PolarisCycle`, `OnrushSprint`, and `LorePage`.
- A new `Implicit` storage mode (PEP091) provides freeform-style identity ownership without initial file materialization; its synchronization boundary is tracked through `BoundaryBegin` audit entries, and `Objective` now uses it (quiet frontmatter identity, file created on demand, boundary-authoritative deletion).
- A vault migration system (PEP092) now runs alongside database migration: the vault carries a `SchemaVersion` in `.plaintorch`, and at startup a `VaultMigrationRunner` upgrades on-disk conventions by loading the vault under the stored version's `VaultConventionSet` and re-canonicalising each entity under the current conventions (body-preserving, graveyard-backed, idempotent). This is also the first abstraction of the vault↔database boundary; its first migration backfills legacy objective files into the PEP091 quiet form.
- The core now has an automated test suite (PEP093) in `../core.tests` (xUnit), driving the real DI graph over a fresh isolated vault per test through the `TestVault` harness. `serve` gained an isolated dev environment: `--ephemeral` (random user-independent temp profile, used by tests/sandbox), socket-only transport by default with opt-in `--loopback`, and — for an ordinary manual `serve` — a persistent per-user development sub-profile under `~/.pleiades/plaintorch-dev` (isolated from the real per-user daemon but, unlike the ephemeral profile, kept across runs and never auto-removed); `serve --daemon` opts a manual serve back onto the real `~/.pleiades/plaintorch` profile for developers building their own background daemon. Coverage is tracked in `_documents/Criteria - Validators, Checks & Unit Test.md`.

## Intentional Scope Limits For This Pass
The following were not fully implemented in this pass because the blueprint does not yet define enough behavior:
- final file deletion monitoring and recreation rules for relation-protected entities
- lore entity CLR models and PUCK reverse parsing from nested lore files
- reflective generation engine
- celestron ledger ducking logic
- `.puck` declaration file loading
- full CRUD/query CLI client transport over the hosted API

## Monorepo Extension
PLAINTORCH now also includes a sibling CLI package in [../cli](../cli) that is intended to become the primary user-facing application surface over the hosted core.

The CLI currently provides:
- a modular command registry
- command-to-class routing
- command-owned subcommand registration
- typed semantic option binding through attributes
- DI-based command activation
- generated root and command help text

Its first commands currently forward to the legacy core entrypoints while the API-client surface is still being developed.

# Orchestration Genesis

## Purpose
The `Pleiades.Orchestration` domain contains the operational story/work models.

## Main Models
- `Directive`
- `OnrushSprint`
- `ExecutiveOrder`
- `Objective`
- `PolarisCycle`
- `PolarisForecast`
- `Executive`
- `Reflective`
- `CelestronTransaction`
- `TagDefinition`

## Model Intent
- `Directive`: long-running major directive, optionally nested
- `OnrushSprint`: short-term focused sprint
- `ExecutiveOrder`: special constraint or direction shaping how an onrush sprint is moved through (PEP099)
- `Objective`: goalpost attached to directives and/or onrush sprints
- `Objective`: goalpost attached to directives and/or onrush sprints, optionally marked as enduring/repeating
- `PolarisCycle`: one daily cycle, either forecast or anecdotal
- `Executive`: execution record within a cycle, optionally standalone and self-titled without a backing objective
- `Reflective`: reflective task record within a cycle
- `CelestronTransaction`: ledger entry for reward/loss accounting
- `TagDefinition`: predefined tag catalog entry with a semantic palette colour

## Tag Registry
- Directives keep assigned tags as a lightweight string list.
- `TagDefinition` provides a place to define valid tags ahead of use.
- `TagColor` uses semantic palette names: `Anna`, `Eris`, `Lulu`, `Nilou`, `Emi`, `Sana`, `Light`, and `Void`.
- `TagPalette` exposes stable UI-facing tokens so future clients can map those semantic colours into actual theme values without changing stored records.

## Workflow States
- `DirectiveStatus`: `Planned` → `Committed` → `Active` → `Fulfilled` → `Over`
- `ObjectiveStatus`: `Standby` → `[Blocked]` → `Onrush` → `Polaris` → `Done` → `Archived`

`Blocked` is treated as an interrupting state for objectives rather than part of the main forward flow.

## Persistence Shape
These types are plain CLR entities decorated with markdown metadata and EF data annotations. Conversions that annotations cannot express, like JSON storage for directive tags or enum-as-string storage, are configured centrally in `PlainfraContext`.

## Navigation Shape
The orchestration model now leans on navigation properties so the object graph expresses intent more clearly:
- `Directive` links to its parent, subdirectives, and related objectives
- `OnrushSprint` exposes its objectives
- `Objective` links back to its directive and onrush sprint, and can collect execution records
- `Objective` can now also mark whether the commitment is enduring/repeating, which gives the domain a durable counterpart to transient one-shot work
- `PolarisCycle` owns the operational details of the day through `Executives` and `Reflectives`

This allows the model to distinguish durable intent from ephemeral action:
- enduring or repeating work belongs on `Objective`
- one-shot operational work can now live directly on `Executive`

This keeps `Executive` and `Reflective` as dependent records that matter primarily inside a cycle rather than as top-level sets.

## Executive Orders
`ExecutiveOrder` (PEP099) attaches durable constraints or directions to an `OnrushSprint`:
- required `Title` (PUCK-named) and owning `OnrushSprintId`
- optional `Summary`, `EffectiveFrom`, and `EffectiveUntil` fields

Identity uses the composite PUCK declaration `x{?}-o{I:2:1}`: the manual first segment carries the owning
onrush's trimmed numeric part, and the order counter increments per owning onrush
(`Onrush x0180 -> E.O. x180-o01`). Orders are stored `Synced`, as single files, in the owning sprint's
`ExecutiveOrders` partition folder with `Index` PUCK storage.

## Executive Time Allocations
`Executive` carries three optional whole-minute working-time-unit allocations (PEP098):
- `Estimation`: the primary allocation, which also doubles as a lightweight progress marker. The sum of estimations across a cycle's executives expresses the day's total workload.
- `Minimum` / `Maximum`: optional bounds on the allocation.

`Executive.NormalizeTimeAllocations()` enforces the coupling and clamping rules so the three values stay coherent regardless of the order they are supplied:
- when a bound is present but the estimation is still unset, the estimation adopts that bound (preferring the minimum);
- the estimation is always clamped into the `[Minimum, Maximum]` envelope when the relevant bound is present.

Alongside the allocations, `Executive` carries `Elapsed` (Patch098.1): the raw count of tracked (passed) minutes. Unlike the allocations it is a running tally rather than a target — it defaults to `0` and is deliberately excluded from `NormalizeTimeAllocations` (never clamped). It is intentionally *not* part of executive planning (`PolarisExecutivePlan`) because a freshly planned executive has not been worked, so its tracked minutes always start at `0`; it only accrues later through `ExecutiveUpdate`, where `null` leaves it unchanged and any value (including `0` to reset) overwrites it. It has no `Clear` flag because it is never unset.

The application/API layer applies these values (at plan time via `PolarisExecutivePlan`, or via `ExecutiveUpdate`) and then calls the normalizer before persisting. The minute-based storage form is translated for consumers in the application/UI layer (see the SDK working-time-unit helpers) rather than in the domain model.

## EF Shape
Most persistence shape now comes directly from the entities:
- navigation properties
- foreign-key properties
- data annotations

`PlainfraContext` only keeps the pieces that conventions and annotations do not express well, mainly value conversions.

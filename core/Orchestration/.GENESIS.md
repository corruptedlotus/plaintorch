# Orchestration Genesis

## Purpose
The `Pleiades.Orchestration` domain contains the operational story/work models.

## Main Models
- `Directive` (abstract) / `StellarDirective` / `LunarDirective`
- `OnrushSprint`
- `ExecutiveOrder`
- `Incentive`: `Objective`, `Fate`, `Decree`
- `PolarisCycle`
- `PolarisForecast`
- `Executive`
- `Reflective`
- `Attentive`
- `Eventive`
- `Timeframe`
- `OrbitScheduleState` (abstract) / `IncentiveOrbitScheduleState` / `TimeframeOrbitScheduleState`
- `CelestronTransaction`
- `TagDefinition`
- `Dependency` / `Checkpoint`

## Model Intent
- `Directive`: abstract base shared by the two directive siblings; carries identity, nesting, tags, and incentives (PEP100), plus an optional database-only availability timeframe (PEP100 patch 2)
- `StellarDirective`: long-running directive with a lifecycle `Status` and optional scheduling dates, optionally nested
- `LunarDirective`: everglow Moonlight directive acting as a law/routine/requirement; table sibling of `StellarDirective` through a discriminator, with its own moonlight `Status` and `Timeframes` (PEP100)
- `OnrushSprint`: short-term focused sprint
- `ExecutiveOrder`: special constraint or direction shaping how an onrush sprint is moved through (PEP099)
- `Incentive`: abstract base of the declarative ecosystem; objectives and declaratives share its table with discriminators (PEP100)
- `Objective`: goalpost attached to directives and/or onrush sprints — one-shot by nature; recurring commitment is a `Decree`
- `Fate`: event-like declarative that happens rather than gets done; all-day or timed, orbit-schedulable (PEP100)
- `Decree`: enduring routine/law controller declarative that materializes attentives; exempt from parenting (PEP100)
- `PolarisCycle`: one daily cycle, either forecast or anecdotal
- `Executive`: execution record within a cycle, optionally standalone and self-titled without a backing objective
- `Reflective`: reflective task record within a cycle
- `Attentive`: per-occurrence instance of a decree, executive-shaped, never bound to a cycle (PEP100, PEP111)
- `Eventive`: per-occurrence instance of a fate or objective due date, executive-shaped, never cycle-bound (PEP100)
- `Timeframe`: directive-level definition of a portion of the day, purely semantic (PEP100). It can auto-include workitems (by college, or as a directive availability) and can be exclusive among the timeframes active at once (PEP100 patches 1 and 2)
- `OrbitScheduleState`: abstract persisted Orbit engine state (snapshot, epoch, seed) that anchors an owner's orbit. `IncentiveOrbitScheduleState` anchors a declarative's orbit and `TimeframeOrbitScheduleState` a timeframe's; they share one table through a discriminator (PEP100 patch 2)
- `CelestronTransaction`: ledger entry for reward/loss accounting
- `TagDefinition`: predefined tag catalog entry with a semantic palette colour

## Tag Registry
- Directives keep assigned tags as a lightweight string list.
- `TagDefinition` provides a place to define valid tags ahead of use.
- `TagColor` uses semantic palette names: `Anna`, `Eris`, `Lulu`, `Nilou`, `Emi`, `Sana`, `Light`, and `Void`.
- `TagPalette` exposes stable UI-facing tokens so future clients can map those semantic colours into actual theme values without changing stored records.

## Workflow States
- `DirectiveStatus`: `Planned` → `Committed` → `Active` → `Fulfilled` → `Over`
- `LunarDirectiveStatus`: `OnHold` / `Active` / `Stale` (no forward lifecycle — lunar directives are everglow)
- `ObjectiveStatus`: `Standby` → `[Blocked]` → `Onrush` → `Polaris` → `Done` → `Archived`
- `FateStatus`: `Active` / `OptOut` / `Cancelled`
- `DecreeStatus`: `Active` / `Abandoned`
- `AttentiveResolution`: `Pending` → `Done` / `Skipped`
- `EventiveResolution`: `Pending` → `Missed` / `Cancelled` (passing is temporal, not stateful)

`Blocked` is treated as an interrupting state for objectives rather than part of the main forward flow.

## Persistence Shape
These types are plain CLR entities decorated with markdown metadata and EF data annotations. Conversions that annotations cannot express, like JSON storage for directive tags or enum-as-string storage, are configured centrally in `PlainfraContext`.

## Navigation Shape
The orchestration model now leans on navigation properties so the object graph expresses intent more clearly:
- `Directive` links to its parent, subdirectives, and related objectives
- `OnrushSprint` exposes its objectives
- `Objective` links back to its directive and onrush sprint, and can collect execution records
- `PolarisCycle` owns the operational details of the day through `Executives` and `Reflectives`

This allows the model to distinguish durable intent from ephemeral action:
- enduring or repeating work belongs on `Decree`, whose attentives carry a timeframe affinity like executives do; placed into a cycle, a decree becomes a decree-backed executive, which carries the allocations
- one-shot work belongs on `Objective`, or directly on `Executive` when it needs no objective at all

This keeps `Executive` and `Reflective` as dependent records that matter primarily inside a cycle rather than as top-level sets.

## The Declarative Ecosystem (PEP100)
`Incentive` is the shared abstract base of `Objective`, `Fate`, and `Decree` (one table, TPH discriminator).
The base carries the directive relation and the parent system (`ParentIncentiveId`), enforced by
`IncentiveParenting`: objectives parent objectives (subtasks) or name a fate as parent, fates parent fates,
and decrees are fully exempt.

Declaratives are event-like: they are never acted on directly. Each occurrence materializes an instance in
the backlog record family — an `Attentive` for a decree, an `Eventive` for a fate (an objective's due date
also materializes an eventive). Instances come into existence through:
- **interaction**: changing a single occurrence creates its instance first, then applies the change to it.
  Orbit occurrences are validated in preview (non-seeking) resolution, so interacting with a future instance
  never advances the schedule state; the occurrence date is the instance identity.
- **proximity**: approaching the event time / upcoming orbit occurrence. An occurrence nobody has interacted
  with stays a projection computed on read (`AgendaProjectionService`) until its time arrives. Time then hardens
  it, when time counts as an interaction (the default). `RollingMaterializationService` runs the harden-on-time
  pass shortly after startup and then hourly. The pass seeks orbit fates, and orbit decrees other than lunar
  reflect-decrees, through now, advancing their persisted `IncentiveOrbitScheduleState`. It also hardens due
  objectives whose day has come. At Polaris cycle begin, lunar reflect-decrees resolve at day granularity against
  the cycle's start day and generate cycle-bound reflectives on a match; cycle begin hardens nothing else.

Attentives and eventives are never Polaris-bound. Manually adding a decree to a Polaris cycle creates a
decree-backed `Executive` instead (PEP111; `PolarisCycleApiService.AddDecreeExecutiveAsync`). A cycle includes
in-window unbound items presentationally, without relational ownership.

Attentives and eventives share the non-hierarchical `Occurrence` base (PEP111): a row id, the owned `Epoch`
(civil moment, granularity, nominal duration, zone), and the `RecurrenceId` — the original epoch moment, pinned
when the occurrence materializes, which with the owner UID is its iCalendar identity and survives a reschedule.
The base is a plain CLR class outside the EF model, so each kind keeps its own table. Occurrences carry no time
allocation: that lives on the Polaris `Executive`, and a decree-backed executive seeds its estimation from the
decree's default length. An eventive's duration comes from its orbit occurrence — a span-format orbit (`=<dur>`)
or a one-off `Z{…}=<dur>` literal — so fates need no duration override. An attentive records `ResolvedOn` when
it transitions to `Done`; leaving `Done` clears it, allowing recent completion history to appear on the day-level
agenda.

Orbit calendars are modular. Every declarative orbit resolves on the declarative's explicit `Calendar` when it
has one, else on the vault default (`AgendaPreferences.DefaultCalendar`, PEP116, **Pleiadean** out of the box).
That covers decree attentives, reflective day-matching and fate eventives alike; only a one-off `Z{…}` fate is
pinned to **Gregorian**. Timeframe orbits always read on the vault default. Decree orbits accept any
granularity — sub-day occurrences carry a time of day, and a super-day occurrence
(week/month/year) stores its whole period as its epoch `Duration`, in days resolved on the declarative's
calendar, so a single attentive's period can collide with multiple Polaris cycles and a Pleiadean month keeps
its 60/61 days. Only reflective schedules are held to strict day granularity. Attentives are always unbound and
may sit at any time and date; placing a decree into a cycle creates a decree-backed executive instead.

Rewards: an attentive grants its decree's predefined `ActiveCelestron` on each execution (revoked when
un-done). Reflectives ignore decree rewards; completing all reflectives of a cycle grants one fixed
collection reward. Eventives grant nothing. Both rules live in `PlaintorchStatePolicyProcessor`.

## Stellar & Lunar Directives (PEP100)
`Directive` is an abstract base; `StellarDirective` (PUCK `A{S:8}`) and `LunarDirective` (PUCK `LUNA{S:3}`) are
its concrete TPH siblings sharing the `Directives` table via a discriminator. Each carries its own `Status`
enum mapped to a distinct column (`Status` for stellar, `LunarStatus` for lunar), so neither state leaks onto the
other; the stellar and lunar workflow shifts guard each other. Only stellar directives carry scheduling dates
(`Due`/`StartDate`/`EndDate`). JSON payloads are polymorphic (`$type`: `stellar`/`lunar`; incentives:
`objective`/`fate`/`decree`).

Vault storage differs by kind: stellar directives live under the `Directives` location, while lunar directives
have their own dedicated `Moonlight` location (default `./Moonlight`). Location is resolved from each type's
declared `VaultStorage` policy through `VaultStoragePathComposer` (REFACTOR Alpha phase 2 — no per-type dispatch),
with `LunarDirective` declaring its own `VaultStorage` overriding the inherited stellar one. The location is a
default, not a binding: which concrete kind a file is comes from its identity, not its folder. When a directive is
composed from a path, `VaultFamilyInstantiationResolver` picks the member by matching the file's PUCK against each
sibling's declaration (`A…` → stellar, `LUNA…` → lunar; REFACTOR Alpha phase 3), so the two kinds are fully
symmetric — making one behave differently later is an attribute swap, not a code change.

## Dependency System (PEP101)
`Dependency` is a directed blocking edge: a **source** (prerequisite) blocks a **target** (dependant).
Endpoints are heterogeneous and loosely referenced (no EF FK) across stellar directives, objectives, whole
fates, single fate/objective occurrences (**eventives**), and checkpoints; lunar directives are excluded.
`DependencyRules` enforces the structural invariants (no self-edge, no cycles, checkpoint sides carry no
trigger/constraint), mirroring `IncentiveParenting`; endpoint existence/kind is validated in the API layer.

- The **trigger** (`OnBegin`/`OnFinish`, default `OnFinish`) lives on the source and selects which source
  lifecycle event satisfies the edge; the **constraint** (`ToBegin`/`ToFinish`, default `ToBegin`) lives on
  the target and selects which target transition is gated. Checkpoint endpoints leave their side empty.
- **Eventive endpoints** follow CalDAV/RFC 5545: `Id` is the owner PUCK id (iCalendar `UID`) and the
  recurrence slot is the occurrence's original `DTSTART` (`RECURRENCE-ID`), backed by the stable
  `Eventive.RecurrenceId` so a reference survives an occurrence being moved.
- `DependencyReconciler` recomputes edge `Satisfied` and checkpoint `Unlocked` on every save (inside the state
  policy pass), propagating checkpoint unlocks to a fixpoint. `DependencyGateService` enforces the gate:
  status shifts through a gated begin/finish are rejected, and a locked fate's materialization is frozen
  (whole-fate pauses orbit generation; a locked single occurrence blocks only itself). The lock is an emitted
  signal, separate from the entity's `status` field.

`Checkpoint` (PUCK `c{S:4}`, database-only) aggregates dependencies and unlocks when all its incoming edges
are satisfied AND its optional Celestron toll is paid AND its optional external condition is met. The toll is a
negative `CelestronTransaction` (order-independent payment); unlocking a checkpoint satisfies edges sourced on
it, cascading.

### Lifecycle phases (PEP101)
Begin/finish are declared, not hardcoded: `[LifecyclePhase]` marks status enum members (`Begin`/`Finish`) and
`[LifecycleStatus]` marks the status property, so `EntityLifecycleResolver` reads them by reflection.
`EventiveLifecyclePhaseSource` is the declared temporal hook for eventives (whose passing is temporal, not a
status). Activation validation requires each status-driven participant to declare at least one begin and one
finish.

## Timeframes (PEP100)
`Timeframe` definitions hang off **lunar** directives only and flag a portion of the day (optionally scoped to
cycles by an Orbit). They do nothing on their own. Executives, and the reflectives and attentives that share their
shape, may name one as their `AffinityTimeframe`: a purely semantic preferred execution window, and a set-null
reference, so deleting the timeframe only un-affines them. The directive API exposes both per-directive timeframe
listing and a global listing that pairs every timeframe with a summary of its owning lunar directive.

**Auto-inclusion** (PEP100 patches 1 and 2) seeds that affinity when a Polaris workitem is created.
`TimeframeInclusion` is an integer-stored, append-only kind:
- `None`: set by hand only.
- `College`: the timeframe includes any workitem whose owning incentive carries one of its
  `AutoInclusionColleges`.
- `Availability`: the timeframe carries no parameter. A `Directive` of either kind names it through its
  database-only `AvailabilityTimeframeId`, which may point at any lunar directive's Availability-mode timeframe.
  Every workitem whose owning incentive belongs to that directive, or to one of its descendants, is affined to it.

`TimeframeAffinityResolver.ResolveAsync` decides, and it is the only resolver. The nearest directive availability
wins: the walk starts at the incentive's own directive and follows `ParentDirectiveId` with a visited set, never
parent incentives. Availability takes precedence over College, whose lowest id wins. Three creation paths use the
resolver:
- executives planned from an objective;
- decree-backed executives;
- cycle-begin reflectives.

A one-shot executive has no incentive and gets none, and attentives are never auto-seeded. Auto-inclusion only
seeds at creation; later changes never re-affine existing workitems. A timeframe leaving Availability mode, or
being deleted, on its own or with its lunar directive, clears the directives that name it in the same save. The
clear is a state-policy rule of the save hook, so every write pathway gets it and the change feed announces the
cleared directives; the set-null foreign key is only the database's backstop. The resolver also ignores any
availability that does not point at an Availability-mode timeframe.

**Exclusivity** (`Exclusive`, PEP100 patch 2) is judged among the timeframes active at one moment. Any active
exclusive timeframe drops every active non-exclusive one, and all the active exclusive ones are kept. Exclusivity
does not affect auto-inclusion or affinity. Which timeframes are active is a core decision (see the Plaintorch
genesis):
- the day filter comes from the strictly active cycle's candidates, which are the timeframes whose orbit matches
  the cycle's local start day, a timeframe without an orbit matching every day;
- the window is `[StartTime, EndTime)` at minute precision;
- a start after the end wraps midnight, and a start equal to the end is never active.

An orbit-scoped timeframe keeps a `TimeframeOrbitScheduleState` (PEP100 patch 2), a sibling of the declaratives'
`IncentiveOrbitScheduleState` under the abstract `OrbitScheduleState`. It pins the orbit's epoch and seed, so an
interval or random orbit reads the same way every cycle:
- It follows the declarative reset policy through the state-policy save hook. Setting or changing the orbit
  re-anchors the state, and clearing the orbit removes it.
- Its epoch is a fixed `Z{…}` literal's own date, else the earlier of today and the open Polaris cycle's day, so an
  orbit set after midnight can still select the day of a cycle begun the evening before and still open. A
  declarative's recurring orbit anchors at today instead. A timeframe state is only previewed and never hardens
  occurrences, so anchoring it back costs no backfill.
- A calendar change never resets it.
- It is only ever previewed, never advanced.
- It is deleted with its timeframe.

## Executive Orders
`ExecutiveOrder` (PEP099) attaches durable constraints or directions to an `OnrushSprint`:
- required `Title` (PUCK-named) and owning `OnrushSprintId`
- optional `Summary`, `EffectiveFrom`, and `EffectiveUntil` fields

Identity uses the composite PUCK declaration `x{?}-o{I:2:1}`: the manual first segment carries the owning
onrush's trimmed numeric part, and the order counter increments per owning onrush
(`Onrush x0180 -> E.O. x180-o01`). Orders are stored `Synced`, as single files, in the owning sprint's
`ExecutiveOrders` partition folder with `Index` PUCK storage.

## Executive Time Allocations
`Executive` carries three optional whole-minute working-time-unit allocations (PEP098):
- `Estimation`: the primary allocation, which also doubles as a lightweight progress marker. The sum of estimations across a cycle's executives expresses the day's total workload.
- `Minimum` / `Maximum`: optional bounds on the allocation.

`Executive.NormalizeTimeAllocations()` enforces the coupling and clamping rules so the three values stay coherent regardless of the order they are supplied:
- when a bound is present but the estimation is still unset, the estimation adopts that bound (preferring the minimum);
- the estimation is always clamped into the `[Minimum, Maximum]` envelope when the relevant bound is present.

Alongside the allocations, `Executive` carries `Elapsed` (Patch098.1): the raw count of tracked (passed) minutes. Unlike the allocations it is a running tally rather than a target — it defaults to `0` and is deliberately excluded from `NormalizeTimeAllocations` (never clamped). It is intentionally *not* part of executive planning (`PolarisExecutivePlan`) because a freshly planned executive has not been worked, so its tracked minutes always start at `0`; it only accrues later through `ExecutiveUpdate`, where `null` leaves it unchanged and any value (including `0` to reset) overwrites it. It has no `Clear` flag because it is never unset.

The application/API layer applies these values (at plan time via `PolarisExecutivePlan`, or via `ExecutiveUpdate`) and then calls the normalizer before persisting. The minute-based storage form is translated for consumers in the application/UI layer (see the SDK working-time-unit helpers) rather than in the domain model.

## EF Shape
Most persistence shape now comes directly from the entities:
- navigation properties
- foreign-key properties
- data annotations

`PlainfraContext` only keeps the pieces that conventions and annotations do not express well, mainly value conversions.

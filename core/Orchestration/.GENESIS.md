# Orchestration Genesis

## Purpose
The `Pleiades.Orchestration` domain contains the operational story/work models.

## Main Models
- `Directive` (abstract) / `StellarDirective` / `LunarDirective`
- `OnrushSprint`
- `ExecutiveOrder`
- `Incentive`: `Objective`, `Fate`, `Decree`
- `PolarisCycle`
- `PolarisForecast`

- `Eventive`

## Model Intent
- `Directive`: abstract base shared by the two directive siblings; carries identity, nesting, tags, and incentives (PEP100), plus an optional database-only availability timeframe (PEP100 patch 2)
- `StellarDirective`: long-running directive with a lifecycle `Status` and an optional due date, optionally nested, optionally a member of an onrush sprint (`OnrushSprintId`, frontmatter `onrush`; PEP102 patch 10); when it is planned to begin or finish, and when it did, are its backlog schedules (PEP101)
- `LunarDirective`: everglow Moonlight directive acting as a law/routine/requirement; table sibling of `StellarDirective` through a discriminator, with its own moonlight `Status` and `Timeframes` (PEP100)
- `OnrushSprint`: short-term focused sprint, tracking objectives, stellar directives (PEP102 patch 10) and checkpoints
- `ExecutiveOrder`: special constraint or direction shaping how an onrush sprint is moved through (PEP099)
- `Incentive`: abstract base of the declarative ecosystem; objectives and declaratives share its table with discriminators (PEP100)
- `Objective`: goalpost attached to directives and/or onrush sprints — one-shot by nature; recurring commitment is a `Decree`
- `Fate`: event-like declarative that happens rather than gets done; all-day or timed, orbit-schedulable (PEP100)
- `Decree`: enduring routine/law controller declarative that materializes attentives; exempt from parenting (PEP100)
- `PolarisCycle`: one daily cycle, either forecast or anecdotal. A day holds at most one: the id is the day's Pleiadean date stamp, and `Day` reads the day back off it (the forecast target of a plan, the start day of a begun cycle). A plan may be made for today itself, and only a cycle not yet begun may be deleted
- `Executive`: execution record within a cycle, optionally standalone and self-titled without a backing objective
- `Reflective`: reflective task record within a cycle
- `Attentive`: per-occurrence instance of a decree, executive-shaped, never bound to a cycle (PEP100, PEP111)
- `Eventive`: per-occurrence instance of a fate, executive-shaped, never cycle-bound (PEP100)
- `Terminative`: the occurrence of an item's due — one per objective, stellar directive or checkpoint that has one — kept its origin's mirror by the state engine (PEP103 patch 7)
- `IDueOwner`: the due contract an objective, a stellar directive and a checkpoint implement; each one's due spawns its terminative (PEP103 patch 7)
- `Timeframe`: directive-level definition of a portion of the day, purely semantic (PEP100). It can auto-include workitems (by college, or as a directive availability) and can be exclusive among the timeframes active at once (PEP100 patches 1 and 2)
- `OrbitScheduleState`: abstract persisted Orbit engine state (snapshot, epoch, seed) that anchors an owner's orbit. `IncentiveOrbitScheduleState` anchors a declarative's orbit and `TimeframeOrbitScheduleState` a timeframe's; they share one table through a discriminator (PEP100 patch 2)
- `CelestronTransaction`: ledger entry for reward/loss accounting
- `BacklogSchedule`: one planned or recorded begin or finish of an incentive, a directive or a checkpoint (PEP101); the backlog's scheduling vocabulary, in place of the directive's former start and end dates
- `TagDefinition`: predefined tag catalog entry with a semantic palette colour

## Tag Registry
- Directives keep assigned tags as a lightweight string list.
- `TagDefinition` provides a place to define valid tags ahead of use.
- `TagColor` uses semantic palette names: `Anna`, `Eris`, `Lulu`, `Nilou`, `Emi`, `Sana`, `Light`, and `Void`.
- `TagPalette` exposes stable UI-facing tokens so future clients can map those semantic colours into actual theme values without changing stored records.

## Workflow States
Each status reads as one of the four lifecycle states (see *Lifecycle states*): Deferred (D), Open (O), Started (S) or
Finished (F).
- `DirectiveStatus`: `Planned` (O) → `Committed` (O) → `Active` (S) → `Fulfilled` (F) → `Over` (F); `Failed` (D) aside
- `LunarDirectiveStatus`: `Active` (S, initial) / `OnHold` (D) / `Stale` (F) — no ordinary lifecycle: a lunar directive starts
  Active and moves at will between the three; lunar reflection follows it, and its timeframes stop once it is Stale
  (PEP103 patch 6)
- `ObjectiveStatus`: `Standby` (O) → `[Blocked]` (O) → `Onboard` (O) → `Polaris` (S) → `Done` (F) → `Archived` (F); `Failed` (D) aside
- `FateStatus`: `Active` (S, initial) / `OptOut` (S) / `Stopped` (D, named `Cancelled` before PEP103 patch 6) — a fate never
  finishes
- `DecreeStatus`: `Active` (S, initial) / `Abandoned` (D) — a decree never finishes
- `AttentiveResolution`: `Pending` (O) → `Done` (F) / `Skipped` (D)
- `EventiveResolution`: `Pending` (O) → `Missed` / `Cancelled` / `OptOut` (D); a pending eventive's time window starts
  and finishes it (passing is temporal, not stateful)
- `TerminativeResolution`: `Pending` (O, initial) / `Resolved` (F) — set only by the state engine, from the origin's
  lifecycle (PEP103 patch 7)

`Blocked` is treated as an interrupting state for objectives rather than part of the main forward flow; it is still
Open, since the objective is meant to go on.

An objective **starts** when it is set to `Polaris` (PEP101): that is its only started status. `Onboard` (named `Onrush`
before PEP103 patch 3) commits it to a sprint without starting it, so a start gate does not refuse the shift to
`Onboard`, and a start-triggered dependency sourced on the objective waits for `Polaris`.

Joining moves an objective along of its own accord (PEP103 patch 3): coming on board the **active** onrush sprint makes it
`Onboard`, and joining the **active** Polaris cycle makes it `Polaris`, from an open status short of the target or a
finished one, and only where nothing blocks the move. The planning sprint and a forecast move nothing until they begin,
and leaving a sprint or a cycle moves nothing back. The state engine does it (*State enforcement* below).

Any status may follow any other, as long as no dependency is reopened (PEP103 patch 4): moving forward needs the gates of
every state it enters, and moving back out of the state a dependency needs is a conflict while that dependency's target
already relies on it — its intrinsic edge to its directive included. Setting an item aside never reopens anything.

Onrush sprints and Polaris cycles run one way through (`CyclePhase`: Planned → Active → Ended): each begins once and ends
once, never before it begins or before its start, and a Polaris cycle never begins before its day. Their planning stays
apart — a sprint is planned as the one placeholder (`x0000`), which never ends; a cycle as a forecast for its own day.

## Persistence Shape
These types are plain CLR entities decorated with markdown metadata and EF data annotations. Conversions that annotations cannot express, like JSON storage for directive tags or enum-as-string storage, are configured centrally in `PlainfraContext`.

## Navigation Shape
The orchestration model now leans on navigation properties so the object graph expresses intent more clearly:
- `Directive` links to its parent, subdirectives, and related objectives
- `OnrushSprint` exposes its objectives, its stellar directives and its checkpoints
- `Objective` links back to its directive and onrush sprint, and can collect execution records
- `PolarisCycle` owns the operational details of the day through `Executives` and `Reflectives`

This allows the model to distinguish durable intent from ephemeral action:
- enduring or repeating work belongs on `Decree`, whose attentives carry a timeframe affinity like executives do; placed into a cycle, a decree becomes a decree-backed executive, which carries the allocations
- one-shot work belongs on `Objective`, or directly on `Executive` when it needs no objective at all

This keeps `Executive` and `Reflective` as dependent records that matter primarily inside a cycle rather than as top-level sets.

Deleting a backlog item keeps the work recorded against it (a structural rule of the state interceptor, so every write
pathway applies it). When an objective or a decree is deleted, its executives — and a decree's reflectives — in
**ended** cycles stay, with the reference cleared and their executed/elapsed/allocations intact. Those in the **active**
cycle and in **planned or forecast** cycles are removed with it. A kept record carries no title of its own.

## The Declarative Ecosystem (PEP100)
`Incentive` is the shared abstract base of `Objective`, `Fate`, and `Decree` (one table, TPH discriminator).
The base carries the directive relation. Incentives do not nest: the former incentive parent system
(`ParentIncentiveId`, `IncentiveParenting` — objectives under objectives or fates, fates under fates) was removed
in Phase 3A, so an incentive's only structural parent is its directive.

Declaratives are event-like: they are never acted on directly. Each occurrence materializes an instance in
the backlog record family — an `Attentive` for a decree, an `Eventive` for a fate, and a `Terminative` for an item's
due (see *Dues and terminatives*). Instances come into existence through:
- **interaction**: changing a single occurrence creates its instance first, then applies the change to it.
  Orbit occurrences are validated in preview (non-seeking) resolution, so interacting with a future instance
  never advances the schedule state; the occurrence date is the instance identity.
- **proximity**: approaching the event time / upcoming orbit occurrence. An occurrence nobody has interacted
  with stays a projection computed on read (`AgendaProjectionService`) until its time arrives. Time then hardens
  it, when time counts as an interaction (the default). `RollingMaterializationService` runs the harden-on-time
  pass shortly after startup and then hourly. The pass seeks orbit fates, and orbit decrees other than lunar
  reflect-decrees, through now, advancing their persisted `IncentiveOrbitScheduleState`. It also hardens the
  terminative of every due that acts once its day has come. At Polaris cycle begin, lunar reflection (PEP104) generates the cycle-bound
  reflectives; cycle begin hardens nothing else. A reflect-decree takes part only while it is Active and every
  lunar directive on its lineage is started (Active); an On Hold or Stale lunar directive pauses reflection in its
  subtree, and nothing else. Every one of these passes asks `TemporalActivation` (PEP103 patch 6): a fate, a decree or
  any item that is finished or set aside generates nothing, and its due acts no more. The cycle takes
  every such decree whose orbit resolves onto its start day (day granularity), then draws
  `ReflectionPreferences.BaseDailyReflectives` more at random from the ones without an orbit, one reflective per
  decree per cycle.

Attentives and eventives are never Polaris-bound. Manually adding a decree to a Polaris cycle creates a
decree-backed `Executive` instead (PEP111; `PolarisCycleApiService.AddDecreeExecutiveAsync`). A cycle includes
in-window unbound items presentationally, without relational ownership.

Attentives, eventives and terminatives share the non-hierarchical `Occurrence` base (PEP111): a row id, the owned `Epoch`
(civil moment, granularity, nominal duration, zone), and the `RecurrenceId` — the original epoch moment, pinned
when the occurrence materializes, which with the owner UID is its iCalendar identity and survives a reschedule.
The base is a plain CLR class outside the EF model, so each kind keeps its own table. An epoch's moment is a civil
wall time; a timed epoch anchored in a `TimeZone` names an absolute `Instant`, and every comparison with this host's
"now" or "today" (agenda, Polaris inclusion, an eventive's begun/finished phase) reads its `LocalMoment`, the instant
on this host's clock (the moment itself when floating or all-day). A fate can also hold
**manual** eventives, added by hand (`POST /api/eventives`, given its whole `Epoch`) rather than generated from its
orbit. A manual eventive
has no `RecurrenceId` (`IsManual`) and belongs to no recurrence set. It is born hardened, never dedups against a
projected occurrence, and is addressed by row id. Only the eventive column is nullable; an attentive is always
schedule-born, so its column stays required. Occurrences carry no time
allocation: that lives on the Polaris `Executive`, and a decree-backed executive seeds its estimation from the
decree's default length. An eventive's duration comes from its orbit occurrence — a span-format orbit (`=<dur>`)
or a one-off `Z{…}=<dur>` literal — so fates need no duration override. An attentive records `ResolvedOn` when
it transitions to `Done`; leaving `Done` clears it, allowing recent completion history to appear on the day-level
agenda.

Orbit calendars are modular. Every declarative orbit resolves on the declarative's explicit `Calendar` when it
has one, else on the vault default (`AgendaPreferences.DefaultCalendar`, PEP116, **Pleiadean** out of the box).
That covers decree attentives, reflective day-matching and fate eventives alike. A one-off `Z{y/M/d}` literal names a
day on that calendar: written without one named, it is pinned to **Gregorian**; changing the calendar through the API
rewrites the literal (`OrbitDays.RewriteFixedLiteral`) so it keeps its day. A declarative also carries an optional
IANA `TimeZone` (floating when unset): the clock its orbit runs on. Every orbit-born occurrence is stamped with it
(`PlaintorchOrbitService.EpochOf`), its schedule is sought, hardened on time and counted (`NextOccurrence`) from "now"
as that zone reads it (`ClockOf`), and a preview over this host's days reaches `OccurrenceZones.ReachDays` either side
and keeps a timed occurrence by the day its instant falls on here. It is also the zone a hand-added occurrence starts
in. Timeframe orbits always read on the vault default. Decree orbits accept any
granularity — sub-day occurrences carry a time of day, and a super-day occurrence
(week/month/year) stores its whole period as its epoch `Duration`, in days resolved on the declarative's
calendar, so a single attentive's period can collide with multiple Polaris cycles and a Pleiadean month keeps
its 60/61 days. Only reflective schedules are held to strict day granularity. Attentives are always unbound and
may sit at any time and date; placing a decree into a cycle creates a decree-backed executive instead.

Rewards: an attentive grants its decree's predefined `ActiveCelestron` on each execution (revoked when
un-done), and so does a decree-backed reflective (PEP104). Completing all reflectives of a cycle also grants the
daily collection reward, `ReflectionPreferences.DailyReward`. Eventives grant nothing. These rules are the state
engine's outcome reactions (`OutcomeReactions`).

## Dues and Terminatives (PEP103 patch 7)
An objective, a stellar directive and a checkpoint can carry a due, and all three are under one contract, `IDueOwner`.
A stellar directive's due is a date, so it falls due as a whole day. Each due spawns one `Terminative`: an occurrence
like an eventive or an attentive, with its own table and its own owner columns (`ObjectiveId`, `DirectiveId`,
`CheckpointId`), exactly one of them set (a check constraint) and each origin owning at most one (unique indexes).
Deleting the origin deletes it. Its origin alone identifies it: its `RecurrenceId` is the due's moment and moves with
the due.

`TerminativeService` is the one due mechanism; the projection, the rolling pass, interaction and the state engine all go
through it.
- **Whether a due acts** is `TemporalActivation.DueActs`: while its item is open or started. A checkpoint declares that
  passing its due is what sets it aside (`IDueOwner.DueDefers`), so its due acts until it unlocks.
- **Projection and hardening.** A due that acts is projected as a pending terminative. Time hardens it on its due's day,
  and so does interaction: raising its ignore flag (`PUT /api/terminatives`, addressed by its origin).
- **The mirror.** The last outcome reaction, after the reconciler, keeps every terminative in line with its origin, hardened
  or not. Its epoch follows the due (all-day for a whole-day due, minute-granular in the due's zone otherwise), and a due
  cleared removes it. Its resolution is the engine's alone: `Pending` while the due acts, `Resolved` once the origin is
  finished or set aside, and pending again if the origin is taken up. An owned due replaced or cleared leaves its owner's
  entry unchanged, so the reaction finds such changes through the owned entries, by their owner's key.
- **The ignore flag** (`Ignored`) is the one field a user sets, and the engine never does. The agenda lists the pending
  terminatives up to its horizon, overdue ones included, unless ignored.

A terminative is not a dependency endpoint: an edge names the origin itself. Eventives belong to fates alone.

## Stellar & Lunar Directives (PEP100)
`Directive` is an abstract base; `StellarDirective` (PUCK `A{S:8}`) and `LunarDirective` (PUCK `LUNA{S:3}`) are
its concrete TPH siblings sharing the `Directives` table via a discriminator. Each carries its own `Status`
enum mapped to a distinct column (`Status` for stellar, `LunarStatus` for lunar), so neither state leaks onto the
other; the stellar and lunar workflow shifts guard each other. Only stellar directives carry a due date (`Due`); the
start and end dates they used to carry became backlog schedules (PEP101, below).
JSON payloads are polymorphic (`$type`: `stellar`/`lunar`; incentives:
`objective`/`fate`/`decree`).

Vault storage differs by kind: stellar directives live under the `Directives` location, while lunar directives
have their own dedicated `Moonlight` location (default `./Moonlight`). Location is resolved from each type's
declared `VaultStorage` policy through `VaultStoragePathComposer` (REFACTOR Alpha phase 2 — no per-type dispatch),
with `LunarDirective` declaring its own `VaultStorage` overriding the inherited stellar one. The location is a
default, not a binding: which concrete kind a file is comes from its identity, not its folder. When a directive is
composed from a path, `VaultFamilyInstantiationResolver` picks the member by matching the file's PUCK against each
sibling's declaration (`A…` → stellar, `LUNA…` → lunar; REFACTOR Alpha phase 3), so the two kinds are fully
symmetric — making one behave differently later is an attribute swap, not a code change.

## Dependency System (PEP101)
`Dependency` is a directed blocking edge: a **source** (prerequisite) blocks a **target** (dependant).
Endpoints are heterogeneous and loosely referenced (no EF FK) across stellar directives, objectives, whole
fates, single fate occurrences (**eventives**), and checkpoints; lunar directives are excluded. A terminative (an item's
due) is no endpoint: an edge names the item.
`DependencyRules` enforces the structural invariants (no self-edge, no duplicate, checkpoint sides carry no
trigger/constraint); endpoint existence/kind and logical possibility (the temporal cycle rule, PEP102) are
validated in the API layer.

- The **trigger** (`OnBegin`/`OnFinish`, default `OnFinish`) lives on the source and selects which source
  lifecycle event satisfies the edge; the **constraint** (`ToBegin`/`ToFinish`, default `ToBegin`) lives on
  the target and selects which target transition is gated. Checkpoint endpoints leave their side empty.
- **Eventive endpoints** follow CalDAV/RFC 5545: `Id` is the owner PUCK id (iCalendar `UID`) and the
  recurrence slot is the occurrence's original `DTSTART` (`RECURRENCE-ID`), backed by the stable
  `Eventive.RecurrenceId` so a reference survives an occurrence being moved.
- `DependencyReconciler` recomputes edge `Satisfied` and checkpoint `Unlocked` on every save (one of the state
  engine's outcome reactions), propagating checkpoint unlocks to a fixpoint. Checkpoints are reconciled even when the
  vault holds no edge at all (they used to be skipped until some unrelated edge existed, so an ungated checkpoint's toll
  or condition never unlocked it). The gate is the state engine's (`StateJudge`, see *State enforcement*): a status
  change is judged on every state it enters (`LifecycleTransition.Entered`), on every pathway, so a jump from an
  unstarted status straight to a finished one passes the start gate as well as the finish gate. A move back, a deferral
  and a shift within one state are not gated; becoming Over needs the directive's children finished.
  `DependencyGateService` reads the lock for what the API serves. A locked fate's materialization is frozen (whole-fate
  pauses orbit generation; a locked single occurrence blocks only itself). The lock is an emitted signal, separate from
  the entity's `status` field.

`Checkpoint` (PUCK `c{S:4}`, database-only) aggregates dependencies and unlocks when all its incoming edges
are satisfied AND its optional Celestron toll is paid AND its optional external condition is met. The toll is a
negative `CelestronTransaction` (order-independent payment); unlocking a checkpoint satisfies edges sourced on
it, cascading. A checkpoint never starts: its unlock is its finish, and re-locking reopens it. Its due is the one way it
fails: still locked once the due has passed, it is Deferred, and it can still finish late by paying the toll it now
owes. With no start of its own, its side of an edge carries no trigger or constraint. The logical-possibility walk
(PEP102) still treats it as a dead end rather than ordering through its finish.

### Intrinsic dependencies (PEP102 patch 9)
An edge carries an `Origin`: `Explicit` (stored, drawn by a person) or `Intrinsic` (derived from the backlog's
structure as it is read, never stored, `Id` 0). The first rule, `DirectiveChildrenIntrinsicRule`: finishing a
stellar directive depends on finishing each of its direct children — its stellar subdirectives and its
objectives — one `child.finish → parent.finish` edge per child, satisfied once the child has finished. A deferred
(failed) end switches the edge off. `DependencyGraphService` reads the stored edges and every `IIntrinsicDependencyRule`'s
derived ones as one graph, which the judge, the reconciler, the API and the purge all read.

The temporal cycle rule is `DependencyOrdering` (pure, in memory): a prospective edge is impossible when, walking
forward from the target's constrained side, the source's triggering side is reachable; the contradicting path is
named in the refusal. Dependencies are the slave of structure: a reparent, or an end entering or leaving Failed,
purges the stored edges the structure now contradicts (`DependencyOrdering.PlanPurge`: those touching the moved
subtree preferred, the most resolving first, newest on a tie, until the graph orders) and the ones the intrinsic
edges restate; deleting an endpoint releases its stored edges. All of it rides the state interceptor, on the audit
record. The v5→v6 vault migration runs the purge once over an existing vault.

An `Over` stellar directive that receives an open child — created under it, moved in, reopened from a finish or taken
up again from a deferral — reopens to `Fulfilled`, the finish that tolerates open work. The reopening is a
compensation, so the enforcement level decides: `Auto` makes it in the same save (its note reconciled after it
commits), `Warn` asks first, `Block` refuses the open work, and `Ignore` leaves the directive Over. Becoming Over again
needs the children finished.

### Lifecycle states (PEP103)
Every backlog kind is read in four states (`LifecycleState`): `Deferred` (-1) → `Open` (0) → `Started` (1) →
`Finished` (2). The main line runs Open → Started → Finished; Deferred sits below it as the side exit for an item set
aside — failed, abandoned, stopped, on hold, skipped or overdue — which has neither started nor finished, satisfies
no dependency it is the source of, and keeps its place on the main line until it resumes. Finishing implies starting.

States are declared, not hardcoded:
- `[LifecycleState]` marks every member of a lifecycle status enum with its state, and `[LifecycleStatus]` marks the
  status property, so `EntityLifecycleResolver` reads them by reflection (`LifecycleDeclarations` reads the enums).
  Objectives, stellar and lunar directives, fates, decrees, attentives and terminatives are status-driven.
- An `ILifecycleStateSource` answers for a kind whose state is not a plain status: `EventiveLifecycleStateSource` (a
  deferring resolution, else the time window: open before the start, started until the end, finished after) and
  `CheckpointLifecycleStateSource` (finished when unlocked, deferred when still locked past its due, open otherwise).
- A finished member may also close its item (`[LifecycleState(LifecycleState.Finished, Closed = true)]`, PEP103 patch 5):
  an objective's `Archived` and a directive's `Over`. A closed status stands only while everything the item depends on
  holds; `LifecycleDeclarations.IsClosed` and `EntityLifecycleResolver.IsClosed` read it, and the lifecycles a client is
  served carry it.
- A kind passes through only the states it declares (`StatesOf`): a fate or a decree is either Started or Deferred and
  never finishes, a lunar directive is never Open; a checkpoint and an attentive never start.
- One member may be initial (`[LifecycleState(..., Initial = true)]`, PEP103 patch 6): the status an item of the kind is
  created in, which every entity's status starts from (`LifecycleDeclarations.InitialStatus`). An objective starts
  `Standby`, a directive `Planned`, and a fate, a decree and a lunar directive `Active`, already under way.
- The status property may declare that its kind keeps a history (`[LifecycleStatus(History = true)]`): a fate, a decree
  and a lunar directive record every state they enter anew (`EntityLifecycleResolver.KeepsHistory`).
- `TemporalActivation` is the one gate on whether time acts on an item: open or started, it is temporally active;
  finished or set aside, it generates no orbit occurrence and its due acts no more (`DueActs`, which keeps a checkpoint's
  due acting until it unlocks). Rules ask it by state, never by status.

The resolver is the one place lifecycles are read:
- `StateOf` gives an entity's or a status's state; `NextState` the next one up the order, and `NextGatedState` the next
  of Started and Finished a dependency can hold back (a deferred item counts as before Open).
- `Transition` reads a move as a `LifecycleTransition`: the progress states it enters (a jump from Open to Finished enters
  Started and Finished) or leaves going back, and whether it defers or resumes. A shift between two statuses of one state
  is no transition, and a deferral enters and leaves nothing on the main line.
- `DefaultStatus` translates a state to a status when the core sets one of its own accord: the lowest-valued member of
  the kind's status enum that declares it (an objective's Deferred is `Failed`, Open `Standby`, Started `Polaris`,
  Finished `Done`). A kind that reaches a state otherwise (an eventive by time, a checkpoint by unlocking) has none.

Activation validates the declarations: every member of a lifecycle status enum declares a state and the enum has a
main-line one; every source passes through a main-line state and its status enum declares only states the source
passes through; no kind has both a status property and a source; and only a finished member closes, never the kind's
default finished status, so a closed item always has an open finish to step back to. A deferred (failed) objective or
directive keeps blocking what it explicitly blocks, and its intrinsic dependencies are switched off. `Archived`/`Over`
are the closed `Done`/`Fulfilled`.

The backlog state enforcement level (BSEL, the `backlog.state-enforcement` preference) decides what happens when a change
would break a lifecycle rule: `Ignore` lets it through, `Auto` compensates by moving the other items it needs, `Warn`
(the default) asks first, and `Block` refuses it; a systemic violation is refused at every level. `StateDecisionService`
is the one place the level is applied: given the conflicts the engine finds, each with the compensations that would
resolve it, it decides to proceed, compensate, wait for confirmation or refuse. Under Warn the API answers 409 Conflict
with the decision; the client cancels, or repeats the call with `X-Plaintorch-Enforcement: auto` to force the
compensations. A change nobody can be asked about (a note edit, a background pass) is refused under Warn.

### State enforcement (PEP103)
One save interceptor, `StateInterceptor` (`core/Plaintorch/Enforcement`), enforces the backlog's state. It runs the
`StateEngine` on every save of a `PlainfraContext`, synchronous or asynchronous and whatever the pathway — the API, the
watcher's note edits, activation and background passes — before anything is written, in four phases:
1. **Structure** (`StructureReactions`): what the change implies whatever the rules say. A deleted incentive keeps its
   ended work, a deleted entity ends its boundary, availabilities never outlive their timeframe's role, a changed orbit
   resets its cursor and a resumed fate or decree seeks it to now, a new edge hardens the occurrences it names, a deleted
   endpoint (a checkpoint included) releases its edges, and a structural change purges the edges the structure
   contradicts or restates. Then the engine's own moves on membership (`MembershipReactions`): an objective joining the
   active onrush sprint becomes `Onboard`, and one joining the active Polaris cycle becomes `Polaris` — joining being a
   move into it, a creation in it, or its sprint or cycle beginning — from an open status short of the target only
   (joining pushes forward, PEP103 patch 5), never over a status the save sets itself, and only where the judge allows the
   move as the save stands
   (`StateJudge.AllowsAsync`). A blocked move is skipped at every level: the engine never compensates nor asks for its
   own moves, and the join itself goes ahead (`state.join` on the record).
2. **Judgement** (`StateJudge`, `StateDecisionService`, `StateCompensator`): the rules the save would break become
   conflicts, and the enforcement level decides. Systemic rules are refused at every level: one planning placeholder,
   one active sprint, one active cycle; an ended sprint or cycle never begins again nor moves its end; nothing ends before
   it begins or before its start, the placeholder never; a Polaris cycle never begins before its day, and a sprint never
   on a day still to come; what an ended sprint or cycle holds (executives, reflectives, orders, checkpoints) is not
   changed, and nothing joins an ended sprint; an executive works at an objective or a started decree. Lifecycle rules are
   judged on every state a save moves an objective, a stellar directive or a fate into, and on every move back: entering
   Started needs the edges constrained to the start satisfied, entering Finished the edges constrained to the finish,
   closing an item every edge into it, a directive finishing or closing needs its children finished or set aside, and
   moving back out of what a dependency needs while its target relies on it reopens the dependency (setting aside
   excepted). What is done is done: a dependency that arrives after an item finished only keeps it from closing, and a
   closed item that gains one — an added edge, a checkpoint locked again, open work arriving under it — or a closed
   objective joining the active sprint or cycle steps back to its open finish. Each conflict carries its compensations —
   a source moved to the state its trigger needs, an open child finished, a target that relied on a reopened dependency
   moved back before the state it gates, a closed item returned to its open finish — each to the default status of its
   new state, and each move
   is judged in turn, so the moves cascade, forward or back, until nothing more is needed. Nothing moves a source that is
   set aside, an occurrence, a fate asked to finish or to go back before its start, or a checkpoint held by its toll or
   condition or with nothing to wait for; a checkpoint held only by its own edges passes the moves through to them, and
   one that relocks takes back what it held. A checkpoint is read one way, by the judge and the reconciler alike
   (`DependencyReconciler.Unlocks`): an unmet edge into it or a false condition locks it; once unlocked it stays so, its
   due no longer bringing its toll due; a locked one unlocks only once it has something to wait for and all of it holds.
3. **Outcomes** (`OutcomeReactions`): next occurrences, forecast supersession, settlements and rewards, the reconciler,
   and then the terminatives brought in line with their origins (PEP103 patch 7), all on the final state, compensations
   included.
4. **Records** (`BacklogScheduleRecorder`).

A save that waits for confirmation or is refused throws `StateEnforcementException` and writes nothing. Compensations
commit with the change in the same save, each on the audit record (`state.compensate`); conflicts Ignore lets through are
recorded too (`state.ignore`). The note of every item the engine moved, and of every vault-backed item whose note-backed
fields a save outside the watcher changes, gets a reconcile intent in the save's transaction and is rewritten once the
save commits, unless its caller writes it already. Messages say what blocks a change ("…is blocked by 2 dependencies"), never which items do;
the compensations name the items confirming would move.

How each pathway meets a stopped change:
- **API**: 409 Conflict with the decision (`StateEnforcementProblem`). The SDK hands a held-back change to the client's
  `stateEnforcement` handler; SIPA asks the user (`StateEnforcementModal`) and the SDK repeats the call with
  `X-Plaintorch-Enforcement: auto`, and a refusal is shown as a warning.
- **Watcher**: under Warn nobody can be asked, so a note edit that breaks a rule is refused (user ruling). The note keeps
  its edit, the database its state, and the note carries a standing `state-refused` issue that says what blocks it. It
  is not retried on a timer: an edit of the note, or the next sweep once the block is settled, applies it.
- **Background and activation passes**: a refusal fails the pass's save, as any other failure does.

## Backlog Schedules (PEP101)
`BacklogSchedule` is the backlog's scheduling vocabulary: one row places one lifecycle state of one owner in time.
- **Type** (`BacklogScheduleType`, stored by name so kinds can be appended): `Plan` — when the user means the item to
  start or finish — or `Record` — when it actually started, finished or was set aside.
- **State** (`LifecycleState`, stored by name): `Started` or `Finished` for a plan, and also `Deferred` for a record;
  never `Open`.
- **Time**: a civil wall-clock moment, like `Due.Moment`, never an absolute instant. A plan at midnight stands for the
  whole day. A record carries the local time it was written.
- **Owner**: exactly one of `IncentiveId` (objective, fate, decree), `DirectiveId` (stellar or lunar) or `CheckpointId`.
  Each is a real, cascading foreign key, so schedules die with their owner and never block its delete; a check
  constraint refuses a row naming no owner or several.

**One place, every save.** Both rules below are `BacklogScheduleRecorder`'s, the last phase of the state engine, which
`StateInterceptor` runs on synchronous saves as well as asynchronous ones, so every write pathway is covered: the API, the
watcher, the CLI, a background pass. (PUCK issuance, which once saved the caller's pending changes as a side effect,
registers its ids on a bare context of its own.) It sees what the engine left behind (its compensations, a checkpoint the
reconciler just unlocked), and the change feed, registered after the interceptor, announces its records. Only bulk
`ExecuteUpdate`/`ExecuteDelete` and raw SQL write past it, as past every save interceptor.

**One schedule per slot.** An owner holds at most one schedule per type and state. Adding a schedule to an occupied slot
replaces the one there, the old row removed in the same save. Two additions to one slot in a single save keep the later
one. A unique index per owner column is the database backstop; SQLite counts nulls as distinct, so rows owned through
different columns never collide.

**Records are written by the core, never by hand, and track every state but Open (PEP103).** On every save, each
incentive, directive or checkpoint the save touches is compared with its stored row (read onto a detached copy and judged
by the same resolver — the stored row rather than EF's original values, so an entity attached instead of loaded is
compared correctly too):
- moving up the main line adds a record of each state it reaches, stamped with the save's moment: a jump from an
  unstarted status straight to a finished one records Started and Finished at the same moment;
- moving back down withdraws the records of the states it leaves: pulling a finished objective back to `Standby` (or
  `Blocked`, which is Open) withdraws both, while reopening it into `Polaris` withdraws only its finish;
- deferring adds a `Deferred` record and keeps the others, since the item keeps its place on the main line: failing a
  started objective keeps its start. Coming back withdraws the `Deferred` record, and the move is read from the place the
  kept records show, so resuming to where the item was changes nothing else;
- an entity created in a state counts as entering it: an objective created straight into a Polaris cycle, a fate, a
  decree or a lunar directive created active;
- a kind that keeps a history (a fate, a decree, a lunar directive) records every state it enters anew and withdraws
  nothing, so it may hold several records of one state (PEP103 patch 6); only plans are unique to their slot;
- a kind is recorded only in the states it passes through: a checkpoint holds `Finished` (added when it unlocks,
  withdrawn when it re-locks) and `Deferred`, never `Started`; a fate or a decree never `Finished`. A checkpoint
  with nothing to wait for is not finished (PEP103 patch 5).

A state that changes with time alone (a checkpoint whose due passes) reads the same stored and current, so it is
recorded only once the engine re-evaluates it on its clock. An entity that reached a state before it was recorded has no
record until it enters the state again; the `LifecycleStates` migration turned begins into starts and finishes into
finishes, and a cancelled (now stopped) fate's finish records into deferrals.

**Plans** are the user's, added and deleted through the API. A plan places a start or a finish of a state its owner's kind
passes through: a checkpoint has no start to plan, and a fate or a decree no finish. Deferral is not
planned.

The directive's former `StartDate`/`EndDate` became its planned begin and finish (a data-preserving migration), and its
notes drop the retired `startDate`/`endDate` keys (`RetiredMarkdownField`, vault schema v5).

## Timeframes (PEP100)
`Timeframe` definitions hang off **lunar** directives only and flag a portion of the day (optionally scoped to
cycles by an Orbit). They do nothing on their own. Executives, and the reflectives and attentives that share their
shape, may name one as their `AffinityTimeframe`: a purely semantic preferred execution window, and a set-null
reference, so deleting the timeframe only un-affines them. The directive API exposes both per-directive timeframe
listing and a global listing that pairs every timeframe with a summary of its owning lunar directive.

**Auto-inclusion** (PEP100 patches 1 and 2) seeds that affinity when a Polaris workitem is created.
`TimeframeInclusion` is an integer-stored, append-only kind:
- `None`: set by hand only.
- `College`: the timeframe includes any workitem whose owning incentive carries one of its
  `AutoInclusionColleges`.
- `Availability`: the timeframe carries no parameter. A `Directive` of either kind names it through its
  database-only `AvailabilityTimeframeId`, which may point at any lunar directive's Availability-mode timeframe.
  Every workitem whose owning incentive belongs to that directive, or to one of its descendants, is affined to it.

`TimeframeAffinityResolver.ResolveAsync` decides, and it is the only resolver. The nearest directive availability
wins: the walk starts at the incentive's own directive and follows `ParentDirectiveId` with a visited set, never
parent incentives. Availability takes precedence over College, whose lowest id wins. Three creation paths use the
resolver:
- executives planned from an objective;
- decree-backed executives;
- cycle-begin reflectives.

A one-shot executive has no incentive and gets none, and attentives are never auto-seeded. Auto-inclusion only
seeds at creation; later changes never re-affine existing workitems. A timeframe leaving Availability mode, or
being deleted, on its own or with its lunar directive, clears the directives that name it in the same save. The
clear is a structural rule of the state interceptor, so every write pathway gets it and the change feed announces the
cleared directives; the set-null foreign key is only the database's backstop. The resolver also ignores any
availability that does not point at an Availability-mode timeframe.

**Exclusivity** (`Exclusive`, PEP100 patch 2) is judged among the timeframes active at one moment. Any active
exclusive timeframe drops every active non-exclusive one, and all the active exclusive ones are kept. Exclusivity
does not affect auto-inclusion or affinity. Which timeframes are active is a core decision (see the Plaintorch
genesis):
- the day filter comes from the strictly active cycle's candidates, which are the timeframes whose orbit matches
  the cycle's local start day, a timeframe without an orbit matching every day;
- the window is `[StartTime, EndTime)` at minute precision;
- a start after the end wraps midnight, and a start equal to the end is never active.

An orbit-scoped timeframe keeps a `TimeframeOrbitScheduleState` (PEP100 patch 2), a sibling of the declaratives'
`IncentiveOrbitScheduleState` under the abstract `OrbitScheduleState`. It pins the orbit's epoch and seed, so an
interval or random orbit reads the same way every cycle:
- It follows the declarative reset policy through the state interceptor. Setting or changing the orbit
  re-anchors the state, and clearing the orbit removes it.
- Its epoch is a fixed `Z{…}` literal's own date, else the earlier of today and the open Polaris cycle's day, so an
  orbit set after midnight can still select the day of a cycle begun the evening before and still open. A
  declarative's recurring orbit anchors at today instead. A timeframe state is only previewed and never hardens
  occurrences, so anchoring it back costs no backfill.
- A calendar change never resets it.
- It is only ever previewed, never advanced.
- It is deleted with its timeframe.

## Executive Orders
`ExecutiveOrder` (PEP099) attaches durable constraints or directions to an `OnrushSprint`:
- required `Title` (PUCK-named) and owning `OnrushSprintId`
- optional `Summary`, `EffectiveFrom`, and `EffectiveUntil` fields

Identity uses the composite PUCK declaration `x{?}-o{I:2:1}`: the manual first segment carries the owning
onrush's trimmed numeric part, and the order counter increments per owning onrush
(`Onrush x0180 -> E.O. x180-o01`). Orders are stored `Synced`, as single files, in the owning sprint's
`ExecutiveOrders` partition folder with `Index` PUCK storage.

## Executive Time Allocations
`Executive` carries three optional whole-minute working-time-unit allocations (PEP098):
- `Estimation`: the primary allocation, which also doubles as a lightweight progress marker. The sum of estimations across a cycle's executives expresses the day's total workload.
- `Minimum` / `Maximum`: optional bounds on the allocation.

`Executive.NormalizeTimeAllocations()` enforces the coupling and clamping rules so the three values stay coherent regardless of the order they are supplied:
- when a bound is present but the estimation is still unset, the estimation adopts that bound (preferring the minimum);
- the estimation is always clamped into the `[Minimum, Maximum]` envelope when the relevant bound is present.

Alongside the allocations, `Executive` carries `Elapsed` (Patch098.1): the raw count of tracked (passed) minutes. Unlike the allocations it is a running tally rather than a target — it defaults to `0` and is deliberately excluded from `NormalizeTimeAllocations` (never clamped). It is intentionally *not* part of executive planning (`PolarisExecutivePlan`) because a freshly planned executive has not been worked, so its tracked minutes always start at `0`; it only accrues later through `ExecutiveUpdate`, where `null` leaves it unchanged and any value (including `0` to reset) overwrites it. It has no `Clear` flag because it is never unset.

The application/API layer applies these values (at plan time via `PolarisExecutivePlan`, or via `ExecutiveUpdate`) and then calls the normalizer before persisting. The minute-based storage form is translated for consumers in the application/UI layer (see the SDK working-time-unit helpers) rather than in the domain model.

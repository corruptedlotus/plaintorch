# Orbit Genesis

## Purpose
The `Pleiades.Orbits` domain is the C# port of the Orbit Scheduler engine (`@pleiades/orbits`, from the
`orbit-scheduler` repository). It resolves Orbit notation — the periodic-time declaration syntax used by the
PEP100 declarative ecosystem — into concrete occurrence streams.

The port is statement-faithful to the TypeScript engine (`packages/node/src`), including exact JavaScript
`Date` UTC arithmetic (day-of-month overflow rolling included), the seeded mulberry-style RNG behind `{#n}`
random indices, and the snapshot format. Fidelity was verified against the reference engine over a battery of
notations (streams, per-step resume round-trips, and cross-language snapshot handoffs all match bit-for-bit).
The code is written to graduate into orbit-scheduler's `packages/dotnet` once that package is established;
until then, treat the TypeScript engine as the source of truth when semantics change.

## Main Parts
- `OrbitAst` / `OrbitParser`: notation grammar (`y M w d h m s`, `z{h:m[:s]}`, indexing `{a,b}`/`{a~b}`/`{#n}`,
  nesting `[...]`, intervals `%x`, limits `*x @x <t >t`, spans `=<dur>`, set operators `+ & ^ -`)
- `OrbitCalendar` (`JsDate`, `OrbitGregorianCalendar`): epoch-millisecond calendar arithmetic with exact JS semantics
- `OrbitPleiadeanCalendar`: the six-month Pleiadean calendar (61-day months, Persian-leap-coupled sixth
  month) as an engine calendar; weeks stay 7-day cycles but are **Saturday-anchored** (Saturday = day 1 of
  the week, Friday = day 7), unlike the Gregorian resolver's Monday-anchored week
- `OrbitSpans`: lazy interval algebra for span-format schedules
- `OrbitEngine`: the resolver — candidate solving, per-node `@x`/`*x` counter budgets with provenance,
  boundary limits, and snapshot `Serialize`/`Resume`/`Promote`
- `OrbitSnapshot`: the JSON interchange state blob (compatible with the TypeScript engine's)
- `OrbitDays`: PLAINTORCH's calendar-date facade (`OrbitOccurrenceInstance` projection, tiered validation,
  seeking/preview helpers)

## Calendars Are Modular
The engine resolves against whichever `IOrbitCalendar` it is given. `PlaintorchOrbitService.ResolveCalendar`
picks it per incentive: an explicit per-declarative `Calendar` wins, otherwise the vault's single global
default — `AgendaPreferences.DefaultCalendar` (PEP116), Pleiadean out of the box. This is one default, **not**
a fate-vs-decree kind split. Timeframes carry no calendar of their own, so their orbits always read on that
default (`ResolveDefaultCalendar`, PEP100 patch 2). Timestamps themselves are calendar-agnostic epoch
milliseconds; only month/week/year boundaries differ (and the Pleiadean week is Saturday-anchored — see
`OrbitPleiadeanCalendar`).

One subtlety the default forces: a **fixed-datetime `Z{…}` literal is calendar-sensitive** — it desugars into a
pinned `y/M/d` unit chain resolved through the calendar's `Set`, so `Z{2026/10/3}` under Pleiadean would land in
a six-month year's overflowed month. A one-off fate's literal is an absolute civil moment authored in Gregorian,
so `DeclarativeApiService` pins such a fate to `Calendar = Gregorian` (on create and on reschedule); recurrences
follow the global default.

## The Two Resolution Modes
This is the load-bearing distinction (mirrors the TS `next*` vs `resolve*` split):
- **Seeking** (`OrbitEngine.Next/NextWithin`, `OrbitDays.SeekDaysWithin`): consumes the stream, charging
  counters and advancing the cursor. Used when materializing instances for a committed window — a beginning
  Polaris cycle — after which the advanced snapshot is re-persisted.
- **Preview** (`OrbitEngine.ResolveWithin/ResolveFrom`, `OrbitDays.PreviewDaysWithin/MatchesDay`): trace-free
  resolution as defined from the epoch. Used for lookahead and for validating a single (possibly future)
  occurrence during interaction. Previewing never pushes the persisted state forward.

The future-instance problem is solved by identity, not state: an occurrence's date (plus its time of day
for sub-day granularities) IS its instance id. Interaction previews a future occurrence, materializes the
instance keyed by that identity, and the later seeking pass recognizes it (existence check by
source + date + time) instead of resolving it again. Seeking also catches up: it consumes every occurrence
pending since the last seek, so nothing is ever resolved twice from the beginning.

## PLAINTORCH Integration
- `PlaintorchOrbitService` (application layer) owns the persisted orbit states. They form a TPH hierarchy
  (PEP100 patch 2): the abstract `OrbitScheduleState`, with `IncentiveOrbitScheduleState` (one per orbit-bearing
  declarative) and `TimeframeOrbitScheduleState` (one per orbit-scoped timeframe) sharing the
  `OrbitScheduleStates` table. A declarative's row is created or reset when an orbit is assigned or changed (API
  or watcher file sync) and advanced only by seeking. The lazily created row pins the schedule's random seed so
  `{#n}` previews stay deterministic.
- Timeframe orbits (PEP100 patch 2) are day-matched in **preview** only, against a Polaris cycle's local start
  day, on the vault default calendar. `MatchesTimeframeDayAsync` matches one timeframe; the candidate computation
  uses the batched `MatchTimeframesDayAsync`, which loads the stored states once and reads the tracked ones once,
  with the same per-timeframe semantics. They decide which timeframes are a cycle's candidates (see the Plaintorch
  genesis).
  - A timeframe's state follows the declarative reset policy through the state-policy save hook.
    `ResetTimeframeStateAsync` re-anchors it when the orbit is set or changed, and it is removed when the orbit
    is cleared. A calendar change never resets it.
  - Its epoch is `OrbitDays.FixedLiteralDate(orbit, timeframe calendar) ?? min(today, open cycle day)`. A lone
    fixed `Z{…}` literal anchors at its own date, with its year, month and day read on the timeframe calendar (the
    vault default), the calendar the engine resolves the orbit on: the calendar-aware overload walks the literal the
    way the engine positions its desugared `y[M[d]]` chain (set, snap to start, set) and returns that day's civil
    date. A Pleiadean `Z{3/3/40}` is therefore the 40th day of a 61-day month. A literal the calendar cannot hold
    returns `null` and falls through to the next rule, so it never fails the save. (The Gregorian
    `FixedLiteralDate(orbit)` the declarative reset uses is total too: an impossible date such as `Z{2026/2/30}`
    returns `null` instead of throwing.)
  - Any other timeframe orbit anchors at the earlier of today and the day of the Polaris cycle that has begun and
    not ended (`TimeframeCandidateService.CycleDay`), or at today when no cycle is open; a declarative's would
    anchor at today. The difference exists because an orbit yields nothing before its epoch: anchored at today, an
    orbit set after midnight could never select the day of a cycle begun the evening before and still open. A
    timeframe state is only previewed and never hardens occurrences, so anchoring it back costs no backfill.
  - The reach-back is not free for a phase-bearing orbit. An interval (`%N`), a count limit (`*N`, `@N`) or a
    seeded random counts from the epoch, so one set while an older cycle is still open counts its phase from that
    cycle's day, not from the day it was set, however old the cycle is. That is the accepted trade-off: every orbit
    set under an open cycle must be evaluable on that cycle's day (see core `.DISCUSSION.md`).
  - The state is never advanced.
  - A timeframe whose orbit predates timeframe states gets one lazily on first evaluation, anchored like the
    incentive lazy path (the day being read if it is past, else today), and the candidate computation saves it.
    If a concurrent write gets there first (the timeframe was deleted, or an orbit edit stored a fresh state), that
    save fails; the lazy states are dropped, a warning is logged, and the computed candidates still stand.
  - A stored orbit that fails to parse is logged and reads as not matching, so it never breaks a listing.
- Validation is tiered per consumer (`PlaintorchOrbitService`): fate orbits only need to parse (any
  granularity, spans welcome — the span supplies the eventive length); decree orbits must be granular (any
  granularity from years to minutes, no spans); reflective schedules and timeframes are strict day
  granularity, since both are only ever matched against a whole day.
- Reflectives are Polaris-bound schedules: a lunar-hierarchy decree with `reflect: true` is resolved at day
  granularity against the day its Polaris cycle started, on the decree's own calendar (its explicit `Calendar`,
  else the vault default, through `ResolveCalendar` as above); a match generates the cycle-bound reflective.

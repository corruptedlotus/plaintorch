# Plaintorch Genesis

## Purpose
The `Pleiades.Plaintorch` domain is the application shell for this bounded slice of PLAINFRA.

## Main Parts
- `PlaintorchEngine`
- `Program`
- `PlaintorchModule`
- `PlaintorchUserLayout`
- `PlaintorchUserConfigurationStore`
- `PlaintorchVaultActivationService`
- `ActiveVaultSession`
- `Pleiades.Plaintorch.Api` contracts and implementations
- `Pleiades.Plaintorch.Api.Changes` entity change feed
- vault markdown consistency orchestration during initialization
- vault watcher/discovery orchestration during hosted runtime
- timeframe candidate caching and timeframe auto-affinity resolution (`Pleiades.Plaintorch.Materialization`, PEP100 patch 2)
- hosted core runtime (`Pleiades.Plaintorch.Hosting`: composition root, host state, launch modes, spawn-mode stdio protocol, file logging, single-instance probe) and Linux service bootstrap generation
- active-vault lock orchestration

## How It Works
- `Program` resolves vault startup inputs, installs A11d modules, and activates the current CLI shell flow
- `Program` is a thin entry point: `PlaintorchLaunchArguments` parses the command line into `PlaintorchHostOptions`, `PlaintorchHostFactory.Create` composes the host (JSON conventions, CORS, per-user transport bindings, launch-mode logging, the A11d module graph), and `Program` only runs the selected command against it. Every entry point (console daemon, CLI, a desktop shell spawning the core, tests) builds the same graph through that one factory
- `PlaintorchHostFactory.ConfigureSerializer` is the one definition of the wire JSON conventions: cycle-tolerant references, the tri-state `Optional<T>` converter, and the `@type` runtime-name property on every object. The host applies it on top of the ASP.NET web defaults (camelCase names, numeric enums). Wire-contract tests apply it to the same web defaults, so they serialize exactly as the host does without an HTTP harness. `TimeframeWireContractTests` pins the PEP100 patch 2 shapes that way: `exclusive`, the numeric `autoInclusion`, `availabilityTimeframeId` on both directive kinds, the tri-state creation affinity, the availability request, and `TimeframeUpdate.exclusive`
- `serve` has three launch modes (`PlaintorchLaunchMode`): **Interactive** (a developer's manual serve; console logs; dev sub-profile), **Daemon** (`--daemon` or a systemd unit; real per-user profile; console plus daily file logs under `~/.pleiades/plaintorch/logs`), and **Spawn** (`--spawn`; the child of a desktop shell; file logs only, a JSON-lines status stream on stdout, and a graceful stop when stdin closes). `--profile <dir>` pins an explicit profile root for any serve (a shell in development points its spawned core at the dev sub-profile with it)
- `PlaintorchHostState` also carries an additive `Sweeping` flag, orthogonal to the phase: the coordinator sets it as it hands off to `Active` (before `MarkReady`, so there is no window where a status surface sees a bare `Active` and stops waiting), and the watcher clears it (`EndSweep`) the moment its startup discovery sweep finishes — or when it sleeps because the vault is unreachable, so the flag never wedges. A 30s coordinator backstop clears it if the watcher never reports. The API keeps serving throughout (mode stays `active`); the flag exists so a desktop splash can stall on the startup sweep and show it, then close when the vault is settled. `/healthz` and the spawn stdout `status` event both include `sweeping`.
- The spawn-mode stdout protocol (`PlaintorchHostStatusStream`) is one JSON object per line with an `event` discriminator: `hello` (pid, profile, endpoint), `status` (a `PlaintorchHostStatus` transition), `listening` (the endpoint accepts connections), `stopping`, and, before the host is even built, `already-running` when another core owns the profile. A shell drives its splash and tray from it in order, without probing the API, and reads the process exit as the crash signal
- `PlaintorchStdinShutdownService` (spawn mode) requests `StopApplication` when stdin reaches end-of-file. A parent that quits, or that dies outright, closes that pipe on every platform, which is the portable equivalent of SIGTERM here (a Node `kill()` on Windows is a hard terminate that would leave the vault lock held)
- `PlaintorchInstanceProbe` is the per-user single-instance guard: before `serve` binds, it asks `/healthz` over the profile's own pipe or socket, and a running core makes the newcomer exit with code 3 (and the `already-running` line in spawn mode) instead of failing on the bind. The vault lock does not cover this, because an idle core holds no vault
- `PlaintorchFileLoggerProvider` (`Logging:PlaintorchFile` in `appsettings.json`) is a small daily-rolling file sink, so a core whose console is invisible (desktop shell) or captured (systemd) still leaves a readable trail. It writes `<profile>/logs/plaintorch-YYYY-MM-DD.log`, one file per UTC day, and keeps the newest 14. Its contract:
  - **Queue and drain.** A logger only formats its line and enqueues it on a bounded channel of `QueueCapacity` (10 000) lines, which drops the oldest line when full. One drain task writes every line waiting (`WaitToReadAsync`, then `TryRead` until empty) and flushes once per batch. Logging never blocks the caller, and a stalled disk costs a bounded amount of memory.
  - **It never stops on its own.** A failed open leaves the waiting lines queued. A failed write or flush loses the lines of that attempt. Either way the file is closed, the failure is reported once on standard error (never stdout, which carries the spawn status stream), and the drain retries with a backoff from 250 ms up to 5 s. Lines lost to a full queue or a failed write are reported as one `[WRN] … N log lines dropped` line as soon as the file is writable again. Only disposal ends the drain; an outer catch that reports on standard error is the last resort.
  - **The container owns it.** `PlaintorchHostFactory` registers it through a factory (`TryAddEnumerable(ServiceDescriptor.Singleton<ILoggerProvider, PlaintorchFileLoggerProvider>(factory))`), never `AddProvider(instance)`, whose instance the container would never dispose. Disposing the host therefore disposes the sink, and `Dispose` completes the queue and waits up to 2 s for the tail to reach the disk. The `[ProviderAlias("PlaintorchFile")]` filters apply either way, since the logging framework matches them against the provider's type.
  - **The filters are found wherever the core runs.** The host's content root is `AppContext.BaseDirectory`, not the working directory, so the `appsettings.json` beside the binaries always supplies the filters (`Microsoft` at Warning, `Microsoft.Hosting.Lifetime` at Information), whoever launched the core and from wherever.
  - **Process failures reach the file.** For a file-logging host, `Program` records three kinds of failure as Critical entries with their stack traces: an exception escaping `RunServeAsync` (the host is already disposed there), an unhandled exception on any thread (the sink is then drained before the runtime terminates the process), and an unobserved faulted task. All three go through `PlaintorchFileLoggerProvider.Append`, which queues while the sink is live and, once it is disposed and its drain has stopped, appends straight to the day file (`AppendDirect`). A direct append must never run beside a live sink on the same file, because two handles appending to one file overwrite each other's lines.
  - **Why (2026-09-26).** The drain used to test `Reader.Count` on an unbounded single-reader channel, which cannot count. The `NotSupportedException` was swallowed right after the first line, so each day log held one line per process start while every later line queued forever in memory. The provider was also an instance registration, so no tail was ever flushed at shutdown. Pinned by `PlaintorchFileLoggerTests`.
- `PlaintorchModule` owns the current DI/service registration graph through `A11d.Module`
- `PlaintorchEngine` coordinates vault bootstrap, PUCK issuance, repository persistence, and markdown emission
- Per-user host configuration now lives outside the vault in `~/.pleiades/plaintorch`
- The current CLI supports vault-local `init` and per-user `activate` flows so a moved vault can be adopted without reinitializing it
- The API abstraction is now grouped by action domain so future transport layers can target a stable application contract before socket protocols are finalized
- The application API is now implemented through separate action-area services and modules, with shared helpers for active-state queries and markdown synchronization
- The API domain is now physically mirrored into `Abstractions`, `Contracts`, `Transport`, `Services`, and `Endpoints`, while supporting markdown/state helpers live outside the API namespace
- The initialization path now also runs a lightweight consistency pass for auto-generated-PUCK markdown files before derived indexes are rebuilt
- The hosted core now starts in **idle daemon mode**: `serve` builds and runs the host without requiring a vault, and `PlaintorchCoreService` is the activation coordinator that decides which vault (if any) is served at runtime
  - On start it resolves the active vault from user settings (`PLAINTORCH_VAULT_PATH` override, else the `ActiveVaultPath` in `~/.pleiades/plaintorch/config.json`). If none is configured it stays idle and waits.
  - It reconciles against user settings continuously — nudged by a `FileSystemWatcher` on the config file plus a periodic safety poll — so `plaintorch activate` (which only rewrites user settings) is picked up, the newly-activated vault is served, and clearing the active vault (`plaintorch deactivate`) returns the core to idle. Switching directly between vaults deactivates the old one before activating the new.
  - Activation binds `VaultLayout`, acquires `.plaintorch.lock`, runs `PlaintorchEngine.InitializeVaultAsync` (which ends by purging the timeframe candidate cache and, best effort, warming it for a Polaris cycle already begun), and then marks a new `ActiveVaultSession` generation ready. Deactivation signals the session idle (stopping vault-scoped background work), releases the lock, purges the PUCK runtime catalog and the timeframe candidate cache, and unbinds the layout. A configured-but-uninitialized or lock-contended vault leaves the core idle rather than crashing the host.
  - `ActiveVaultSession` is the readiness/lifecycle seam between the coordinator and vault-scoped hosted services (currently the watcher). Each activation is a monotonically increasing generation with its own cancellation token; consumers track the generation they served so a session is never re-entered, which keeps the serving loop from spinning.
  - `/healthz` reports daemon `mode` (`idle`/`active`) and the active vault path without touching vault state, so idle vs. serving is observable.
- The CLI now exposes `deactivate` alongside `activate`; `PlaintorchVaultActivationService.Deactivate()` clears the active vault in user settings.
- `PlaintorchServiceBootstrapper` generates a Linux systemd **user** unit and its install script only. The Windows machine service it used to generate ran as LocalSystem, so the "per-user" profile resolved to the system account and no user's client could reach the pipe; per-user autostart on a desktop is the standalone shell's job (`../standalone`), and a Windows server runs `serve --daemon` under the user's own session or scheduled task
- Kestrel now binds to the per-user PLAINTORCH socket path and serves the HTTP API over that unix domain socket transport
- The service/runtime path now prefers async initialization and async application endpoint handling
- the service acquires `.plaintorch.lock` before starting the host so vault ownership is enforced before another instance can continue startup
- The hosted runtime now also wires full watcher reconciliation for supported file-backed models: startup discovery scan, path-only sync candidate construction, debounced filesystem watchers, self-write suppression, file-originated create/update flows, canonical rewrite-from-database flows, and purges when storage policy requires them
- The PowerShell-rendered splash popup is gone. `PlaintorchCoreService` now only reports phase transitions to `PlaintorchHostState` (Starting, Idle, Activating, Active, Failed, Stopping, each with a message and the vault concerned); whoever hosts the core decides how to present them. `/healthz` exposes the phase (`phase`, `message`, `vault`, `endpoint`, `since`) beside `mode`/`activeVault`, and in spawn mode the same transitions stream to stdout for the desktop shell's splash
- `PlaintorchUserConfigurationStore.Save` writes atomically (temp file, then move) and `PlaintorchUserConfiguration` keeps unknown keys through `[JsonExtensionData]`, because the desktop shell reads and writes the same `config.json` directly (its own `shell` section) and the core's watcher must never observe a partial write or a core-side save drop the shell's keys
- `PlaintorchMarkdownStorageService` now provides a generic canonical markdown write/delete path for the application shell, preserving existing body content verbatim while normalizing only frontmatter and canonical file identity. It locates an identity-driven entity's existing file across its whole territory (resolving the sync model by family assignability, then `VaultStoragePolicyEngine.EnumerateCandidateMarkdownPaths(model)`), so a save rewrites the file wherever the user placed it — the same resolution discovery uses on read — instead of assuming the canonical root and orphaning a duplicate.
- Per-type save shaping is an **opt-in hook**, not a branch in the central write path: `IEntitySaveHook` / `EntitySaveHook<T>` (resolved as `IEnumerable<IEntitySaveHook>`, matched by `CanHandle`) can override the resolved write path after the mode policy runs; an entity with no registered hook is unchanged. `LorePageSaveHook` is the only one today, re-homing a lore page's self-named folder under a reassigned parent. **Latent (flagged 2026-09-13):** that reassignment path is currently **unreachable through the API** — `LorePageApiService.UpdateAsync` never changes `ParentId`, and `SetIndexAsync` re-keys ids without a `previous` snapshot — so the hook fires only if some future reparent operation presents a changed parent. The logic is preserved (moved verbatim), not wired.
- **Reparenting moves the note (2026-09-20).** A composed storage path (`VaultStorageAttribute.ParentIdProperty` + `ParentEntityType`) puts the parent *in the path*, and on disk the path is the authority for that relationship — while an identity-driven or freeform mode keeps a note wherever it was authored. Those two collide on a reparenting: the API changed the parent, the note stayed put, and the next watcher pass read the old parent back. This is a property of the placement policy, not of any one type, so the rule lives in the generic save pipeline (`PlaintorchMarkdownStorageService.IsReparented`): whenever the declared parent id differs from `previous`, the write lands at the canonical path regardless of the mode's authored-location preference — a self-named directory moves whole (everything nested travels with it), a single note is rewritten under the new parent, and a cleared parent lands at the location root. Any other edit still leaves the note alone; a per-type save hook (lore) still runs afterwards and may refine the path. The parent of every update contract is tri-state (`Optional<string?>`): omitted keeps it, a value reparents, an explicit `null` **de-parents** (a directive to the top level, an incentive to standalone). `DirectiveApiService.EnsureCanReparentAsync` refuses a parent that would break the tree: missing, the directive itself, one of its descendants, or the other family (PEP100). Pinned by `DirectiveReparentingTests`.
- **Taking an activity back out of a cycle (2026-09-20).** `IPolarisCycleApi.RemoveExecutiveAsync` (`DELETE /api/executives/{id}`) deletes the cycle's *record* and nothing else — never the objective or decree behind it, and never any state. Since PEP111 there is one kind of record to remove: adding a decree to a cycle creates a decree-backed executive (`AddDecreeExecutiveAsync`), so objective-backed and decree-backed executives are both taken out through this route. The former `RemoveAttentiveAsync` / `DELETE /api/polaris/attentives/{id}` is gone with the Polaris-bound attentive it removed. The authority rule: the core advances a backlog item's state on the strength of cycle participation and **never walks it back**, so an objective whose executive is removed stays in whatever state it has (`Polaris` included), and what an executed decree-backed executive granted stays granted. (The core does not yet hold to this rule everywhere; the mismatches are to be reconciled later, likely under PEP103 — do not add new demotions meanwhile.) An attentive is never removed this way: every attentive is an unbound occurrence of its decree's schedule, resolved or skipped but never deleted. Pinned by `PolarisActivityRemovalTests`.
- Lore "active" has one definition, the core's `LoreIndex` (the latest begun page walked up to its root). `LorePageApiService` stamps a transient `IsActive` on every `LorePage` it returns (List computes it from the loaded set; single-page returns from the whole-vault index), so the grid reads active from the API instead of re-deriving its own (previously divergent, structural) spine — a client can't re-compute a "now"-dependent date rule without drifting from the core's UTC clock.
- **Active timeframes are a core decision too (PEP100 patch 2).** For the same reason as lore "active", the client no longer works out which timeframes are in play. `GET /api/timeframes/active` (`IDirectiveApi.ListActiveTimeframesAsync(at)`) answers in two stages:
  - **Candidates, per cycle.** A begun Polaris cycle's candidates are every timeframe without an orbit plus every timeframe whose orbit day-matches the cycle's day. `TimeframeCandidateService.CycleDay` defines that day as the cycle's local start day, the same one reflectives use. Orbits read on the vault default calendar. The set is fixed for the cycle's life, even past midnight.
  - **Cache.** The `TimeframeCandidateCache` singleton, modelled on `LoreActiveCache`, holds one volatile entry of candidate **ids** keyed by cycle id and cycle start, so a re-begun cycle misses. Records are projected fresh on every read, so renames and window edits never go stale.
  - **Warm points.** `PolarisCycleApiService.ActivateAsync` warms the cache as its last step, after materializing, writing the cycle note and auditing the begin, and only when the cycle is now strictly active. `PlaintorchEngine.InitializeVaultAsync` (and its sync twin) purges it and warms it for a cycle that had already begun before boot. Both warms resolve `TimeframeCandidateService` from a child scope (`IServiceScopeFactory`), because an options snapshot is fixed per scope. The activation scope may have pinned the calendar preference before preferences were loaded. A begin's request scope may already have read it while materializing reflectives, before a concurrent calendar change finished; warming in that scope would store candidates read on the old calendar under the new version.
  - **Warms are best effort.** Both warm points log any failure other than cancellation as a warning and swallow it, so a warm never fails a begin that is already committed, or a vault activation. The next read recomputes.
  - **Lazy recompute.** A miss recomputes lazily, and a computation saves any timeframe orbit state it had to create lazily. If a concurrent write makes that save fail with a `DbUpdateException` (the timeframe was deleted, or an orbit edit stored a fresh state under the unique timeframe index), the lazy states are detached, a warning is logged, and the computed ids are still returned.
  - **Invalidation.** `TimeframeCandidateCacheInterceptor`, registered beside `LoreActiveCacheInterceptor`, collects in `SavingChanges` and invalidates only after the save commits. It fires on:
    - any `Timeframe` added, modified or deleted;
    - a `PolarisCycle` added or deleted, or with its `StartTime`/`EndTime` modified, which covers a cycle begun or ended through its note's frontmatter by the watcher;
    - any `Directive` deleted, since the database cascades a lunar directive's timeframes away with no tracked timeframe entry;
    - the `DefaultCalendar` preference row changing.

    Orbit state rows are deliberately not a trigger: the lazy-state save would discard the warm it belongs to. `UserPreferenceService` also invalidates the cache itself, after its store write (see the calendar preference below).
  - **Race safety.** A version counter makes a recompute that raced an `Invalidate`/`Purge` drop its stale result instead of storing it. Recomputes are serialized, so two concurrent misses never insert the same lazy state twice.
  - **The calendar preference.** The interceptor's calendar trigger fires inside the save, before `UserPreferenceService` updates the in-memory store that the options read. The service therefore invalidates again once the store holds the new value: after `SetRawAsync` and `ResetAsync` for the `DefaultCalendar` key, and after every `LoadAsync`. A recompute that read the old calendar between the two invalidations is handled in one of two ways. If it has already stored its entry, the second invalidation drops that entry. If it is still running when the second invalidation lands, the version check discards its result. `A_recompute_right_after_the_calendar_preference_call_sees_the_new_calendar` pins the first way only: its racing recompute runs to completion from the save's `SavedChanges` event and stores the old-calendar set, and the test asserts that the store write leaves the cache empty and the next read sees the new calendar. The version check is pinned on the bare cache (`A_recompute_racing_an_invalidation_never_stores_its_stale_result`). The child-scope warms (see warm points) keep a warm from reusing a calendar its scope read before the change. That edge was found by reading the code, and its fix has no test, since it needs a calendar change to land in the middle of a begin.
  - **The active filter.** Only a strictly active cycle (`StartTime` set, `EndTime` unset, highest id first) has active timeframes; there is no any-state "today's cycle" fallback here. A candidate is active when the local time, at minute precision, lies in `[StartTime, EndTime)`. A start after the end wraps midnight, and a start equal to the end is never active. If any active timeframe is `Exclusive`, only the active exclusive ones are returned. Records are shaped and ordered exactly like the global listing (a shared projection), `Exclusive` included.

  Pinned by `TimeframeCandidateTests` and `ActiveTimeframesTests`.
- **One timeframe auto-affinity resolver (PEP100 patch 2).** `TimeframeAffinityResolver.ResolveAsync(directiveId, college)` is the single place auto-inclusion is decided. It tries the nearest directive availability first, then the college rule (`ResolveForCollegeAsync`: College-mode timeframes only, lowest id wins).
  - **The availability walk.** The resolver reads one `Directives` projection (id, parent, availability) and the ids of the Availability-mode timeframes, then walks the projection in memory from the incentive's directive up `ParentDirectiveId`. Ordinal comparers and a visited set stop at a loop in a hand-edited lineage. An availability counts only if it still names an Availability-mode timeframe.
  - **Memoized per scope.** The resolver is scoped, and it keeps both reads for its scope, so a cycle begin that resolves every reflective reads them once. A save through the scope's context drops the memo (`SavedChanges`), so a resolution after a write in the same unit of work still sees that write. The college lookup is not memoized.
  - **Call sites.** All three auto-assignment sites use it: `PolarisCycleApiService.PlanExecutiveAsync`, `AddDecreeExecutiveAsync`, and the reflectives in `ProximityMaterializationService.MaterializeForCycleAsync`.
  - **Tri-state creation affinity.** On both create paths the affinity is an `Optional<long?>`. An omitted key is Auto: the resolver, or none for a one-shot executive, which has no incentive. An explicit `null` is none. An id must exist. `ResolveCreationAffinityAsync` validates an explicit id before any cycle auto-start or objective creation, so a refused request leaves nothing behind. Auto resolves once the objective or decree is known. The saved executive's `AffinityTimeframe` reference is loaded before it is returned.
  - **Setting an availability.** `IDirectiveApi.SetAvailabilityAsync` (`PUT /api/directives/{id}/availability`) sets it for either kind. It accepts only an Availability-mode timeframe, and `null` clears. The field is database-only, so the method saves directly with no write-queue note rewrite, and audits `directive.set-availability`.
  - **Clearing references.** The state-policy save hook clears every directive naming a stale timeframe, tracked, in the same save. It is `PlaintorchStatePolicyProcessor.ClearStaleAvailabilityReferencesAsync`, the first policy `ApplyAsync` runs. A timeframe is stale in three cases:
    - its `Timeframe` entry is deleted;
    - its entry's `AutoInclusion` is modified away from `Availability`, judged against the original value;
    - its lunar directive's entry is deleted. The database cascade removes those timeframes out of EF's sight, so their ids are read from the store before the save.

    The policy loads the referencing directives tracked, then nulls each one whose pending availability still names a stale timeframe, skipping directives deleted in the same save. Riding the save hook covers every write pathway once: the directive API (which no longer clears anything itself), the CLI, the watcher's delete-from-database action and a bare context save. The change-feed interceptor is registered after the state policy, so it announces every cleared directive. The foreign key's `SET NULL` remains the database-level backstop for a write that bypasses EF.

  Pinned by `TimeframeAffinityResolverTests`, `AvailabilityAffinityTests`, `CreationAffinityTests` and `DirectiveAvailabilityTests`. The last asserts the change-feed announcements too, including through a bare-context save and through the watcher's delete action.
- default Onrush/Polaris title generation now follows the calendar phrasing `Onrush/Polaris {d} of {MMMM} {y}` through the shared title factory path
- `PlaintorchChangeFeedInterceptor` announces entity changes from the EF save hook, for the same reason `PlaintorchStatePolicyInterceptor` sits there: it is the one place every write pathway passes through, so the watcher syncing a markdown edit, the CLI and the scheduler are covered alongside the API. It is registered after the state policy, so it announces what policy left behind rather than what the caller originally asked for
- Changes carry identity only — the runtime type name, matching the `@type` the API serializes, and the PUCK. A child record with no identity of its own (executive, reflective, eventive, attentive) is announced as a change to its owner, resolved from EF relationship metadata rather than hardcoded key names
- A `Dependency` edge (PEP101) fits neither rule: it has no PUCK of its own, and its endpoints are loose references the domain deliberately leaves without foreign keys, so owner resolution finds nothing to walk. It is special-cased to announce both of its endpoints as modified — the entities a client actually observes. An eventive endpoint names its owner rather than a tracked type, which still carries, because any announcement revalidates the observed listings on the far side
- `PlaintorchChangeBroker` fans changes out to listeners as a singleton, dropping the oldest events for a subscriber that has stopped reading; a consumer that misses events revalidates what it is showing, so a gap costs a refetch rather than correctness
- `GET /api/system/changes` streams the feed as server-sent events, with heartbeats so a connection that died without closing is detectable
- The engine is intentionally thin: it orchestrates use of the other domains rather than re-implementing their responsibilities

## Current Scope
This layer is still a bootstrap shell with minimal CLI behavior:
- `init`
- `activate`
- `deactivate`
- `serve` (`--daemon`, `--spawn`, `--ephemeral`, `--profile <dir>`, `--loopback`, `--vault <path>`)
- `bootstrap-service` (Linux systemd user unit only)

It is the correct place for future application workflows, sync commands, and operator-facing orchestration.

## API Direction
The `Pleiades.Plaintorch.Api` contracts now mirror the blueprint action model:
- `ISystemApi`
- `IDirectiveApi`
- `IObjectiveApi`
- `IOnrushSprintApi`
- `IPolarisCycleApi`

These are application contracts, not transport DTOs. They are intentionally async and cancellation-aware so the future background service and socket transport can bind to them cleanly.

Those contracts are now backed by modular in-process services:
- `SystemApiService`
- `DirectiveApiService`
- `ObjectiveApiService`
- `OnrushSprintApiService`
- `PolarisCycleApiService`
- `PlaintorchApiService`

Registration is split across dedicated modules so application-area composition stays clean as the host/runtime surface grows.

The next application-shell step is stronger operator-visible diagnostics, explicit regression coverage for metadata-only canonical rewrites, and continued retirement of legacy synchronous engine pathways in favor of the hosted async application surface.

# Plaintorch Genesis

## Purpose
The `Pleiades.Plaintorch` domain is the application shell for this bounded slice of PLAINFRA.

## Main Parts
- `PlaintorchEngine`
- `Program`
- `PlaintorchModule`
- `PlaintorchUserLayout`
- `PlaintorchUserConfigurationStore`
- `PlaintorchVaultActivationService`
- `Pleiades.Plaintorch.Api` contracts and implementations
- `Pleiades.Plaintorch.Api.Changes` entity change feed
- vault markdown consistency orchestration during initialization
- vault watcher/discovery orchestration during hosted runtime
- hosted core runtime and service bootstrap generation
- active-vault lock orchestration

## How It Works
- `Program` resolves vault startup inputs, installs A11d modules, and activates the current CLI shell flow
- `Program` now also exposes `serve` and `bootstrap-service` commands for running or preparing the background core
- `PlaintorchModule` owns the current DI/service registration graph through `A11d.Module`
- `PlaintorchEngine` coordinates vault bootstrap, PUCK issuance, repository persistence, and markdown emission
- Per-user host configuration now lives outside the vault in `~/.pleiades/plaintorch`
- The current CLI supports vault-local `init` and per-user `activate` flows so a moved vault can be adopted without reinitializing it
- The API abstraction is now grouped by action domain so future transport layers can target a stable application contract before socket protocols are finalized
- The application API is now implemented through separate action-area services and modules, with shared helpers for active-state queries and markdown synchronization
- The API domain is now physically mirrored into `Abstractions`, `Contracts`, `Transport`, `Services`, and `Endpoints`, while supporting markdown/state helpers live outside the API namespace
- The initialization path now also runs a lightweight consistency pass for auto-generated-PUCK markdown files before derived indexes are rebuilt
- The hosted core now starts through `PlaintorchCoreService`, initializes the active vault on service start, and waits for coordinated host shutdown
- `PlaintorchServiceBootstrapper` now generates Windows PowerShell service-install scripts or Linux systemd user-service assets from the CLI
- Kestrel now binds to the per-user PLAINTORCH socket path and serves the HTTP API over that unix domain socket transport
- The service/runtime path now prefers async initialization and async application endpoint handling
- the service acquires `.plaintorch.lock` before starting the host so vault ownership is enforced before another instance can continue startup
- The hosted runtime now also wires full watcher reconciliation for supported file-backed models: startup discovery scan, path-only sync candidate construction, debounced filesystem watchers, self-write suppression, file-originated create/update flows, canonical rewrite-from-database flows, and purges when storage policy requires them
- Interactive Windows `serve` runs can now show a splash/status popup during startup and failure states, using application-owned splash assets copied with the build output and a declarative presentation model instead of hardcoded script styling
- `PlaintorchMarkdownStorageService` now provides a generic canonical markdown write/delete path for the application shell, preserving existing body content verbatim while normalizing only frontmatter and canonical file identity
- default Onrush/Polaris title generation now follows the calendar phrasing `Onrush/Polaris {d} of {MMMM} {y}` through the shared title factory path
- `PlaintorchChangeFeedInterceptor` announces entity changes from the EF save hook, for the same reason `PlaintorchStatePolicyInterceptor` sits there: it is the one place every write pathway passes through, so the watcher syncing a markdown edit, the CLI and the scheduler are covered alongside the API. It is registered after the state policy, so it announces what policy left behind rather than what the caller originally asked for
- Changes carry identity only — the runtime type name, matching the `@type` the API serializes, and the PUCK. A child record with no identity of its own (executive, reflective, eventive, attentive) is announced as a change to its owner, resolved from EF relationship metadata rather than hardcoded key names
- `PlaintorchChangeBroker` fans changes out to listeners as a singleton, dropping the oldest events for a subscriber that has stopped reading; a consumer that misses events revalidates what it is showing, so a gap costs a refetch rather than correctness
- `GET /api/system/changes` streams the feed as server-sent events, with heartbeats so a connection that died without closing is detectable
- The engine is intentionally thin: it orchestrates use of the other domains rather than re-implementing their responsibilities

## Current Scope
This layer is still a bootstrap shell with minimal CLI behavior:
- `init`
- `activate`
- `serve`
- `bootstrap-service`

It is the correct place for future application workflows, sync commands, and operator-facing orchestration.

## API Direction
The `Pleiades.Plaintorch.Api` contracts now mirror the blueprint action model:
- `ISystemApi`
- `IDirectiveApi`
- `IObjectiveApi`
- `IOnrushSprintApi`
- `IPolarisCycleApi`

These are application contracts, not transport DTOs. They are intentionally async and cancellation-aware so the future background service and socket transport can bind to them cleanly.

Those contracts are now backed by modular in-process services:
- `SystemApiService`
- `DirectiveApiService`
- `ObjectiveApiService`
- `OnrushSprintApiService`
- `PolarisCycleApiService`
- `PlaintorchApiService`

Registration is split across dedicated modules so application-area composition stays clean as the host/runtime surface grows.

The next application-shell step is stronger operator-visible diagnostics, explicit regression coverage for metadata-only canonical rewrites, and continued retirement of legacy synchronous engine pathways in favor of the hosted async application surface.

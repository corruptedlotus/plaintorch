# PLAINTORCH Discussion Notes

## Environment Assumption
- PLAINTORCH is designed to work against an Obsidian vault directory.
- The SQLite database is stored inside the vault under `.plaintorch-data/plaintorch.sqlite3`.
- Vault-local PLAINTORCH settings live in the `.plaintorch` file at the vault root.
- The implementation now uses EF Core with the SQLite provider through `PlainfraContext`.
- Per-user host configuration now lives outside the vault in `~/.pleiades/plaintorch`.

## Implemented From Current Blueprint
- Core models for `Directive`, `OnrushSprint`, `Objective`, `PolarisCycle`, `Executive`, and `Reflective`.
- Added `CelestronTransaction` for ledger entries.
- PUCK notation metadata and a first-pass parser/generator for:
  - manual numerators
  - spiritgem numerators
  - incremental numerators
  - date-stamp numerators
  - telescope and filesystem separators in generated IDs
- Vault bootstrap and SQLite schema creation.
- EF Core `DbContext` mapping for current CLR models and PUCK support tables.
- Markdown frontmatter serialization for vault-facing files.
- File path conventions for directives, onrush sprints, and journal cycles.
- Polaris forecast/start/finish lifecycle helpers.
- Console bootstrap flow with `init` and `activate` commands.
- Code organization is being shifted into domain folders and namespaces:
  - `Pleiades.Puck`
  - `Pleiades.Orchestration`
  - `Pleiades.Vault`
  - `Pleiades.Plaintorch`

## Domain Consolidation Note
- `Operations` has been merged into `Orchestration` so directives, objectives, cycles, executives, and reflectives all live in the same bounded context.

## Missing or Underspecified Blueprint Details
The following items were not fully specified, so they were left as discussion items rather than hard-coded behavior.

### 1. File-to-database synchronization contract
The blueprint says markdown-backed models should be two-way bound with the database, but it does not define:
- the authoritative conflict-resolution order when both DB and file changed
- how to detect external Obsidian edits reliably
- whether sync is manual, startup-based, background, or file-watcher based
- how partial sync failures should be logged or surfaced

Current groundwork:
- startup now performs a narrow consistency pass for auto-generated-PUCK file names
- title-only filenames are accepted as legitimate user-created pre-sync inputs for generated-ID entities
- unknown-ID files are now normalized back to title-only names by default, or purged when a storage mode later requires strict enforcement
- the background service transport is now verified over the per-user unix domain socket and can be used as the future sync/discovery control plane
- deletion paths now have temporal graveyard foundations, including desync-driven file purges
- audit trail entries can now record discovery/sync actions using soft entity references and temporal entry keys
- sync model detection is now explicitly path-only through the vault watcher catalog, and sync policy is read from `VaultStorageAttribute.Mode`
- watcher reconciliation now executes the decided actions for supported file-backed models, including file-originated create/update flows, canonical rewrite-from-database flows, file purges, and self-write suppression
- canonical markdown rewrites now preserve the existing markdown body verbatim; storage and watcher authority is intentionally limited to frontmatter and canonical file identity
- watcher rename handling now includes relocation-first reconciliation so moved entities are updated from their new path context before standalone old/new path fallbacks
- canonical parent-reassignment sync now relocates self-named entity directories as whole trees (including `FileFirst`), preserving nested children during parent folder moves
- lore parent reassignment now supports horizontal moves only (expected static-level parent boundaries), while vertical reassignment remains blocked by static nesting constraints
- directives now support freeform watcher detection through frontmatter `puck` identity under `VaultStorageMode.Freeform`, and watcher no longer auto-creates missing-id freeform directives from filename/path presence alone
- unknown freeform directive PUCK assertions are now purged by policy, while known PUCK files continue update/rewrite reconciliation
- directive initialization now has an API-assisted path (`/api/directives/init`) that routes through watcher candidate validation and creation logic
- watcher path filtering now excludes hidden/metadata-style folders (`.` and `_` segments) and Obsidian attachment folders configured through `.obsidian/app.json:attachmentFolderPath`
- startup watcher sweep now executes in policy-aware order (existing-entity sync/rewrite first, then creations, then purges/conflicts), reducing side-effect races during initial reconciliation
- watcher now tracks a runtime issue registry (`VaultWatcherIssueRegistry`) and derives health states (`ok|issues|standby|offline`) for system briefing/status surfaces
- watcher issue handling is now criteria-driven and declarative through `VaultWatcherIssueSignal` + `VaultWatcherIssueType`, so failures and recoveries are resolved by explicit success criteria rather than exception identity alone
- issue registry now records criterion evaluation state and exposes totals (evaluated vs failed criteria) so status surfaces can reflect both encountered and non-encountered criteria outcomes
- system diagnostics API now exposes full watcher issue payloads (`/api/system/watcher/issues`) including criticality, human-readable descriptions, criteria metadata, occurrence counts, and originating path metadata
- system diagnostics API now exposes path-scoped watcher diagnostics (`/api/system/watcher/issues-for?path=...`) for file/folder-specific issue and criterion inspection
- watcher major issue taxonomy now favors concrete operational causes (for example `FilePermissionDenied`, `FileInUse`, `MarkdownValidationError`, `PuckViolation`, `PolicyViolation`) over only pipeline-stage labels, so diagnostics better explain what users should inspect
- partition-folder safeguards now prevent partition containers (for example directive-local `Objectives/`) from being misdetected as directive entities during path-only discovery
- objective candidate classification under directive roots now honors configured partition folder expectations, reducing cross-shape ambiguity in mixed directive/objective trees
- freeform directive boundary enforcement now flags/disallows freeform ownership assertions inside non-directive managed roots (metadata, objectives, onrush, journal, saga)
- freeform path assertion rules in markdown storage were aligned with watcher discovery so valid directive-root/default placements no longer trigger fallback relocation churn
- directive `/api/directives/init` now enforces watcher policy outcomes for freeform onboarding: initialization proceeds only for valid `CreateFromFile` candidates and rejects policy-boundary or validation violations with concrete reasons
- manual directive init now also supports freeform markdown files without frontmatter PUCK by treating explicit API init as an intentional create override for that specific watcher `Ignore` case, while still rejecting root/entity/partition boundary violations
- self-named watcher candidate detection now excludes root-level same-name files inside entity roots (for example `Onrush/Onrush.md`) to prevent startup sweep false-positive entity creation
- directive parent-id resolution now falls back to frontmatter `puck` when filename identity is absent, so objective files manually added under directive partition folders (`Objectives/`) can still be picked up and linked to the owning directive
- containing-directive resolution now also supports freeform parent directories whose anchor note name differs from the folder name (for example `Directives/Nooo/Mewo!.md`), so nested partition objectives like `Directives/Nooo/Objectives/Shooma.md` are no longer missed
- freeform directive boundary checks now explicitly reject key-directory ownership assertions (vault root, entity roots, and partition folders) to stay aligned with PEP090 root-node constraints
- watcher storage policy logic is now mode-specific and routed through dedicated services (`Freeform`, `Enforced`, `Optional`, `Synced`, `FileFirst`) instead of a single centralized decision branch
- freeform model belonging now depends on frontmatter `puck` identity resolution (not path-shape), and watcher no longer auto-initializes freeform files without PUCK identity during discovery/sweep
- containing-directive inference now runs through centralized ownership-boundary policy (`VaultWatcherPathPolicy`) so root directories are never treated as directive-owned containers
- non-freeform PUCK candidates now preserve filename-derived title authority during discovery/reconciliation so safe file renames update canonical title upstream instead of being rewritten from stale database title
- objective identity hydration now keeps markdown relation mapping for `directive` so watcher validation/reconciliation no longer churns on missing relation identity
- canonical metadata rewrites now preserve unknown custom frontmatter properties while still normalizing authoritative keys
- frontmatter validation/deserialization now scopes metadata authority to `MarkdownField`-mapped properties (plus `puck`), reducing false invalidation from unrelated frontmatter keys

Still needed:
- authoritative conflict policy when both the database and markdown changed materially
- relation-protected delete/recreate enforcement during live watcher reconciliation
- explicit regression tests that prove canonical rewrites never synthesize or mutate markdown body content
- broader relocation identity matching for purely manual/nested IDs that cannot be inferred from filename alone
- full freeform-boundary enforcement parity with PEP090 language for complex same-type directory ownership edge cases

### 3.1 Path-only sync topology
The sync system now assumes that model detection must be resolved from path alone.

Implemented direction:
- `VaultStorageAttribute` now carries explicit storage-shape metadata
- file-backed types can declare dynamic parent composition via parent-id metadata
- objectives are now synced file-backed entities and may appear either in the standalone `Objectives` root or within directive directories
- directive/objective coexistence under shared roots is permitted only when topology validation can still distinguish candidate paths unambiguously
- path-derived hierarchy is mirrored into frontmatter for readability, but path remains authoritative during discovery and sync
- canonical markdown storage now resolves parent hierarchy generically from storage metadata before composing the canonical file path

Still needed:
- clearer conflict semantics when frontmatter parent references disagree with composed path ancestry
- final policy for path changes caused by parent title or custom-directory updates while external edits are in flight
- whether `MarkdownFileLocator` should also become fully metadata-driven internally instead of still containing some entity-specific path branching

### 3.2 PEP091 implicit policy and PUCK storage
PUCK identity storage is now an explicit `VaultStorageAttribute.PuckStorage` policy (`Quiet` frontmatter identity by default, `Index` filename identity opt-in) that is fully decoupled from the storage mode. A new `Implicit` storage mode was added: it is identity-driven like freeform but withholds initial file materialization and only becomes deletion-authoritative once a `BoundaryBegin` audit entry marks that its file has begun existing.

Implemented direction:
- `MarkdownFrontMatterSerializer` and `MarkdownFileLocator` now branch on `PuckStorage` (quiet vs index) instead of `Mode == Freeform`
- `PolarisCycle`, `OnrushSprint`, and `LorePage` were recalibrated to `Index`; `Directive` and `Objective` are `Quiet`
- `Objective` moved from `Synced` to `Implicit`: creating an objective no longer writes a file, `POST /api/objectives/{id}/begin` (or a user-authored file with matching `puck` frontmatter) begins its boundary, and deleting the boundary-begun file removes the database row
- deletions of quiet title-only files recover identity from the `BoundaryBegin` entry's recorded vault-relative path, because the filename carries no identity
- the `AuditLogEntry.Action` column is now indexed for rapid boundary checks

Migration caveats to watch:
- pre-PEP091 objective files use the `{id} - {Title}.md` index form with no `puck` frontmatter; under implicit/quiet ownership they are no longer recognized as objectives (frontmatter identity is required), so legacy objective files must be re-materialized (`begin`) or given `puck` frontmatter to be picked up again
- implicit storage, like freeform, does not auto-create entities from title-only files that lack `puck` identity, which is a deliberate departure from the previous synced-objective behavior that adopted title-only pre-PUCK files
- boundary path recovery keys on the recorded vault-relative path; a rename immediately followed by deletion before rediscovery could miss the recovery until the boundary location is refreshed on next materialization

### 3.3 PEP092 vault migration system
The vault now versions its on-disk conventions (`.plaintorch:SchemaVersion`) and migrates them at startup alongside the database migration, through `Pleiades.Vault.Migration`. The model is load-then-re-canonicalise: `VaultLoader` reads the vault under the `VaultConventionSet` for the stored version, and each entity is re-emitted under the current conventions via `PlaintorchMarkdownStorageService.RecanonicalizeAsync`, preserving the markdown body. `VaultMigrationRunner` gates on the version, records `VaultMigrationHistory`, and snapshots legacy files to the graveyard for rollback. The first migration (v1→v2) backfills PEP091 objective files.

Implemented direction / deliberate refinements:
- Only the loader is convention-parameterised; the writer always emits current conventions because migrations only move forward. This avoided an invasive, regression-prone refactor of the whole `MarkdownFileLocator`/`MarkdownFrontMatterSerializer` write path.
- A migration declares the entity types it targets (scoping, not per-file diffing), keeping unrelated entities untouched.
- Rollback snapshots are taken as file *copies* into `graveyard/files/migration-v{from}-to-v{to}` before rewrite (the temporal service otherwise moves files, which would remove the source the re-canonicalise pass reads).
- Idempotency comes primarily from the version gate; a re-run also self-skips because already-converted files no longer resolve identity under the old conventions.

Still needed / known limitations:
- Filename-*separator* changes are not yet convention-aware (the loader's Index parse uses the current `PuckNamedIdentity.Separator`); a version that changes the separator needs a bespoke loader.
- Rollback snapshots copy single files; self-named-directory-shaped migrations would need to snapshot the whole directory.
- A migration that finishes with per-entity conflicts still advances the version (conflicts are audited but not retried); a stuck file needs manual attention rather than blocking all future migrations.
- No per-file dry-run yet; `VaultMigrationRunner.GetPendingPlan()` reports which migrations would run at the version level.
- Legacy objective files without resolvable v1 identity (title-only pre-PUCK drafts) are intentionally left untouched by the migration.

### 3.4 PEP093 test harness and dev-latch environment
The core now has an xUnit suite in `../core.tests` that drives the real DI graph over a fresh, isolated vault per test
(`TestVault` builds the host with `Install<PLAINTORCH>()` but never starts it, so the watcher/Kestrel stay dormant, and
behaviour is exercised deterministically through the discovery→decision→sync pipeline). This begins closing the
zero-test / weak-observability gap flagged as the core's biggest risk ahead of the planned dispatch-coupling refactors.

`serve` gained an isolated dev environment so tests and sandbox sessions no longer collide on, or pollute, the real
per-user socket/config/port: `--ephemeral` (random user-independent temp profile), socket-only by default with opt-in
`--loopback`, and interactive relaunch as the static `PLAINTORCHDEV` account.

Still needed / notes:
- Coverage today is a high-risk tranche (body preservation, implicit boundary, classification, migration round-trip,
  serializer round-trip, version store, file locator); the full surface and its status live in
  `_documents/Criteria - Validators, Checks & Unit Test.md`, which is the coverage backlog for future PEPs.
- The `PLAINTORCHDEV` relaunch success path is Windows-centric and not CI/sandbox-exercisable (no account/credentials);
  only the `--ephemeral` and reject-on-failure paths are covered automatically.
- The static dev password lives in-tree (dev-only, unprivileged account) and is overridable via `PLAINTORCHDEV_PASSWORD`.
- Tests are behaviour-focused (files + database + decisions) so they survive, rather than obstruct, the refactors.

### 13. Transitory task modeling
Open blueprint question:
- should transitory tasks become thematic/unending objectives, standalone executives, or a hybrid?

Analytic view:
- transitory tasks are usually operational occurrences, not enduring intent objects
- `Objective` should stay the durable commitment layer because it carries strategic identity, onrush assignment, college, and reward value
- `Executive` should stay the cycle-scoped execution layer because it describes concrete work performed within a Polaris cycle

Recommended direction:
- use a hybrid model
  - thematic or unending work should live as durable `Objective` records
  - individual transient acts should usually be represented as `Executive` records, optionally linked to those objectives
  - allow objective-less standalone executives for one-off chores, interruptions, or ephemeral operational work that should not pollute the long-lived objective backlog

Why this is the cleanest fit:
- it preserves backlog hygiene by not forcing every fleeting action into the strategic objective layer
- it preserves cycle history by keeping actual performed work attached to Polaris cycles
- it avoids turning executives into pseudo-objectives with long-lived meaning they were not designed to hold
- it gives later analytics a useful split between intent (`Objective`) and execution (`Executive`)

Practical implication for future implementation:
- if standalone executives are adopted, the `Plan Executive` flow should remain capable of creating an execution record without creating or linking an objective
- recurring thematic work can then be modeled as one enduring objective with many executives over time, which is more analytically stable than proliferating duplicate objectives

Current implementation:
- `Objective` now includes an enduring/repeating flag
- `Executive` can now carry its own optional title and exist without a linked objective
- the Polaris executive planning surface now supports one-shot executive creation directly

Remaining nuance:
- it is still undecided whether one-shot executives should ever produce Celestron value directly or whether rewards should remain objective-derived only

### 14. Async boundary completeness
The project now has a much stronger async path for service execution, but it is not fully async end-to-end yet.

Now async-capable:
- hosted core startup
- database migration startup path
- lore reindex orchestration
- markdown file writes and body reads in the API markdown service
- HTTP endpoint handlers and application API surfaces

Still partly synchronous:
- user configuration file load/save
- vault settings load/save
- consistency-reconciliation filesystem traversal and rename/delete operations
- several repository helper methods still use synchronous EF Core save/query patterns
- the legacy synchronous engine/bootstrap methods still exist for CLI convenience

Implication:
- the service path is now async enough to proceed with discovery/sync work, but the file engine should be built on the async-capable paths and continue retiring synchronous persistence and file I/O where practical

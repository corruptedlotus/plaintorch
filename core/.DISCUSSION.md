# PLAINTORCH Discussion Notes

## Environment Assumption
- PLAINTORCH is designed to work against an Obsidian vault directory.
- The SQLite database is stored inside the vault under `.plaintorch-data/plaintorch.sqlite3`.
- Vault-local PLAINTORCH settings live in the `.plaintorch` file at the vault root.
- The implementation now uses EF Core with the SQLite provider through `PlainfraContext`.
- Per-user host configuration now lives outside the vault in `~/.pleiades/plaintorch`.

## Implemented From Current Blueprint
- Core models for `Directive`, `OnrushSprint`, `Objective`, `PolarisCycle`, `Executive`, and `Reflective`.
- Added `CelestronTransaction` for ledger entries.
- PUCK notation metadata and a first-pass parser/generator for:
  - manual numerators
  - spiritgem numerators
  - incremental numerators
  - date-stamp numerators
  - telescope and filesystem separators in generated IDs
- Vault bootstrap and SQLite schema creation.
- EF Core `DbContext` mapping for current CLR models and PUCK support tables.
- Markdown frontmatter serialization for vault-facing files.
- File path conventions for directives, onrush sprints, and journal cycles.
- Polaris forecast/start/finish lifecycle helpers.
- Console bootstrap flow with `init` and `activate` commands.
- Code organization is being shifted into domain folders and namespaces:
  - `Pleiades.Puck`
  - `Pleiades.Orchestration`
  - `Pleiades.Vault`
  - `Pleiades.Plaintorch`

## Missing or Underspecified Blueprint Details
The following items were not fully specified, so they were left as discussion items rather than hard-coded behavior.

### 1. File-to-database synchronization contract
The blueprint says markdown-backed models should be two-way bound with the database, but it does not define:
- the authoritative conflict-resolution order when both DB and file changed
- how to detect external Obsidian edits reliably
- whether sync is manual, startup-based, background, or file-watcher based
- how partial sync failures should be logged or surfaced

Current groundwork:
- startup now performs a narrow consistency pass for auto-generated-PUCK file names
- title-only filenames are accepted as legitimate user-created pre-sync inputs for generated-ID entities
- unknown-ID files are now normalized back to title-only names by default, or purged when a storage mode later requires strict enforcement
- the background service transport is now verified over the per-user unix domain socket and can be used as the future sync/discovery control plane
- deletion paths now have temporal graveyard foundations, including desync-driven file purges
- audit trail entries can now record discovery/sync actions using soft entity references and temporal entry keys
- sync model detection is now explicitly path-only through the vault watcher catalog, and sync policy is read from `VaultStorageAttribute.Mode`
- watcher reconciliation now executes the decided actions for supported file-backed models, including file-originated create/update flows, canonical rewrite-from-database flows, file purges, and self-write suppression
- canonical markdown rewrites now preserve the existing markdown body verbatim; storage and watcher authority is intentionally limited to frontmatter and canonical file identity
- watcher rename handling now includes relocation-first reconciliation so moved entities are updated from their new path context before standalone old/new path fallbacks
- canonical parent-reassignment sync now relocates self-named entity directories as whole trees (including `FileFirst`), preserving nested children during parent folder moves
- lore parent reassignment now supports horizontal moves only (expected static-level parent boundaries), while vertical reassignment remains blocked by static nesting constraints
- directives now support freeform watcher detection through frontmatter `puck` identity under `VaultStorageMode.Freeform`, and watcher no longer auto-creates missing-id freeform directives from filename/path presence alone
- unknown freeform directive PUCK assertions are now purged by policy, while known PUCK files continue update/rewrite reconciliation
- directive initialization now has an API-assisted path (`/api/directives/init`) that routes through watcher candidate validation and creation logic
- watcher path filtering now excludes hidden/metadata-style folders (`.` and `_` segments) and Obsidian attachment folders configured through `.obsidian/app.json:attachmentFolderPath`
- startup watcher sweep now executes in policy-aware order (existing-entity sync/rewrite first, then creations, then purges/conflicts), reducing side-effect races during initial reconciliation
- watcher now tracks a runtime issue registry (`VaultWatcherIssueRegistry`) and derives health states (`ok|issues|standby|offline`) for system briefing/status surfaces
- watcher issue handling is now criteria-driven and declarative through `VaultWatcherIssueSignal` + `VaultWatcherIssueType`, so failures and recoveries are resolved by explicit success criteria rather than exception identity alone
- issue registry now records criterion evaluation state and exposes totals (evaluated vs failed criteria) so status surfaces can reflect both encountered and non-encountered criteria outcomes
- system diagnostics API now exposes full watcher issue payloads (`/api/system/watcher/issues`) including criticality, human-readable descriptions, criteria metadata, occurrence counts, and originating path metadata
- system diagnostics API now exposes path-scoped watcher diagnostics (`/api/system/watcher/issues-for?path=...`) for file/folder-specific issue and criterion inspection
- watcher major issue taxonomy now favors concrete operational causes (for example `FilePermissionDenied`, `FileInUse`, `MarkdownValidationError`, `PuckViolation`, `PolicyViolation`) over only pipeline-stage labels, so diagnostics better explain what users should inspect
- partition-folder safeguards now prevent partition containers (for example directive-local `Objectives/`) from being misdetected as directive entities during path-only discovery
- objective candidate classification under directive roots now honors configured partition folder expectations, reducing cross-shape ambiguity in mixed directive/objective trees
- freeform directive boundary enforcement now flags/disallows freeform ownership assertions inside non-directive managed roots (metadata, objectives, onrush, journal, saga)
- freeform path assertion rules in markdown storage were aligned with watcher discovery so valid directive-root/default placements no longer trigger fallback relocation churn
- directive `/api/directives/init` now enforces watcher policy outcomes for freeform onboarding: initialization proceeds only for valid `CreateFromFile` candidates and rejects policy-boundary or validation violations with concrete reasons
- manual directive init now also supports freeform markdown files without frontmatter PUCK by treating explicit API init as an intentional create override for that specific watcher `Ignore` case, while still rejecting root/entity/partition boundary violations
- self-named watcher candidate detection now excludes root-level same-name files inside entity roots (for example `Onrush/Onrush.md`) to prevent startup sweep false-positive entity creation
- directive parent-id resolution now falls back to frontmatter `puck` when filename identity is absent, so objective files manually added under directive partition folders (`Objectives/`) can still be picked up and linked to the owning directive
- containing-directive resolution now also supports freeform parent directories whose anchor note name differs from the folder name (for example `Directives/Nooo/Mewo!.md`), so nested partition objectives like `Directives/Nooo/Objectives/Shooma.md` are no longer missed
- freeform directive boundary checks now explicitly reject key-directory ownership assertions (vault root, entity roots, and partition folders) to stay aligned with PEP090 root-node constraints
- watcher storage policy logic is now mode-specific and routed through dedicated services (`Freeform`, `Enforced`, `Optional`, `Synced`, `FileFirst`) instead of a single centralized decision branch
- freeform model belonging now depends on frontmatter `puck` identity resolution (not path-shape), and watcher no longer auto-initializes freeform files without PUCK identity during discovery/sweep
- containing-directive inference now runs through centralized ownership-boundary policy (`VaultWatcherPathPolicy`) so root directories are never treated as directive-owned containers
- non-freeform PUCK candidates now preserve filename-derived title authority during discovery/reconciliation so safe file renames update canonical title upstream instead of being rewritten from stale database title
- objective identity hydration now keeps markdown relation mapping for `directive` so watcher validation/reconciliation no longer churns on missing relation identity
- canonical metadata rewrites now preserve unknown custom frontmatter properties while still normalizing authoritative keys
- frontmatter validation/deserialization now scopes metadata authority to `MarkdownField`-mapped properties (plus `puck`), reducing false invalidation from unrelated frontmatter keys
- the startup auto-generated-PUCK consistency pass is now confined to declared territory and notation-gated, both policy-level and model-agnostic: a stray `prefix - title.md` is normalized/purged only when its prefix tokenizes against the entity's declared PUCK *and* the file sits in a specific (non-vault-root) scan root or a folder hosted by a parent entity that exists in the database (hosting types derived from the catalog's declared `ParentEntityType`, never hard-coded) — so non-entity notes elsewhere (e.g. `Projects/2024-01 - Roadmap.md`) are no longer stripped of their prefix at startup (`NonEntityFileIsolationTests` / `NonEntityFileParityTests` / `AutoGeneratedPuckConsistencyTests`)
- the migration loader (`VaultLoader`) is now confined to the same declared territory: the v1→v2 objective migration reads objectives under the legacy Index filename convention, and a PUCK-shaped prefix in a non-owned folder (e.g. `Projects/j00000099 - Draft.md`) passed the notation gate and was migrated (prefix stripped). The loader now trusts a filename-embedded identity only inside a specific scan root or a database-known hosting parent's folder (`NonEntityFileMigrationTests`)

Still needed:
- authoritative conflict policy when both the database and markdown changed materially
- relation-protected delete/recreate enforcement during live watcher reconciliation
- explicit regression tests that prove canonical rewrites never synthesize or mutate markdown body content
- broader relocation identity matching for purely manual/nested IDs that cannot be inferred from filename alone
- full freeform-boundary enforcement parity with PEP090 language for complex same-type directory ownership edge cases
- the shared containing-directive resolver (`MarkdownFileLocator.TryResolveDirectivePuckFromDirectory`, fanned out to `VaultWatcherPathPolicy` / `VaultPathSyncModelCatalog`) still loose-parses arbitrary dashed *filenames* in a folder as directive evidence. In the watcher pipeline this is a harmless over-approximation — the frontmatter-PUCK belonging gate and the FK-existence normalization catch non-entities downstream — but it is not PUCK-based the way the philosophy wants policy outside auto-assign roots to be. Tightening it (frontmatter-only, or directive-notation-gated) is a candidate follow-up; the consistency pass no longer relies on it for authority.

### 1.4 Message sheets and localisation
Operator-facing watcher and frontmatter-validation prose now lives on embedded resource sheets
(`core/Resources/WatcherMessages.resx`, `MarkdownMessages.resx`) behind typed `Pleiades.Resources.*` accessors, pinned by
`MessageSheetCatalogTests`. Localising is adding a `<Sheet>.<culture>.resx` beside the neutral one — nothing else changes.

Still needed / to decide:
- who sets the culture: the wire carries resolved text, not keys, in two halves — `WatcherIssueRecord.Message` (the
  reason's descriptor message, resolved per request, so it follows a culture change immediately) and `Detail` (the
  occurrence's specific text, baked at raise time in the daemon's `CurrentUICulture`, so an already-raised issue keeps
  its language until re-observed). A user-facing locale therefore needs a daemon-wide setting (user settings or
  `.plaintorch`) applied to the host's UI culture. Shipping keys + arguments for the detail too, and resolving
  client-side, is the alternative if per-client language ever matters.
- an Instance dismissal now fingerprints `OperationStatus.Fingerprint` — a structural, culture-invariant identity the
  reporter composes from facts — never the detail text, so localisation cannot lift or break a snooze. Rows persisted
  before this (which fingerprinted the message text) no longer match and their issues resurface once (re-dismiss);
  deliberately not shimmed: the dismissal core is domain-neutral and should not know the old composition.
- audit-log details (`VaultWatcherSyncService`'s `reason = …` entries) and the API services' `InvalidOperationException`
  texts are deliberately still literal English: they are logs / developer-facing, not the issue surface. Move them onto a
  sheet if a client ever renders them.

### 3.2 PEP091 implicit policy and PUCK storage
PUCK identity storage is now an explicit `VaultStorageAttribute.PuckStorage` policy (`Quiet` frontmatter identity by default, `Index` filename identity opt-in) that is fully decoupled from the storage mode. A new `Implicit` storage mode was added: it is identity-driven like freeform but withholds initial file materialization and only becomes deletion-authoritative once a `BoundaryBegin` audit entry marks that its file has begun existing.

Implemented direction:
- `MarkdownFrontMatterSerializer` and `MarkdownFileLocator` now branch on `PuckStorage` (quiet vs index) instead of `Mode == Freeform`
- `PolarisCycle`, `OnrushSprint`, and `LorePage` were recalibrated to `Index`; `Directive` and `Objective` are `Quiet`
- `Objective` moved from `Synced` to `Implicit`: creating an objective no longer writes a file, `POST /api/objectives/{id}/begin` (or a user-authored file with matching `puck` frontmatter) begins its boundary, and deleting the boundary-begun file removes the database row
- deletions of quiet title-only files recover identity from the `BoundaryBegin` entry's recorded vault-relative path, because the filename carries no identity
- the `AuditLogEntry.Action` column is now indexed for rapid boundary checks

Migration caveats to watch:
- pre-PEP091 objective files use the `{id} - {Title}.md` index form with no `puck` frontmatter; under implicit/quiet ownership they are no longer recognized as objectives (frontmatter identity is required), so legacy objective files must be re-materialized (`begin`) or given `puck` frontmatter to be picked up again
- implicit storage, like freeform, does not auto-create entities from title-only files that lack `puck` identity, which is a deliberate departure from the previous synced-objective behavior that adopted title-only pre-PUCK files
- boundary path recovery keys on the recorded vault-relative path; a rename immediately followed by deletion before rediscovery could miss the recovery until the boundary location is refreshed on next materialization

### 3.3 PEP092 vault migration system
The vault now versions its on-disk conventions (`.plaintorch:SchemaVersion`) and migrates them at startup alongside the database migration, through `Pleiades.Vault.Migration`. The model is load-then-re-canonicalise: `VaultLoader` reads the vault under the `VaultConventionSet` for the stored version, and each entity is re-emitted under the current conventions via `PlaintorchMarkdownStorageService.RecanonicalizeAsync`, preserving the markdown body. `VaultMigrationRunner` gates on the version, records `VaultMigrationHistory`, and snapshots legacy files to the graveyard for rollback. The first migration (v1→v2) backfills PEP091 objective files.

Implemented direction / deliberate refinements:
- Only the loader is convention-parameterised; the writer always emits current conventions because migrations only move forward. This avoided an invasive, regression-prone refactor of the whole `MarkdownFileLocator`/`MarkdownFrontMatterSerializer` write path.
- A migration declares the entity types it targets (scoping, not per-file diffing), keeping unrelated entities untouched.
- Rollback snapshots are taken as file *copies* into `graveyard/files/migration-v{from}-to-v{to}` before rewrite (the temporal service otherwise moves files, which would remove the source the re-canonicalise pass reads).
- Idempotency comes primarily from the version gate; a re-run also self-skips because already-converted files no longer resolve identity under the old conventions.

Still needed / known limitations:
- Filename-*separator* changes are not yet convention-aware (the loader's Index parse uses the current `PuckNamedIdentity.Separator`); a version that changes the separator needs a bespoke loader.
- Rollback snapshots copy single files; self-named-directory-shaped migrations would need to snapshot the whole directory.
- A migration that finishes with per-entity conflicts still advances the version (conflicts are audited but not retried); a stuck file needs manual attention rather than blocking all future migrations.
- No per-file dry-run yet; `VaultMigrationRunner.GetPendingPlan()` reports which migrations would run at the version level.
- Legacy objective files without resolvable v1 identity (title-only pre-PUCK drafts) are intentionally left untouched by the migration.

### 3.4 PEP093 test harness and dev-latch environment
The core now has an xUnit suite in `../core.tests` that drives the real DI graph over a fresh, isolated vault per test
(`TestVault` builds the host with `Install<PLAINTORCH>()` but never starts it, so the watcher/Kestrel stay dormant, and
behaviour is exercised deterministically through the discovery→decision→sync pipeline). This begins closing the
zero-test / weak-observability gap flagged as the core's biggest risk ahead of the planned dispatch-coupling refactors.

`serve` gained an isolated dev environment so tests and sandbox sessions no longer collide on, or pollute, the real
per-user socket/config/port: `--ephemeral` (random user-independent temp profile), socket-only by default with opt-in
`--loopback`, and — for an ordinary manual `serve` — a persistent per-user development sub-profile under
`~/.pleiades/plaintorch-dev`. A manual serve runs against that sub-profile (isolated from the real per-user profile, but
persistent rather than destroyed like the ephemeral one) instead of `~/.pleiades/plaintorch`, so a developer sandbox
never touches a real installed daemon and no separate OS account is required. `serve --daemon` opts a manual serve back
onto the real per-user profile for developers building their own background daemon; the installed service runner (and the
`bootstrap-service` assets it generates, which pass `--daemon`) always use the real profile.

Still needed / notes:
- Coverage today is a high-risk tranche (body preservation, implicit boundary, classification, migration round-trip,
  serializer round-trip, version store, file locator); the full surface and its status live in
  `_documents/Criteria - Validators, Checks & Unit Test.md`, which is the coverage backlog for future PEPs.
- Manual `serve` isolation is now a directory sub-profile rather than an OS-account relaunch, so it works uniformly in
  CI/sandbox without provisioning an account; the earlier `PLAINTORCHDEV` relaunch (and its in-tree dev password) has
  been retired, and the orphaned `DevUser/` setup scripts have been removed (2026-09-15).
- Tests are behaviour-focused (files + database + decisions) so they survive, rather than obstruct, the refactors.

### 3.5 PEP099 executive orders
Executive orders are implemented as a new `Synced`/single-file/`Index` entity partitioned under the owning
onrush sprint's `ExecutiveOrders` folder, with issue/list/update/delete API actions and SDK mirrors.

Deliberate interpretations of the proposal text:
- The PEP writes the notation as `x{?}-o{I:2}`, but incremental numerators are declared `{I:k:i}` in the
  implemented notation grammar, so the canonical declaration is `x{?}-o{I:2:1}` (seed 1 ⇒ first order `o01`).
- The PEP example (`Onrush x0180 -> E.O. x180-o01`) implies orders are numbered within their owning onrush, but
  incremental sequences were previously keyed globally per declaration. Incremental sequence keys are now
  prefix-scoped (declaration + already-rendered leading segments) for non-first segments, so each onrush numbers
  its own orders. First-segment counters keep their historical key, preserving existing sequences.
- The same example trims the numeric part's padding (`x0180` composes as `x180-...`), so the manual segment input
  is the tokenized numeric value of the owning onrush id, unpadded.
- `Summary`, `Effective From`, and `Effective Until` are listed as model fields without requiredness; they are
  implemented as optional, while `Title` and the owning sprint remain required. A populated effective window is
  validated (`from <= until`).
- Orders cannot be issued against the in-planning placeholder sprint (`Id == "0"`) because their PUCK embeds the
  owning onrush numeral, which the placeholder does not have yet; the sprint must be begun first.
- Because order identity is filename-embedded (`Index`) and requires caller input, title-only files inside an
  `ExecutiveOrders` partition surface as conflicts instead of auto-creating entities; files under unknown sprint
  directories are likewise flagged rather than adopted.

Open questions:
- whether orders should ever migrate with objectives when a planning placeholder sprint is begun
- whether an order's effective window should be validated against the owning sprint's start/end dates

### 3.6 PEP100 declarative ecosystem
Implemented as specified in the wrapped-up proposal, with these deliberate interpretations and open edges:

Deliberate interpretations:
- The PEP's "siblings sharing a base model with discriminators" is realized as EF TPH: `LunarDirective : Directive`
  (rather than renaming `Directive` to `StellarDirective` across the entire codebase), and
  `Objective`/`Fate`/`Decree` under a new abstract `Incentive`. The `Objectives` table was renamed to
  `Incentives` with data-preserving discriminator backfills.
- The Orbit engine now exists in core as `Pleiades.Orbits` — a statement-faithful C# port of
  `@pleiades/orbits` from the orbit-scheduler repository (fidelity-verified against the TypeScript engine:
  identical streams incl. seeded `{#n}` randoms, per-step snapshot resume, and cross-language snapshot
  handoffs). The port should eventually graduate into orbit-scheduler's empty `packages/dotnet`; until then
  the TS engine is the semantic source of truth.
- Resolution modes are used deliberately (see `core/Orbit/.GENESIS.md`): seeking resolution materializes
  instances for a beginning Polaris cycle and advances the persisted per-declarative `IncentiveOrbitScheduleState`;
  preview (non-seeking) resolution validates interaction with single — possibly future — occurrences. The
  future-instance problem is solved by identity: day-granular occurrence dates are the instance ids, so a
  previewed future instance is recognized (not duplicated) when seeking later reaches its date.
- Orbit validation is tiered per consumer: fate orbits only need to parse (any granularity; span-format
  `=<dur>` orbits supply the eventive length, so no duration override is needed); decree orbits must be
  granular but accept any granularity (sub-day → timed attentives, super-day → a period carried as the epoch
  `Duration`, spanning — and colliding with — multiple Polaris cycles); reflective schedules and timeframes are strict day
  granularity. Resolution calendars are modular, with one rule since PEP116: a declarative's explicit `Calendar`
  wins, otherwise the vault default (`AgendaPreferences.DefaultCalendar`, Pleiadean out of the box) applies, for
  fates, decrees and reflectives alike. The core pins a calendar itself in one case only: a one-off `Z{…}` fate
  is set to Gregorian, because its literal is authored in Gregorian. Timeframes have no calendar of their own and
  always read on the vault default. Orbit changes — through API or watcher file sync — reset the schedule state; a
  lazily recreated state re-anchors at first use, which re-phases interval schedules like `d%2`
  (acceptable until a ruling on anchor semantics).
- An occurrence's RECURRENCE-ID is one datetime (PEP111), so it cannot by itself tell an all-day slot from a
  timed slot at exactly 00:00. Where the owner has an orbit, the slot resolves through it (the orbit occurrence's
  granularity is authoritative); a slot known only by its moment treats midnight as all-day (`Epoch.FromSlot`).
  The attentive reward-ledger key keeps its pre-collapse text for all-day and non-midnight slots, but a timed
  attentive at 00:00 — previously keyed `…T00:00` — now keys as all-day. Decree orbits are overwhelmingly
  day-granular, so this is recorded rather than engineered around.
- Proximity has a background clock, which answers the former open question of who fires it between cycle
  begins. `RollingMaterializationService`, a hosted service, runs the harden-on-time pass
  (`ProximityMaterializationService.MaterializeForNowAsync`) 15 seconds after startup and then hourly. When time
  counts as an interaction (`MaterializationPolicyOptions.TimeIsInteraction`, on by default), the pass does three
  things:
  - it seeks orbit fates, and orbit decrees other than lunar reflect-decrees, through now, hardening the
    occurrences whose time has arrived;
  - it hardens the due objectives whose day has come;
  - it advances each schedule's cached next occurrence.

  Every occurrence still in the future stays a projection computed on read (`AgendaProjectionService`), and cycle
  begin hardens only the cycle-bound reflectives.
- Lunar reflection now generates reflectives: at cycle begin, an active lunar-hierarchy decree with
  `reflect: true` whose orbit day-matches the cycle's start day creates one cycle-bound reflective
  (description = decree title, decree provenance recorded). Source pools, weighting, cooldowns, and prompt
  synthesis remain PEP104.
- `EventiveResolution` has no "happened" member — passing is temporal, per the states clarification; pending
  occurrences simply pass.
- The reflective collection reward amount is a placeholder constant
  (`PlaintorchStatePolicyProcessor.ReflectiveCollectionReward = 10`) until a proposal pins the number.
- Fates and decrees now follow the objective vault policy (Implicit + quiet PUCK + `Fates/`/`Decrees/`
  roots and directive partitions), with begin-boundary endpoints and sibling-aware watcher candidate rules;
  identity-driven belonging disambiguates the three incentive kinds by their PUCK discriminators.
- Lunar directives inherit `Directive`'s freeform storage. Watcher hydration stays base-typed: file edits
  sync base fields, `lunarStatus` mutates through the API only, and unknown `LUNA` puck assertions follow
  the unknown-freeform-puck purge policy.
- Superseded by PEP111: there is no Polaris-bound attentive any more. Adding a decree to a cycle creates a
  decree-backed executive (`AddDecreeExecutiveAsync`), and every attentive is an unbound occurrence of its
  decree's schedule. The former question of moving an attentive from unbound to bound no longer arises.
- Objectives set parents through `ObjectiveUpdate` (not at creation); fates accept parents at both points.
- Directive and incentive JSON payloads now carry a `$type` discriminator (`stellar`/`lunar`,
  `objective`/`fate`/`decree`) so derived fields survive base-typed endpoints.

Patch100.2 (exclusive and active timeframes, availability, auto affinity): implemented direction and deliberate
readings.

Active timeframes and windows:
- **Timeframe windows wrap midnight.** This resolves the former open question. A window whose start is later than
  its end runs from its start, through midnight, to its end. A window whose start equals its end is never active.
  This is the client's former rule, now enforced by the core at `GET /api/timeframes/active`.
- **Affinity presentation is unchanged.** A chip still shows the window as authored. A cycle's candidate set is
  fixed for its life, so a cycle kept open past midnight keeps the timeframes of the day it began on, and an
  overnight window keeps showing on the far side of midnight.
- **Only a strictly active cycle has active timeframes.** That is a cycle that has started and not ended. Without
  one, nothing is active; the any-state "today's cycle" fallback other readers use does not apply here. The
  clock is the local wall clock at minute precision, applied to the timeframe's own start and end as well.
- **Which day and calendar.** The cycle's day is its local start day, the same day reflectives match against.
  Timeframe orbits read on the vault default calendar, since timeframes have no calendar of their own.
- **Exclusivity is judged among the timeframes active at that moment,** not among the whole day's candidates.
  An exclusive timeframe that is not active suppresses nothing, and several active exclusive ones are all
  returned. This is how the request's "if any of the matching timeframes is exclusive" was read. Judging it across
  the day's candidates would let a morning-only exclusive timeframe hide every other timeframe all day.
  Exclusivity does not touch auto-inclusion or affinity.
- **Active timeframes are evaluated on read.** No core timer computes them: the core computes the active set per
  request from the cycle's cached candidates. The chip asks again on the shared 60s tick, so it can trail a window
  edge by up to about a minute (accepted).

Candidate cache:
- **Warms are best effort.** The begin warm runs last: after the begin is committed, its note written and the
  begin audited. A failing warm therefore can no longer leave a begun cycle without its note or its audit entry.
  It and the vault-activation warm log any failure other than cancellation as a warning and swallow it, so
  neither a begin nor a vault activation fails over a cache. The lazy recompute on the next read covers a failed
  warm. Pinned by `A_failed_warm_never_fails_the_begin_or_the_vault_activation`.
- **A lost race pinning a lazy state is harmless.** The candidate computation saves any lazily created timeframe
  state. If a concurrent timeframe delete (foreign key) or orbit edit (unique timeframe index) makes that save
  fail, the lazy states are detached and a warning is logged. The candidates computed for that read still stand,
  and the next computation reads whatever state is stored by then. Pinned by
  `A_lost_race_pinning_a_lazy_state_still_yields_the_computed_candidates`, which forces the failure with a
  temporary SQLite trigger.
- **The default-calendar change invalidates twice.** This closes a race that was earlier recorded here as open. The
  save hook fires inside the save, before `UserPreferenceService` updates the in-memory store the options read, so the
  service now invalidates again after its store write for that key (`SetRawAsync`, `ResetAsync`) and after every
  `LoadAsync`. A recompute that read the old calendar between the two invalidations is handled in one of two ways:
  - if it has already stored its entry, the second invalidation drops that entry;
  - if it is still running when the second invalidation lands, the version check discards its result.

  `A_recompute_right_after_the_calendar_preference_call_sees_the_new_calendar` pins the first way only. Its racing
  recompute runs to completion from the save's `SavedChanges` event and stores the old-calendar set, and the store
  write's invalidation then leaves the cache empty. The version check is pinned only on the bare cache
  (`A_recompute_racing_an_invalidation_never_stores_its_stale_result`).
- **Both warms run in a child scope.** This closes an edge that was earlier recorded here as open. An options
  snapshot is fixed per scope. A begin's request scope may already have read the default calendar while
  materializing reflectives, and a calendar change may finish before the warm starts. A warm in that scope would
  pass the version check with the old calendar and stay cached until the next invalidation. The begin warm
  therefore resolves its candidate service from a fresh scope, as the vault-activation warm already did. The edge
  was found by reading the code, and the fix has no test, since it needs a calendar change to land in the middle of
  a begin.

Timeframe orbit state:
- **Timeframe orbit states copy the declarative reset policy.** Setting or changing an orbit re-anchors the
  state. Clearing the orbit removes it. A calendar change never resets it, so flipping the default calendar changes
  how a `w[d{…}]` orbit reads (Pleiadean weeks start on Saturday, Gregorian weeks on Monday), while an interval
  orbit keeps its phase.
- **A timeframe epoch reaches back to the open cycle.** A set or changed timeframe orbit is anchored at
  `FixedLiteralDate(orbit, timeframe calendar) ?? min(today, open cycle day)`:
  - a lone fixed `Z{…}` literal anchors at its own date, as a declarative's does. Its year, month and day are read
    on the timeframe calendar (the vault default, Pleiadean unless changed), the calendar the engine resolves the
    orbit on, so the epoch is the civil day of that calendar's date. A Pleiadean `Z{3/3/40}` is the 40th day of a
    61-day month, not an impossible Gregorian date;
  - a literal the calendar cannot hold (a day or month out of range) falls back to the rule below instead of
    failing the save. Before this, `FixedLiteralDate` built a Gregorian `DateOnly` from the raw numbers, so a
    Pleiadean-only day threw inside the save hook and the timeframe create or update failed, and an in-range
    Pleiadean literal got an epoch read as a Gregorian date;
  - any other orbit anchors at the earlier of today and the day (`TimeframeCandidateService.CycleDay`) of the
    cycle that has begun and not ended. A cycle begun, ended or deleted in the same save counts by its pending
    state. With no open cycle, the anchor is today.

  A declarative's recurring orbit still anchors at today. The difference exists because an orbit yields no
  occurrence before its epoch: anchored at today, an orbit set after midnight could never select a cycle begun the
  evening before and still open, which matches against its start day. A timeframe state is only previewed and never
  hardens occurrences, so anchoring it back costs no backfill. Pinned by
  `An_orbit_set_after_midnight_under_a_cycle_begun_yesterday_evening_anchors_on_the_cycle_day`, which asserts both
  the candidacy and the stored epochs. The literal reading is pinned by the `TimeframeOrbitStateTests` Pleiadean
  literal tests and by `OrbitDaysLiteralTests`.
- **The reach-back moves the phase of phase-bearing orbits.** "No backfill" does not mean "no effect". An orbit
  whose occurrences are counted from the epoch — an interval (`d%2`), a count limit (`*N`, `@N`) or a seeded random
  (`{#n}`) — takes its phase from the anchor. Set while an older cycle is still open, it counts from that cycle's day,
  not from the day it was set, however old the cycle is: a `d*3` set on the 25th under a cycle begun on the 11th
  spends its three days on the 11th to the 13th. This is the accepted trade-off of the rule: every orbit set under an
  open cycle must be evaluable on that cycle's day, and the open cycle's day is the product's logical day (cycles end
  only when the user ends them). Capping the reach-back (for example to one day) would reintroduce the bug for any
  cycle open two days or more. A stale open cycle is the root cause, and no single anchor serves both it and the
  next cycle.
- **A backdated begin still misses a later anchor.** The rule helps only an orbit set while its cycle is open. An
  orbit set with no cycle open anchors at today. A cycle begun afterwards with a start on an earlier day (an
  explicit earlier start time, or a note whose start is written on an earlier day) matches against a day before that
  epoch, so the timeframe is not its candidate. `A_cycle_begun_yesterday_evening_keeps_its_start_day_past_midnight`
  is the one test that re-anchors states by hand (`AnchorTimeframeStatesBeforeAsync`). It needs orbits set on a day
  before a backdated begin, which a test running within one day cannot produce through the product. The other
  candidate tests assert against the states the product creates.
- **Legacy timeframes get a state lazily.** A timeframe with an orbit but no state, from before states existed, gets
  one on first evaluation, anchored like the incentive lazy path (the day being read if it is past, else today). The
  candidate computation saves it so the anchor and seed are pinned.
- **The state-table Down cannot keep timeframe states.** The old table is keyed by incentive, so the hierarchy
  migration's Down deletes them rather than failing.

Availability:
- **The nearest directive wins.** The walk starts at the owning incentive's directive and climbs
  `ParentDirectiveId`, stopping at a repeat in a hand-edited loop. It never follows `ParentIncentiveId`. The owning
  lunar directive's moonlight status is ignored, as it is for college.
- **Any Availability timeframe may be picked.** A directive may choose an Availability-mode timeframe of any lunar
  directive, not only one in its own lineage. Availability timeframes still appear in the active set and can
  still be picked as manual affinities.
- **Availability beats College, and seeds only at creation.** Changing an availability never re-affines existing
  workitems. Cycle-begin reflectives go through the same combined resolver as executives. Attentives are never
  auto-seeded, because since PEP111 adding a decree to a cycle creates an executive instead.
- **Availability is database-only.** It is not frontmatter, and the watcher restores it on every note sync.
- **References are cleared on the way out, on every pathway.** The directives that name a timeframe are cleared,
  tracked, in the same save, so the change feed sees them, in three cases:
  - the timeframe leaves Availability mode;
  - the timeframe is deleted;
  - its lunar directive is deleted. The database cascade removes that directive's timeframes out of EF's sight, so
    their ids are read from the store before the save.

  The clear is a state-policy rule, the first one the save hook runs
  (`PlaintorchStatePolicyProcessor.ClearStaleAvailabilityReferencesAsync`). So the API, the CLI, the watcher's
  delete-from-database action and a bare context save all get it, and the directive API no longer clears anything
  itself. The change-feed interceptor is registered after the state policy, so it announces the cleared
  directives. The set-null foreign key stays only as a database-level backstop for a write that bypasses EF. The
  resolver also ignores any availability that does not point at an Availability-mode timeframe.
- **The watcher does not remove a directive whose note is deleted.** This is older than this patch; it was found
  while testing the watcher pathway above. The Freeform mode means to remove a known entity whose file is deleted,
  but a deleted file reaches it with no id here. Directive notes use Quiet PUCK storage, so the id lived only in the
  deleted file's frontmatter. Discovery recovers a deleted file's id only from an Index filename or from an Implicit
  boundary entry, and neither applies. The mode therefore decides `Ignore`, and the startup orphan pass, which walks
  only Implicit boundaries, misses it too. The directive stays in the database. This was observed for a lunar
  directive's note, and by reading, a stellar directive's note takes the same path. The watcher-pathway availability
  test therefore hands the watcher's own delete action the directive's id, as an identity-bearing removal would
  reach it. If the watcher ever removes such a directive, the save hook already clears the availabilities.
- **The resolver is memoized per scope.** It reads the directive lineage projection and the Availability-mode
  timeframe ids once per scope, and drops them after any save through that scope. A cycle begin with many
  reflect-decrees therefore no longer reads the whole directive table for each decree. The college lookup still
  runs for each resolution.

Creation affinity:
- **It is tri-state on the wire** (`Optional<long?>` on `PolarisExecutivePlan` and `PolarisDecreeAdd`):
  - an omitted key is Auto;
  - `null` is an explicit none;
  - an id must exist, and an unknown one is refused before any side effect.

  Under Auto, a one-shot executive gets none, since it has no incentive to resolve from. Before this patch,
  `PolarisDecreeAdd`'s `null` meant auto, and an explicit none at creation was not possible.
- **The editor sets the mode on its own.** Saving an inclusion mode sends only the mode, because colleges sent
  alongside would be re-applied. The college list saves on its own too, so emptying it now leaves the timeframe in
  College mode, matching nothing, instead of dropping it to None.

Tests:
- **Wire shapes are pinned; the routes are not.** `TimeframeWireContractTests` serializes and deserializes with the
  host's own settings: `PlaintorchHostFactory.ConfigureSerializer` applied to the ASP.NET web defaults, as the host
  applies it. It pins these shapes:
  - `exclusive` and the numeric `autoInclusion` (Availability is 2) on timeframes and timeframe records;
  - `availabilityTimeframeId` on both directive kinds through the polymorphic base;
  - the tri-state creation affinity on both create contracts;
  - the availability request;
  - `TimeframeUpdate.exclusive`.

  `GET /api/timeframes/active` and `PUT /api/directives/{id}/availability` are still covered only through the
  services, and nothing drives them over HTTP. That leaves three things untested:
  - the route bindings;
  - the icon media enrichment on the active listing;
  - an empty `{}` availability body, which binds a `null` id and so clears.

  Like the other `/api/timeframes` routes, they are held over until core.tests has an in-process HTTP harness.

Patch100.3 (the timeframe flare): client-only, deliberate readings.
- **A flare mirrors the core's active listing exactly.** An executive or reflective row flares while its affinity
  timeframe is among the timeframes `GET /api/timeframes/active` returns. So a row affined to a timeframe hidden
  behind an active exclusive one does not flare, and neither does a done row or one without an affinity. The heading
  chips and the rows read one shared SDK record (`repos.activeTimeframes`), so they cannot disagree. They re-read it
  together on the 60s tick, which costs one coalesced request, and on any change the client hears of.
- **Reflective rows flare; their group does not.** The Daily Reflectives group is collapsed by default, so an
  active reflective's flare shows only once the group is opened. This was the user's call.
- **The `--flare-intensity` registration was invalid until now.** Its `@property` rule lacked the required `inherits`
  descriptor, so every host dropped it, and the property never interpolated. It now inherits, which the flare's
  pseudo-elements rely on.
- **Verified in a browser harness only.** The real Polaris card, with its executive and reflective rows, ran against a
  fake core transport. That covered which rows flare, the single shared request, the ignition and fade transitions,
  and the glint. It has not been seen against a live core.

Open questions:
- whether a re-anchored (lazily recreated) orbit state should preserve the original epoch instead of
  re-phasing from first use. This now also covers a legacy timeframe's lazily created state, which anchors at its
  first evaluation.
- whether fate `Opt-out` should be occurrence-scoped rather than declarative-scoped
- whether due-date eventives should auto-move when the objective's due date changes
- whether a change to a directive's availability, or to a timeframe's colleges or mode, should ever re-resolve
  existing workitems. If so, a manual affinity would have to be told apart from an auto-seeded one, which nothing
  records today.
- whether availability should also reach an incentive through its parent incentive, for example a subtask filed
  under a different directive than its parent objective
- whether a directive's availability picker should be narrowed to its own lineage's lunar directives
- whether the active timeframes should be pushed (a window-edge event or a change-feed signal) instead of polled on
  the 60s tick. The flare on executive and reflective rows (Patch100.3) now trails a window edge by the same minute.
- whether a directive should be served with its `availabilityTimeframe` navigation, or a lighter lookup should
  exist. While an availability is set, the directive banner fetches the whole timeframe listing to resolve one
  chip; a banner without one, such as most of Obsidian's inline note banners, makes no request. It refetches only
  when the availability id changes, so a rename or re-icon of that timeframe made elsewhere keeps the old face
  until then or until the banner is rebuilt. Nothing polls or retries. A failed read looks like a dangling id,
  because the SDK resolves a transport or HTTP failure as an empty listing, so either way the chip reads
  "No Availability" until the id changes or the banner is rebuilt.
- whether a cycle begun with a start on an earlier day than a timeframe orbit's anchor should reach back to it, for
  example by re-anchoring such states at the begin, which would re-phase an interval or random orbit
- whether the watcher should remove a directive whose Quiet note is deleted. That needs the deleted file's
  identity from somewhere other than its frontmatter, such as a path recorded per note, the way an Implicit
  boundary entry records one.
- whether a declarative's `Z{…}` literal should be read on its own resolver calendar. Only the timeframe reset reads
  the literal on its calendar; the declarative reset still reads it as Gregorian, which is right for a fate (one-off
  fates are pinned to Gregorian, PEP111) but not for a decree resolving on the Pleiadean calendar. Such a decree's
  literal gets a Gregorian-read epoch: an in-range Pleiadean date such as `Z{3/3/10}` anchors in the Gregorian year
  3, and a Pleiadean-only day such as `Z{3/3/40}` (no Gregorian date) now falls back to today, where it used to
  throw. In that fallback, a literal date already past is missed by the seek. This edge predates Patch100.2 and is
  left as is.

### 3.7 PEP097 filename character filter
Entity names allow any character but a line break, yet they are synced to filenames, where a subset break the filesystem (`/  : * ? " < > |`) or Obsidian indexing (`[ ] ^ #`). `PuckFileNameCodec` (`core/Puck`) encodes those to reversible Unicode look-alikes at the single title→filename write chokepoint (`PuckNamedIdentity.FormatFileName`/`FormatTitleOnlyFileName`, replacing the old lossy `_` sanitiser) and decodes them at the filename→title read chokepoints (`ParsePath`/`ParseLoosePath`/`DecodeFileName`, `VaultStoragePathComposer.ReadFilenameIdentity`, and the two direct directory-name readers). The pure value parsers (`Parse`/`ParseLoose`/`TryParse`) and the display `Format` stay filter-free.

Implemented direction / deliberate bounds:
- The database and frontmatter always carry the real title; only the on-disk filename carries look-alikes. Encode/decode are exact inverses (pinned by `FilenameCodecTests`), so write→scan→read round-trips a forbidden-character title without churn (pinned end-to-end by `FilenameConstraintTests`).
- Media upload names (`VaultMediaService`) are out of scope: they are arbitrary user binaries behind a validation/whitelist boundary, not entity names that must round-trip.
- Accepted ambiguity: a user typing a look-alike by hand decodes to its plain counterpart. Characters outside the 13-entry set (including control characters) are left as-is rather than made irreversible, so the old `_`-for-any-invalid-char safety net no longer fires for exotic control characters (not a realistic entity-title case, and they would already break YAML frontmatter).

### 13. Transitory task modeling
Open blueprint question:
- should transitory tasks become thematic/unending objectives, standalone executives, or a hybrid?

Analytic view:
- transitory tasks are usually operational occurrences, not enduring intent objects
- `Objective` should stay the durable commitment layer because it carries strategic identity, onrush assignment, college, and reward value
- `Executive` should stay the cycle-scoped execution layer because it describes concrete work performed within a Polaris cycle

Recommended direction:
- use a hybrid model
  - thematic or unending work should live as durable `Objective` records
  - individual transient acts should usually be represented as `Executive` records, optionally linked to those objectives
  - allow objective-less standalone executives for one-off chores, interruptions, or ephemeral operational work that should not pollute the long-lived objective backlog

Why this is the cleanest fit:
- it preserves backlog hygiene by not forcing every fleeting action into the strategic objective layer
- it preserves cycle history by keeping actual performed work attached to Polaris cycles
- it avoids turning executives into pseudo-objectives with long-lived meaning they were not designed to hold
- it gives later analytics a useful split between intent (`Objective`) and execution (`Executive`)

Practical implication for future implementation:
- if standalone executives are adopted, the `Plan Executive` flow should remain capable of creating an execution record without creating or linking an objective
- recurring thematic work is modeled as a decree with many attentives over time, which is more analytically stable than proliferating duplicate objectives

Current implementation:
- `Objective` carries no enduring/repeating flag (removed once decrees and their attentives covered recurring commitment in full, allocations and affinity included)
- `Executive` can now carry its own optional title and exist without a linked objective
- the Polaris executive planning surface now supports one-shot executive creation directly

Remaining nuance:
- it is still undecided whether one-shot executives should ever produce Celestron value directly or whether rewards should remain objective-derived only

  untouched (turning those predicates into strategy-owned candidate enumeration rides phase 3's registry
  projection). The `DirectiveInitAndResolutionTests` pin is now a positive assertion.

Refactor phases 0–1 (entity model catalog + gateway) are done: the resolution/watcher/known-id/clone glue now
runs declaration-driven through `VaultEntityModelCatalog` + `VaultEntityGateway` (see Vault genesis). The full
phase plan, test gates, parked items, and decision log live in `_documents/REFACTOR Alpha.md`. Decisions
taken with the operator: base-declaration (`A{S:6}`) lookups query the whole directive family, trusting PUCK
tokenization instead of a defensive stellar-only filter (no per-entry resolution-scope hook introduced yet —
hooks arrive when a real special behaviour needs one); previous-state snapshots cover *all* mapped scalars and
owned references rather than hand-picked field lists. Remaining hardcoded-by-design: `SystemApiService`'s
per-type path→identity fallbacks (genuinely type-specific behaviour) and `MarkdownFileLocator`'s per-shape
composition (phase 2 target).

## Frontend Repository System (PEP106)

The frontend now resolves entities through an identity map and repositories in `sdk.ts/plaintorch/repository`
(see the SDK genesis). Verified by typecheck, build, the core test suite, and SDK harnesses driving the real
client through a stub transport. Open / deliberately bounded:

- **No TypeScript test runner exists.** The store, repository, invalidation and change-feed semantics were
  developed against throwaway harnesses that each caught a real defect (sparse-payload merges overwriting
  cached fields with class defaults; an echo-suppression window measured at the wrong point). Nothing in
  `sdk.ts` or `obsidian` runs on CI, so those guarantees are currently unpinned. Adding a runner and
  landing those harnesses as real tests is the obvious follow-up.
- **Loading and error states are available but not surfaced.** `EntityRef`/`DerivedRef` expose `loading` and
  `error`; banners still render blank while resolving, and a failed resolution looks the same as a missing
  entity. Deliberately left alone rather than inventing visual treatment — this is the remaining half of the
  "global loading mechanism" task.
- **Note and PUCK resolutions are not invalidated by entity writes.** A rename moves a note, so a path-keyed
  resolution can go stale; banners refresh the specific resolution they care about after a title edit, but
  there is no general rule. Invalidating all resolutions on every entity write was judged more churn than the
  case is worth until it demonstrably bites.
- **Polymorphic principals in change-feed owner mapping.** A child record's owner is announced under the
  declared principal type. `Directive`/`LunarDirective` are the only polymorphic pair, and no child record
  has a directive foreign key, so the ambiguity does not currently arise; the client's dependency table
  invalidates both directive keys anyway. Worth remembering if a child record ever gains one.
- **A successful write revalidates its own entity.** Redundant when the response already carried the entity,
  necessary when it returned only a boolean. Kept uniform rather than conditional; it is one request, gated
  on the entity being observed.
- **`ReferenceHandler.IgnoreCycles` poisons nested collections, and absorption amplified it.** The core
  serializes with `IgnoreCycles` (`Program.cs`), which writes `null` wherever an object would recur within
  itself. `GET /api/objectives/{id}` does `.Include(o => o.OnrushSprint)`, EF fixup wires the inverse
  navigation, and the response therefore carries `onrushSprint.objectives: [null]` — the hole being the
  objective that was asked for. Merging that faithfully both handed consumers a hole to iterate and emptied
  the canonical sprint every other surface was reading. The reviver now repairs such an array for the
  instance it is constructing and omits its key from the payload keys, reusing the sparse-response mechanism
  so a truncated collection can never overwrite a properly loaded one. This was latent until the dependency
  edge announcement (Patch102.1) started causing objective refetches while a sprint was on screen.
  Harness-verified — the scenario, worth re-creating if a runner ever lands: absorb a sprint with two
  objectives, then absorb one of those objectives carrying `onrushSprint.objectives: [null]`, and assert the
  canonical collection is intact, hole-free, and still overwritable by a genuine update (including a genuine
  empty).
- **A resync burst against the named pipe surfaced as `read EPIPE`, and the database made it worse.** The
  repo answers a write by resyncing — a change-feed event invalidates records and fires the reads a client
  needs to catch up — so a single dependency edge fans out into a small burst of concurrent requests over the
  one pipe, landing exactly while the `DependencyReconciler` holds SQLite's write lock through its fixpoint.
  Three things compounded, fixed together:
  - *SQLite had no concurrency configuration at all.* `UseSqlite` with a bare `Data Source` means the default
    rollback journal (whole-file write lock) and `busy_timeout = 0` (a reader meeting that lock fails at once
    rather than waiting). `SqlitePragmaConnectionInterceptor` now sets `journal_mode = WAL` and
    `busy_timeout = 5000` on every opened connection, so reads proceed alongside the single writer and the
    brief remaining contention waits. This is the root fix; the transport changes only shape the burst.
  - *The transport churned connections.* An earlier attempt set `agent: false`, which sends `Connection:
    close` and so tears down and rebuilds a pipe connection for every request — a burst then races the
    server's pool of pipe instances, which is itself a `read EPIPE` source. `send` now uses a bounded
    keep-alive `Agent` (`maxSockets: 8`): connections are reused, and a burst past the cap queues rather than
    opening an unbounded number of pipes at once. The long-lived feed keeps its own dedicated connection.
  - *The canvas observed both onrush sprints at all times*, so it fetched and revalidated the one it was not
    showing. Each sprint `DerivedRef` is now gated to its mode, halving the onrush traffic in the burst.
  Note the interaction with the edge-endpoint announcement above: because an edge announces *both* endpoints,
  one edge write produces two change events, hence two resync passes — which is what turned a latent fragility
  into a routine error once the canvas started writing edges.
- **`null` for an absent optional broke edge identity, so edges reached the client but never drew.** The API
  sets no `DefaultIgnoreCondition`, so an absent `DateOnly?`/`TimeOnly?` is written as `null`, not omitted. A
  dependency endpoint therefore arrives with `recurrenceDate: null`, while a node the canvas builds from an
  objective has the field missing (`undefined`). `endpointKey` — the identity both are matched on — guarded
  the no-recurrence case with `=== undefined`, so the two spellings of the same endpoint produced different
  keys (`Objective:j1` vs `Objective:j1@Tnull`), and `resolveEdges` dropped every edge as connecting nodes
  that, by key, did not exist: nodes rendered, edges silently did not. `endpointKey`, `sourceRef` and
  `targetRef` now treat null and undefined alike. This is the same wire hazard as the cycle-truncation and
  sprint-collection cases above — the core writes `null` where the client assumes `undefined` — and is worth
  watching at every boundary that keys or compares an optional field. Harness-verified against the reported
  symptom: a sprint of two objectives plus one dependency carrying null recurrence fields resolves to exactly
  one edge with the fix and zero without it.

## Dependency Graph Editor (Patch102.1)

The onrush context of the dependency canvas is implemented: an interactive graph where drawing
between two nodes creates the dependency and adding or removing a node is a membership of the sprint. Nodes
derive from `EntityItem`, placement comes from dagre behind `graphLayout.ts`, and the surface appears both as
the briefing's `planning` tab and as its own leaf.

Found while building it, and worth recording:

- **Dependency edges were invisible to the change feed.** `PlaintorchChangeFeedInterceptor.Collect` announces
  an entry either because it is `IPuckNamedEntity` or through the foreign keys `OwnersOf` walks. A
  `Dependency` is neither — no PUCK, and no foreign keys by deliberate design — so creating or deleting one
  broadcast nothing, and a second client never learned of it. Now special-cased to announce both endpoints.
- **There is no `PUT /api/dependencies/{id}`.** Trigger and constraint can only be changed by deleting the
  edge and creating a replacement, which is not atomic: the canvas restores the original if the recreate is
  refused, but a real endpoint would remove the window entirely.
- **A rejected write is silent.** The node transport resolves a failed request to `undefined`, so a cycle the
  core refused looks exactly like success unless the call site checks. The canvas pre-checks the two
  refusals it can (a loop, a duplicate edge) so the gesture is answered where it happened, and reports
  anything else through a notice. This is a general hazard for every new call site, not a canvas one.
- **Checkpoints were not tracked frontend-side.** `Checkpoint` is a `PuckNamedEntity` and was already
  announced by the feed, but was missing from `entityTypeNames`, so nothing absorbed it. Added, with a
  repository beside it.

Still open:
- The directive-focus context, with editable parent-child edges, is deliberately blocked on PEP103, which
  owns the gating and automation logic that parent-child relationships fall under. The endpoints exist; the
  governance does not.
- The freeform context needs somewhere to persist the curated node set — plugin `saveData()` or per-leaf
  view state. The plugin uses neither today.
- Node sizes are fixed rather than measured, and eventive endpoints are excluded from the onrush context
  because their id names the owner under a different kind.

## Graph usability and milestone binding (Patch102.2 / 102.3)

Second and third passes on the canvas; the full write-up is in the PEP, the decisions worth recording here:

- **Milestone lifecycle across the placeholder onrush.** An onrush comes to exist three ways — planned (the
  `id 0` placeholder), started new, or begun (which materialises the placeholder into a real row and removes
  it). The milestone (`OnrushSprint.MilestoneCheckpointId`, an optional 1:1) is attached on every creating
  path, and on begin the placeholder's milestone and tracked checkpoints are re-pointed to the real sprint
  before the placeholder row is removed, so the sprint keeps the milestone it planned with. Two relationships
  run between `OnrushSprint` and `Checkpoint` — the 1:1 milestone and the 1:many tracked set — configured
  explicitly (distinct FKs, `SetNull` both ways) so neither cascades and EF does not conflate them.
- **Uniqueness cannot live in the index alone.** The rule is one edge per source-target-*resolved*-trigger-
  constraint, but SQLite treats each null as distinct, so a duplicate with a defaulted (null) trigger slips a
  raw-column unique index. `DependencyRules` compares the resolved values and is the authority; the compound
  index is a backstop for the non-null case. Pinned by a test that a defaulted edge and an explicit
  finish-triggered one collide.
- **Layout is UI state, kept out of the vault.** `OnrushSprint.GraphLayout` is a database-only JSON column,
  written through a dedicated endpoint that skips the markdown rewrite and the audit log — it changes on every
  drag and the vault should never see it. Keyed by node key, so membership changes re-place only what is new.
- **A checkpoint's empty sides are a rule, not a default.** A checkpoint endpoint must carry no trigger
  (source) or constraint (target); the canvas routes every create and reshape through one path that nulls the
  checkpoint side, and the edge menu withholds those options, so the validator is never handed an edge it
  would reject for that reason.

- **Logical possibility replaced acyclicity, and it runs on the connection, not the query pipeline.** The
  operator supplied a recursive-CTE probe: does the new edge (asserting `source.trigger` before
  `target.constraint`) contradict the ordering the graph already imposes, checked by walking a two-sided
  begin/finish state graph forward from the target and seeing whether the source's triggering state is
  reachable. It is *temporal-cycle* detection, strictly finer than the node-level `EnsureNoCycle` it replaced
  — a node cycle whose begin/finish orders out (A.begin → B.begin → A.finish) is orderable and now allowed,
  where the coarse check forbade it. Keeping both would have made the probe pointless (a temporal
  contradiction is always a node cycle, so `EnsureNoCycle` dominates), so `EnsureNoCycle` was removed and the
  probe is the sole cycle rule. Two adaptations to this schema: trigger/constraint are stored as text on
  different vocabularies, normalised to a shared begin=0/finish=1 axis (omitted trigger → finish, omitted
  constraint → begin) with null for a checkpoint's absent side; and it is executed as a raw `DbCommand`
  because EF's `SqlQueryRaw` wraps a statement as a subquery, which a top-level `WITH RECURSIVE` cannot be.
  Checkpoints fall out on their own — a null side never matches the join or the begin→finish step — which is
  the operator's intended handling. Pinned by tests that an orderable begin/finish cycle is accepted, an
  unorderable one and a plain default cycle rejected, and a checkpoint chain untroubled.
- The composite-endpoint key the probe joins on is built by string-concatenating the stored columns, so an
  eventive endpoint's recurrence date/time must serialise identically as a bound parameter and as a stored
  column. They share Microsoft.Data.Sqlite's text form, so they match; worth remembering if that ever drifts.

Still open:
- Removing a *tracked* checkpoint from an onrush is a delete, not a detach — there is no endpoint to null a
  checkpoint's `OnrushSprintId` while keeping the checkpoint, so the node menu offers "Delete checkpoint"
  where an objective offers "Remove from Onrush". A detach endpoint would restore the parity.

## Desktop shell and hosting refactor (2026-09-15)

The end-game entry points are: (1) the raw console daemon for dedicated servers and development, (2) the Obsidian
plugin, (3) a desktop app that is a standalone version of the plugin and more, and (4) a per-user desktop background
app hosting the core with status and basic settings. (3) and (4) are one Electron codebase under `../standalone` with
two build flavours: **standalone** bundles and spawns the published core, **client** ships none and attaches to
whatever core answers on the profile's pipe or socket. Electron.NET was considered and rejected: package (3) must
work against an external core, so every status and setting has to be reachable through the API or the shared
`config.json` anyway, which leaves in-process DI with nothing to offer but a second main-process implementation.

What changed in the core to make that possible:
- The composition root left `Program` (`PlaintorchHostFactory`), so a shell, the CLI, and the tests build the same graph.
- The PowerShell splash was replaced by `PlaintorchHostState`, surfaced on `/healthz` and, in spawn mode, streamed to
  stdout as JSON lines. Shared memory was considered for the loading state and rejected: Node has no cross-process
  shared memory without a native addon, and the child's stdio already gives ordered events plus exit-as-crash-signal.
- Spawn mode stops gracefully on stdin end-of-file, because a Node `kill()` on Windows is a hard terminate.
- Daemon and spawn modes log to daily files under the profile; spawn mode logs nowhere else, so stdout stays clean.
- A single-instance probe over the profile's own transport replaces a raw bind failure.
- The Windows machine service (LocalSystem, hence the wrong "per-user" profile and an unreachable pipe) is gone; the
  systemd user unit stays for headless Linux. Per-user autostart is the shell's job.
- `config.json` is written atomically by both writers and the core preserves keys it does not model.

Still open:
- The Obsidian components import the Node SDK client directly (`core` from `@pleiades/sdk/plaintorch/node`), so reusing
  them in the sandboxed renderer of the desktop app needs either a bridge-backed client injected where that singleton
  is, or a node-enabled renderer like Obsidian's. The status window uses its own small lit components for now.
- Beyond the SDK-client coupling, some Obsidian components carry Obsidian-runtime dependencies (notably modals) that
  simply do not exist in the Electron renderer and would fail at runtime, which is why the main frontend is not being
  brought over yet. The desktop status window deliberately uses its own small lit components and only the data-level
  SDK (e.g. the system briefing), not the Obsidian component library.
- `@a11d/lit` reactive properties depend on legacy-decorator accessor semantics, so the shell's esbuild build and its
  tsconfig both pin `useDefineForClassFields: false` (target es2022 would otherwise default it on and silently break
  reactivity — the window renders once, then never updates). The Obsidian plugin avoids this only by targeting es2021.
- The shell's SDK bridge implements `send` only; the change feed (`stream`) is not bridged, so the renderer revalidates
  on its own schedule.
- Installer signing/notarization, real icons, and the update host are placeholders in `../installer`.
- Windows notifications from the shell need an AppUserModelID shortcut for unpackaged runs; not wired yet.

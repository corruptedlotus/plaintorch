# PLAINTORCH Genesis Log

## Rules of Engagement
This part is written by Susu, the original creator. Machines and humans who are contributing to this project please make sure you follow these simple conventions while working on the project:
- Make sure you add XML documentation (and other forms of in-code documentation for other languages) to keep the components of the system identifiable and clarified.
- Check the latest .OPERATION file in root for the current project heading objectives. If you complete any of those objectives, mark them.
- Check .ORIGIN for the ideas behind the project.
- Keep .GENESIS files in every domain updated with information on what has been developed in there, what they do, and briefly on how they work.
- Update the root .DISCUSSION file to include your concerns, uncertainties and requirements for the project. Remove them when they're no longer relevant.
- DO NOT, I repeat, do not run `serve` with project root as a vault. Use `./_sandbox` as your test vault.

## Purpose
Initial foundation for PLAINTORCH based on the blueprint in the introduction document, with an Obsidian-vault-first layout and managed SQLite persistence.

## Current Architectural Direction
- Obsidian vault is the filesystem source for human-authored content.
- SQLite inside the vault is the structured source for indexed state and relations.
- EF Core is now the sole persistence access layer; direct SQLite command usage has been removed from application services.
- The application shell now composes its DI graph through A11d modules instead of wiring each service directly in `Program`.
- Markdown files are generated in an Obsidian-friendly layout.
- Source layout is domain-driven rather than split by technical categories.
- `Operations` has been folded into `Orchestration` to keep work-execution concepts in a single domain.
- Objective colleges now align with the updated action-college list: `Swords`, `Creation`, `Lore`, `Eloquence`, `Glamour`.
- Tags can now be defined ahead of time through `TagDefinition`, with semantic palette names stored separately from eventual UI colour values.
- Table and column names now rely on EF Core conventions instead of explicit overrides, keeping the schema aligned with CLR `PascalCase` names unless conventions require otherwise.
- XML documentation comments are being added across the created code surface so the domain model and infrastructure APIs remain self-describing.
- Current implementation prioritizes bootstrap, persistence, and identity scaffolding.
- User-level host state is now beginning to form around active-vault selection and future socket placement.
- The next transport/runtime work can now target a stable implemented application layer instead of inventing ad hoc command shapes.
- Sync model detection is now explicitly path-only, and file sync policy is driven by `VaultStorageAttribute.Mode` rather than inferred from CLR type usage sites.

## Intentional Scope Limits For This Pass
The following were not fully implemented in this pass because the blueprint does not yet define enough behavior:
- full reconciliation execution from discovered file changes into the database and back
- final file deletion monitoring and recreation rules for relation-protected entities
- lore entity CLR models and PUCK reverse parsing from nested lore files
- reflective generation engine
- celestron ledger ducking logic
- `.puck` declaration file loading
- full CRUD/query CLI client transport

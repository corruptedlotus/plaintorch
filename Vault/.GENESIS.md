# Vault Genesis

## Purpose
The `Pleiades.Vault` domain bridges the application to the Obsidian vault and the SQLite database inside it.

## Subdomains
- `Pleiades.Vault`: vault-level settings, layout, and bootstrap operations
- `Pleiades.Vault.Markdown`: markdown metadata, frontmatter serialization, and file location rules
- `Pleiades.Vault.Database`: EF Core context, initialization, and repository access

## Main Parts
- `VaultOptions`: vault-level configuration
- `VaultLayout`: canonical filesystem paths
- `VaultStorageAttribute`: per-type file-backing policy, shape, and dynamic parent composition metadata
- `MarkdownFieldAttribute`: marks properties that should be reflected into markdown
- `MarkdownFrontMatterSerializer`: writes YAML frontmatter for markdown-backed entities and validates/reads typed frontmatter back into CLR models
- `MarkdownFileLocator`: computes canonical markdown file paths and reconstructs path-derived hierarchy
- `LoreIndexer`: scans saga markdown files and stores a lightweight lore chronology index
- `PlainfraContext`: EF Core context for the vault database
- `PlainfraContextFactory`: creates design-time EF contexts for migrations
- `PlainfraContextInitializer`: applies migrations at startup
- `PlaintorchRepository`: application-facing persistence operations
- `VaultBootstrapper`: ensures required directories and database bootstrap
- `VaultTemporalDataService`: archives deleted entities and files into graveyards
- `VaultAuditLogService`: records soft-reference audit entries for application, discovery, and sync activity
- `VaultStorageTopologyValidator`: rejects ambiguous shared-root file-storage layouts before activation
- `VaultPathSyncModelCatalog`: path-only sync model catalog for watcher/discovery logic
- `VaultMarkdownDiscoveryService`: startup and on-change markdown discovery, validation, and candidate construction
- `VaultWatcherService`: debounced filesystem watcher host for vault-backed markdown

## How It Works
- The vault root is resolved from options
- The `.plaintorch` file stores vault-local PLAINTORCH settings, including logical location key overrides
- The `.plaintorch-data` metadata folder contains the SQLite database by default
- The `.plaintorch-data/graveyard/files` tree preserves archived file-backed data after deletion while database tables preserve temporal metadata and serialized entity snapshots
- EF Core maps the current CLR model set into that database and now initializes it through migrations
- Only types explicitly marked with `VaultStorageAttribute` receive markdown file backing; all other types are database-only by default
- File-backed types now declare an explicit storage shape so self-named markdown directories and single-file entities can coexist safely under watcher roots
- Dynamic parent composition is now supported for file-backed entities such as nested directives and directive-contained objectives
- PUCK-backed markdown filenames use the `{Puck token} - {Title}` convention so identity can be inferred from the path without duplicating `id` and `title` in frontmatter
- Path-derived relations are mirrored into frontmatter for readability, but discovery and sync treat the path as authoritative
- Saga lore remains file-first, but a lightweight database index is rebuilt from canonical saga markdown paths so chronology can be queried without moving lore authority out of the vault files
- The vault root is now protected by `.plaintorch.lock` while the active service instance owns it
- The watcher/discovery layer now scans the configured vault roots, resolves candidate model type from path only, validates frontmatter into CLR models, and emits provisional sync decisions while suppressing service-originated write loops

## EF Mapping Approach
- Table and column naming now mostly follows EF Core conventions, so the physical schema defaults to implicit `PascalCase` names
- `PlainfraContext` is kept for the pieces annotations do not express well: enum conversions and JSON conversion for directive tags
- Predefined tag metadata lives in `TagDefinitions`, while directives keep only assigned tag ids in their tag list
- Lore indexing stores only lightweight references and extracted chronology tokens, not canonical lore body content
- Audit and graveyard tables intentionally use soft references and standalone archival keys so temporal history survives duplicate lifecycles and later retention cleanup
- Navigation properties are preferred so aggregate shape is visible in the CLR model instead of being inferred only from Fluent API
- `Executive` and `Reflective` are mapped through navigation properties from `PolarisCycle`, so they do not need top-level `DbSet` properties to participate in persistence
- Shared scan roots are only allowed when path-discriminability and storage-topology validation can still distinguish model identity without consulting the database

## Design Note
This domain owns persistence and vault I/O. It should stay infrastructure-facing, while orchestration and PUCK stay focused on domain behavior.

# Vault Watcher & Sync Plan

## Premise

Sync model detection must be purely path-based.

- The model type is resolved from the file path alone.
- Sync policy is resolved from the target type's `VaultStorageAttribute`.
- Frontmatter is used for property sync and validation, not for deciding what model a file represents.
- Path identity is authoritative for file-backed entity detection.

This means the watcher must never infer model type from frontmatter fields such as `id`, `title`, `status`, or relation properties.

## Current foundations

- Path-backed markdown layout already exists through `MarkdownFileLocator`.
- Frontmatter now has two-way CLR property conversion plus validation.
- Temporal graveyards and audit logging already exist.
- PUCK tokenization exists and can validate mixed manual/automatic identifiers.
- Path-based sync model catalog now exists as the intended model-resolution root.

## System goals

1. Detect vault-backed models from path only.
2. Apply sync policy from `VaultStorageAttribute.Mode` only.
3. Preserve auditability for every discovery and reconciliation action.
4. Preserve deleted or conflicting data through graveyard retention.
5. Avoid self-induced watcher loops.

## Phase 1: path model catalog

Create and rely on a single path model catalog that defines, for every vault-backed model:

- CLR type
- root path
- path shape rules
- storage mode
- canonical identity rules

All discovery and watcher flows should ask the catalog to resolve a path before doing any other work.

## Phase 2: discovery scan

Add a startup discovery service that:

1. enumerates vault-backed roots from the path model catalog
2. resolves each markdown path to a model from path alone
3. parses loose path identity
4. parses and validates frontmatter into a CLR candidate
5. records a sync candidate object with:
   - absolute path
   - vault-relative path
   - resolved model type
   - path identity
   - parsed CLR model
   - validation issues
   - body hash
   - filesystem timestamps

## Phase 3: sync decision engine

Build an explicit decision engine that receives a sync candidate and returns one action:

- create database entity from file
- update database entity from file
- rewrite file from canonical database state
- recreate protected file
- purge desynchronized file
- quarantine conflict
- ignore with audit

This engine must consult `VaultStorageAttribute.Mode` for all policy decisions.

### Policy rules by storage mode

#### `Synced`
- creation can originate from file or core
- property changes reconcile both ways
- deletion can propagate both ways
- invalid frontmatter fields are overwritten by canonical state

#### `Optional`
- entities are core-created
- file presence is optional
- property changes reconcile both ways when the file exists
- file deletion does not imply entity deletion

#### `FileFirst`
- entities are file-created
- file removal implies tracked removal
- core does not manufacture missing files unless explicitly repairing corruption

#### `Enforced`
- entities are core-created
- file presence and canonical naming are enforced
- unknown files are purged to graveyard
- missing files are recreated from canonical state

## Phase 4: PUCK creation policy

Use PUCK tokenization during creation flows:

- manual PUCK segments must be supplied by the caller
- automatic PUCK segments must be generated by the core
- if a caller supplies a full PUCK for a mixed declaration, only the manual segments are taken from caller input
- caller input for automatic segments is ignored
- path identity remains the authority for file-originated creation

For file sync specifically:

- if path identity lacks required manual PUCK input, the file cannot create an entity
- if path identity contains automatic segments, they are normalized to canonical core-issued output on write-back

## Phase 5: watcher runtime

Add a hosted watcher service that:

- watches all catalog roots
- debounces bursts of file events
- coalesces rename, write, create, and delete operations
- submits work into a serialized per-vault reconciliation queue

The watcher must tag service-originated writes so canonical write-back does not trigger infinite loops.

## Phase 6: conflict handling

Conflicts to detect:

- duplicate files for one path identity
- invalid path identity for the resolved model
- invalid frontmatter values
- path/title divergence
- file delete blocked by relational policy
- stale file overwriting newer canonical state

Conflict policy:

- preserve originals in graveyard
- emit audit entries
- prefer explicit reconciliation over silent destruction

## Phase 7: delete and recreate rules

Deletion behavior must remain policy-driven:

- relation-blocked deletions recreate canonical files instead of losing state
- removable entities archive temporal data before deletion
- desync purges archive files before removal

## Phase 8: observability

Every watcher/discovery decision should emit an audit entry, including:

- discovered
- parsed
- validated
- imported
- updated
- rewritten
- recreated
- purged
- conflicted
- ignored

## Implementation order

1. Path model catalog as the sole resolution source
2. Startup discovery scan with dry-run reporting
3. Sync candidate and decision models
4. Apply-mode reconciliation for existing file-backed types
5. Watcher hosted service with debounce and serialized work queue
6. Conflict and recreation rules
7. Retention cleanup policy for graveyard and audit data

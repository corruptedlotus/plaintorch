# SDK Genesis

## Purpose
`@pleiades/sdk` is the TypeScript client for the PLAINTORCH core. It carries the wire contracts, a transport
layer over the core's local socket, and PLAINTORCH's declarations to the repository system —
`@corruptedlotus/local-repo`, its own repository beside this one — that keeps a frontend in step with the core and
with itself.

## Main Parts
- `plaintorch/coreClient.ts` — the client: transports, request helpers, deserialization
- `plaintorch/nodeCoreClient.ts` — the Node client, talking over the per-user socket or Windows named pipe
- `plaintorch/internal/transport.ts` — the transport contract, the fetch transport, line reassembly
- `plaintorch/{objectives,directives,declaratives,onrush,polaris,lore,system,schedules}` — one domain SDK each,
  contracts and models beside them
- `@corruptedlotus/local-repo` (the sibling repository, linked as `file:../../local-repo` until it is consumed from npm, re-exported from `plaintorch/index.ts` so
  `@pleiades/sdk` imports of it keep resolving) — the repository system (below): generic, importing nothing of PLAINTORCH's
- `plaintorch/repos/` — PLAINTORCH's use of it: its policy (entity shape, model construction, trusted fields),
  what a change makes stale, its change feed, and `PlaintorchRepositories` — the client's `repos`
- `plaintorch/calendar`, `helpers/` — Pleiadean date handling and formatting

## How It Works

### Deserialization
The core stamps `@type` — the runtime .NET type name — onto every object it serializes, nested ones included.
The client parses every response with the store's reviver, so construction runs bottom-up over the whole graph: nested models
become real model instances, and a list response is constructed element by element even though the root array
carries no type name of its own. `@a11d/api-dotnet`'s `ModelValue` registry maps type names to constructors.

### The identity map
Every response passes through the reviver, and every node identifiable as a tracked entity is absorbed into
`EntityStore`, which holds exactly one canonical instance per `{typeName}:{id}`. An entity already in the
store has the incoming fields merged into the instance that is already on screen rather than replacing it, so
every surface holding a reference is looking at current state by construction, and synchronizing them reduces
to telling them to re-render.

Two details carry most of the weight:
- The merge runs against **the keys the wire payload carried**, captured before construction. Constructing a
  model widens a sparse payload to the full shape of its class, so merging against the constructed instance
  would let a response that merely omits a field overwrite the cached value with a class default.
- Subscribers fire **only when a field actually changed**, and unchanged values keep their references, so a
  poll that returns identical data re-renders nothing.
- A collection that came back **cycle-truncated is withheld from the merge**. The core serializes with
  `ReferenceHandler.IgnoreCycles`, which writes `null` wherever an object would recur inside itself, so a
  back-reference drags a gutted copy of its owner's collection along: asking for one objective returns its
  sprint, and that sprint's `objectives` arrives as `[null]` — the hole being the objective that was asked
  for. Merging that would empty the sprint every other surface is reading, so a nested entity's holed or empty
  array is left out of the payload keys, which is the same mechanism that already protects a sparse response.
  The withholding guards the *merge*; an entity seen for the first time as such a back-reference is adopted
  as constructed, so the holes are also **repaired at construction** (`repos/policy.ts`): the model is built
  from the payload with the `null` entries taken out of its collections. What is adopted is then incomplete
  rather than unsafe to walk, until a response that speaks for the collection fills it.
- A **canonical entity is a cyclic graph, so it is never a write body**. Once both sides have been seen, the
  identity map links an objective to its directive and the directive's `objectives` back to it. Anything holding
  an objective reaches the same loop: an onrush through its members, a Polaris cycle through its executives'
  incentives. Every incentive read carries its directive, so these links are routine. `JSON.stringify` of such
  a body throws, so a write sends only the fields it changes (`{ [keyPath]: value }` from a banner's binder),
  never `update(id, entity)`. `objectiveUpdateCycle.test.ts` pins the cycle on the objective, sprint and cycle
  shapes the core sends. The core's side of it, serializing its own cyclic tracked graphs, is
  `NestedHierarchySerializationTests`.

Tracked entities are exactly the core's `PuckNamedEntity` subclasses — the things with a PUCK for an
identifier. `Executive`, `Reflective`, `Eventive`, `Attentive` and `Terminative` (PEP103 patch 7) carry numeric keys, are always reached
through an owner, and are absorbed as part of that owner. They are recognized by shape (`@type`, a string
`id`, a string `title`) rather than from a list of names, because a polymorphic entity serializes under its
own runtime type name (a fate is `Fate`, not `Objective`) and a list drifts.

### Policy
The package knows nothing about PLAINTORCH. The store is built with an `EntityPolicy`, and
everything domain-specific reaches it that way:
- **identity** — which values are tracked entities, and under which key (`identify`);
- **models** — how a payload becomes a class instance, here through `@a11d/api-dotnet`'s registry;
- **mergeable keys** — which fields of a payload are trusted, which is where the two rules above live;
- **dependents** — handed to the `InvalidationScheduler` rather than the store: what a change makes stale.

PLAINTORCH's are declared once, in `repos/policy.ts` and `repos/dependents.ts`, and the client builds
its store from them. The system has been its own package since 2026-10-11 (`_documents/Plan - Local Repo Separation.md`,
and the package's own `.GENESIS.md`); a suite in the package fails if its core imports anything from outside it.

### Repositories
`EntityRepository` owns *when the core is contacted*: read-through caching against a freshness window,
in-flight dedup keyed by identity, and `mutate()` as the single write path. `DerivedRepository` does the same
for views with no identity of their own — the briefing, note and PUCK resolutions. `PlaintorchRepositories`
composes them onto the client as `repos` and can resolve a repository from a runtime type name, which is what
lets a generic surface observe an entity without a switch over every kind. It extends the generic `RepositorySet`, which owns everything that spans repositories — type-name routing, invalidation, the eviction sweep — and through which every repository is created, so none can exist without the sweep and the feed knowing of it.

Dependency edges are the one thing listed rather than tracked. A `Dependency` has a numeric key and no PUCK,
and its endpoints are loose references, so there is nothing for the identity map to absorb — `dependencyList`
is the record a graph surface observes, and the entities at the ends of those edges are tracked as usual.
`onrushCurrent` and `onrushPlanning` are records for the opposite reason: *which* sprint is current is itself
the question being asked, so there is no id to look up until the core answers.

The domain SDKs remain the way to talk to the core directly — a picker's one-shot search, an imperative vault
command. Anything a surface displays and must keep current goes through a repository. Responses are absorbed
either way, so a transient search still yields canonical instances.

A listing can never **empty** a collection. PLAINTORCH's policy withholds a nested entity's empty array as not
loaded (`mergeableKeys` in `repos/policy.ts`), and every entity a listing serves is nested, so re-reading a
listing after the last member of a collection left (a Polaris cycle's last executive moved to another day) keeps
drawing the member that is gone. Only a response with the entity at its root applies the emptying: after a write
that can empty a collection, refresh that entity through its own repository (`core.repos.polaris.refresh(id)`;
SIPA's `revalidatePolarisCycles(...emptied)` does this for the cycles a write took executives out of).

### What a read can say
A fetcher answers one of three ways, and the repositories treat each differently:
- **a value** — absorbed, and stamped as freshly resolved;
- **nothing** (`undefined`) — the core answered that there is nothing there. A known entity is **removed**
  from the store; a derived record is emptied;
- **no answer** (`unresolved`) — the core could not be reached, or failed. Whatever is held stays as it was,
  still stale, and is asked for again next time. An outage no longer blanks what is on screen.

The store keeps one of three **data states** per identity — `not-loaded`, `loaded`, `removed` — and a derived
record tells never resolved from resolved to nothing. A removal is announced to the identity's observers and
noted in the change ledger, so a response issued before it (a listing still in flight) cannot bring the entity
back. A deletion announced on the change feed removes the entity at once; the refetch that follows confirms it.

What held a removed entity lets go of it, because PLAINTORCH's policy says `removal: "detach"`: the store takes
it out of the collections of the other entities it holds and out of the derived records' values, replacing each
collection with a new array and telling its observers. A listing loses the row and a sprint loses the objective
the moment it is removed. The mode is the store's policy (`"detach"` or `"keep"`, for every type or per type);
single references are left as they are.

The client's own reads cannot tell the last two apart — a failed request and an empty one both come back as
nothing, and the listing SDKs turn nothing into `[]`. `repos/answered.ts` is the **interim** bridge:
`getJsonAnswer` reports whether the core answered (a success or a not-found) and the repositories' fetchers
read through SDK instances that surface the difference. It carries no reason for a failure and is the piece an
error model replaces.

### Invalidation
`repos/dependents.ts` declares once what a change to each type makes stale, resolved against the canonical
instance rather than a response payload — an objective carries no cycle of its own, but the instance in the
store carries the executives naming every cycle holding it.

Invalidating is not refetching. Everything affected is marked stale; a refetch is only issued for identities
something is observing, and anything else resolves lazily for whoever asks next. Dirty identities settle on a
microtask, so one write touching several aggregates produces one pass.

### Writes
`mutate()` holds an identity while a write is in flight, so a revalidation cannot refetch over an edit that
has not settled. A rejected write is rolled back: the client reports failure by returning nothing rather than
throwing, so an absent result is the rejection signal. That test is the default, not a rule of the repository
system — a repository (or a whole set) declares what counts as an accepted write, and every write path
(`mutate`, `commit`, a draft's `commit`) uses the same one. Because two-way bindings apply an edit to the canonical
instance *before* anything is sent, the caller captures the previous state and hands it to `mutate()` as the
rollback point — and announces the edit through `store.touch()`, since there is nothing left for absorption to
detect.

### The change feed
`PlaintorchChangeFeed` — the generic `ChangeFeed` pointed at the core's stream — consumes server-sent events and invalidates what they name, which is
how writes made outside the frontend — a markdown edit the watcher picks up, the CLI, the scheduler — reach
the screen. It is strictly an optimization: every guarantee except promptness holds with it off, so an
unreachable feed is not an error, and a reconnect marks everything stale because anything that happened while
disconnected was missed.

Streaming is a separate, optional transport operation. The ordinary request path buffers to an end that never
comes for a feed held open, and the Node client is socket-only by design, so in practice there is one
streaming path: a long-lived `node:http` request over the socket or named pipe.

## Consumers
The UI (`@pleiades/sipa`, bundled by the Obsidian plugin) binds to this through the package's Lit controllers
(`@corruptedlotus/local-repo/lit`): `EntityRef` resolves and observes an entity, `DerivedRef` does the same for a record, and
`EntityWatch` observes an entity a component was handed rather than one it resolves. They are thin — the store and
repositories do not know what Lit is — and SIPA keeps two subclasses in `sipa/components/data/EntityRef.ts` that supply
what PLAINTORCH adds: the toast a rejected write raises, the installed core's store, and `EntityRef.awaitCommit`.

`awaitCommit` is for a surface that asks for a change itself and shows its outcome — the state bubble. It sends the
change in a state enforcement scope (`client.withStateEnforcement`, PEP103), so a change the core holds back for
confirmation, or refuses, comes back with the outcome instead of reaching the client-wide prompt, and no failure toast
is raised; `{ force: true }` repeats it with the user's confirmation. A scope covers only what is sent before its first
`await`, which holds because every SDK call, and the repository's commit around it, sends synchronously. A state is
never bound to an editable: a binder's catch-all sends one field (`'*': (o, keyPath) => update(o.id, { [keyPath]:
o[keyPath] })`), and the state bubble sends the shift.

Each exposes the data states beside `loading` and `error`: `EntityRef.notLoaded` / `removed`,
`DerivedRef.notLoaded`, `EntityWatch.removed`. A banner whose entity was removed says so (`p7t-entity-absence`)
instead of going on showing it — through a reference, or when shown a provided copy of a removed entity — and one whose entity could not be loaded says that and offers to try again; the executive and occurrence editors do the same for the entity they are about; a
row or card handed an entity that has since been removed is stood down (`entity-removed`) until its listing
drops it.

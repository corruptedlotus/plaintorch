# SDK Genesis

## Purpose
`@pleiades/sdk` is the TypeScript client for the PLAINTORCH core. It carries the wire contracts, a transport
layer over the core's local socket, and the repository system that keeps a frontend in step with the core and
with itself.

## Main Parts
- `plaintorch/coreClient.ts` — the client: transports, request helpers, deserialization
- `plaintorch/nodeCoreClient.ts` — the Node client, talking over the per-user socket or Windows named pipe
- `plaintorch/internal/transport.ts` — the transport contract, the fetch transport, line reassembly
- `plaintorch/{objectives,directives,declaratives,onrush,polaris,lore,system}` — one domain SDK each,
  contracts and models beside them
- `plaintorch/repository/` — the repository system (below)
- `plaintorch/calendar`, `helpers/` — Pleiadean date handling and formatting

## How It Works

### Deserialization
The core stamps `@type` — the runtime .NET type name — onto every object it serializes, nested ones included.
`readJsonResponse` parses with a reviver, so construction runs bottom-up over the whole graph: nested models
become real model instances, and a list response is constructed element by element even though the root array
carries no type name of its own. `@a11d/api-dotnet`'s `ModelValue` registry maps type names to constructors.

### The identity map
Every response passes through the reviver, and every node identifiable as a tracked entity is absorbed into
`EntityStore`, which holds exactly one canonical instance per `{typeName}:{id}`. An entity already in the
store has the incoming fields merged into the instance that is already on screen rather than replacing it, so
every surface holding a reference is looking at current state by construction, and synchronizing them reduces
to telling them to re-render.

Two details carry most of the weight:
- The merge runs against **the keys the wire payload carried**, captured before construction. Constructing a
  model widens a sparse payload to the full shape of its class, so merging against the constructed instance
  would let a response that merely omits a field overwrite the cached value with a class default.
- Subscribers fire **only when a field actually changed**, and unchanged values keep their references, so a
  poll that returns identical data re-renders nothing.

Tracked entities are exactly the core's `PuckNamedEntity` subclasses — the things with a PUCK for an
identifier. `Executive`, `Reflective`, `Eventive` and `Attentive` carry numeric keys, are always reached
through an owner, and are absorbed as part of that owner. The registry in `identity.ts` is explicit rather
than derived from `@model`, because only some contracts are classes and a polymorphic entity serializes under
its own runtime type name (a fate is `Fate`, not `Objective`).

### Repositories
`EntityRepository` owns *when the core is contacted*: read-through caching against a freshness window,
in-flight dedup keyed by identity, and `mutate()` as the single write path. `DerivedRepository` does the same
for views with no identity of their own — the briefing, note and PUCK resolutions. `PlaintorchRepositories`
composes them onto the client as `repos` and can resolve a repository from a runtime type name, which is what
lets a generic surface observe an entity without a switch over every kind.

Dependency edges are the one thing listed rather than tracked. A `Dependency` has a numeric key and no PUCK,
and its endpoints are loose references, so there is nothing for the identity map to absorb — `dependencyList`
is the record a graph surface observes, and the entities at the ends of those edges are tracked as usual.
`onrushCurrent` and `onrushPlanning` are records for the opposite reason: *which* sprint is current is itself
the question being asked, so there is no id to look up until the core answers.

The domain SDKs remain the way to talk to the core directly — a picker's one-shot search, an imperative vault
command. Anything a surface displays and must keep current goes through a repository. Responses are absorbed
either way, so a transient search still yields canonical instances.

### Invalidation
`invalidation.ts` declares once what a change to each type makes stale, resolved against the canonical
instance rather than a response payload — an objective carries no cycle of its own, but the instance in the
store carries the executives naming every cycle holding it.

Invalidating is not refetching. Everything affected is marked stale; a refetch is only issued for identities
something is observing, and anything else resolves lazily for whoever asks next. Dirty identities settle on a
microtask, so one write touching several aggregates produces one pass.

### Writes
`mutate()` holds an identity while a write is in flight, so a revalidation cannot refetch over an edit that
has not settled. A rejected write is rolled back: the client reports failure by returning nothing rather than
throwing, so an absent result is the rejection signal. Because two-way bindings apply an edit to the canonical
instance *before* anything is sent, the caller captures the previous state and hands it to `mutate()` as the
rollback point — and announces the edit through `store.touch()`, since there is nothing left for absorption to
detect.

### The change feed
`PlaintorchChangeFeed` consumes the core's server-sent event stream and invalidates what it names, which is
how writes made outside the frontend — a markdown edit the watcher picks up, the CLI, the scheduler — reach
the screen. It is strictly an optimization: every guarantee except promptness holds with it off, so an
unreachable feed is not an error, and a reconnect marks everything stale because anything that happened while
disconnected was missed.

Streaming is a separate, optional transport operation. The ordinary request path buffers to an end that never
comes for a feed held open, and the Node client is socket-only by design, so in practice there is one
streaming path: a long-lived `node:http` request over the socket or named pipe.

## Consumers
The Obsidian plugin binds to this through reactive controllers in `obsidian/components/data`: `EntityRef`
resolves and observes an entity, `DerivedRef` does the same for a record, and `EntityWatch` observes an entity
a component was handed rather than one it resolves. They are thin — the store and repositories do not know
what Lit is.

# Local Repo Genesis

## Purpose
`@corruptedlotus/local-repo` is the frontend repository system: an identity map of canonical entity instances,
typed repositories over a backend, drafts, invalidation, a change-feed client, and Lit bindings. It was written
for PLAINTORCH (PEP106 and Patch106.1, 2026-07) inside `@pleiades/sdk`, and extracted into this package in five
stages between 2026-10-02 and 2026-10-11 (`_documents/Plan - Local Repo Separation.md`) so that another
project can install it without importing anything of PLAINTORCH's. PLAINTORCH is its first consumer.

## Layout
- `index.ts` — the core entry: everything below except the bindings. No runtime dependency.
- `lit/` — the bindings entry (`@corruptedlotus/local-repo/lit`): `EntityRef`, `EntityWatch`, `QueryRef`,
  `DerivedRef`, `ReactiveBinder`. Depends on `@a11d/lit` (a peer), and on the core.
- `testing.ts` — the fakes the suites use (`@corruptedlotus/local-repo/testing`).
- `*.test.ts` beside each file; `foreignDomain.test.ts` is the acceptance fixture; `policy.test.ts` guards the
  import boundaries and the `.js` extensions.
- `dist/` — built by `npm run build` (`tsconfig.build.json`); not committed.

## How it works
**The store** (`entityStore.ts`) keeps one record per `{type}:{id}` with the canonical instance, subscribers,
a version, a freshness stamp, and the data state. Absorption (`absorption.ts`) is a `JSON.parse` reviver: each
object the policy identifies as an entity is merged into its record's instance — only the payload's keys, and
only those `mergeableKeys` allows — and the instance is returned in the payload's place, so a response is a
graph of canonical instances by the time the caller sees it. Collections are replaced, not spliced, when they
change (`equivalence.ts` decides what changed), so a host handed a collection as a property sees a new
reference. `store.read` brackets a request in the **ordering ledger**: a read notes the revision it was issued
at, a local change (`touch`, a write, a removal) records its revision per identity, and a response issued before
an identity's last change is not absorbed for it. The ledger prunes to the oldest read in flight.

**The policy** (`policy.ts`) is the only place a domain enters: `identify`, `models`, `mergeableKeys`,
`removal`. `resolvePolicy` fills the defaults (plain objects, every key, detach). `identity.ts` has the key
helpers, the `identifyByShape` preset, and `collectEntityKeys`, the walk the sweep and the dependents use.

**Repositories** (`entityRepository.ts`, `derivedRepository.ts`) own *when the backend is contacted*: a
freshness window, in-flight de-duplication, and the three read outcomes (`outcome.ts`): a value is absorbed and
stamped; `undefined` removes the entity — unless it was absorbed or changed while the request was in flight, in
which case the older answer is dropped; `unresolved` keeps what is held and leaves it stale. Writes go through
`mutation.ts`: apply optimistically, send, judge the result with the `WriteSuccess` policy, then invalidate on
success or roll back to the snapshot. `draft.ts` is the fork: a copy built through the policy's models (or a
prototype-preserving copy), a baseline, and a commit that sends only the diff.

**Removal** (`store.remove`, `detach.ts`): the instance is marked in a `WeakSet` (`wasRemoved`), the record
empties into the `removed` state, and under the `detach` mode the entity is taken out of every collection the
store can reach — owners' collections, including inside value objects, and derived records' values — each
replaced by a new array, with the owners notified and left stale. Single references stay; `wasRemoved` is how
their holders find out.

**Spanning the repositories** (`repositorySet.ts`, `invalidation.ts`, `changeFeed.ts`): the set creates every
repository so it can route a type name, hand the scheduler its dependents table, be the feed's sink
(`invalidateAll`, `revalidateObserved`, `acceptAuthority`, `invalidate`, `remove`), and run the eviction
sweep: prune unobserved stale records, gather roots (resolved records plus subscribed entities), keep what they
reach, evict the rest. The feed knows only a source of lines and the sink; `Deleted` removes at once.

**The bindings** (`lit/`) are `@a11d/lit` `Controller`s with no decorators. `EntityRef` takes the repository
and the identifier as thunks (both can change while the host is mounted), subscribes, resolves, and owns the
edit cycle: `beginEdit` snapshots, `commit` touches, sends through the repository's `commit`, and calls the
`rejected` hook on a rollback; `binder` folds that behind an `@a11d/lit` `bind`. `EntityWatch` takes the store
(or a thunk of it) and an instance; `QueryRef` reads the type index through `repository.store`; `DerivedRef`
takes its repository. The bindings' suites mount real hosts under happy-dom and drive a real `<input>` through
the binder; under Node, Lit resolves to its server build, so the suite installs the native default binding
property itself.

## Packaging
- `exports` carry three conditions per entry. `source` points at the TypeScript and is what the repository's
  own consumers (`sdk.ts`, `sipa`, the Obsidian plugin, the standalone shell) select — `customConditions` in
  their tsconfigs, `conditions` in their esbuild and Vitest configs — so they bundle and type-check the sources
  without a build step, as they do for the SDK and SIPA. `types` and `default` point at `dist/` for a consumer
  that installs the tarball; `files` ships `dist` and the README only, so the `source` condition is inert there.
- Relative imports carry `.js` extensions so the emitted JavaScript and declarations resolve under Node's own
  resolution (`moduleResolution: NodeNext`) as emitted; the suite in `policy.test.ts` enforces it.
- The build targets ES2021 with `useDefineForClassFields: false`, so a controller's fields are assigned, not
  defined, after `Controller`'s constructor has registered it with the host. Under define semantics a controller
  created on an already-connected host would have its fields wiped after `hostConnected` ran.
- `@a11d/lit` is a required peer of the `/lit` entry and a pinned devDependency here, for the suites. Inside
  this repository that is a second copy beside SIPA's, so the bundlers alias `@a11d/lit` onto SIPA's copy and
  SIPA's Vitest dedupes it; TypeScript deduplicates identical package versions on its own, which is why the
  devDependency is pinned to the version SIPA resolves.
- Acceptance: `npm pack`, install the tarball with `@a11d/lit` into a scratch project with `strict`, `NodeNext`
  and `skipLibCheck: false`, type-check a consumer of all three entries, and run the core under Node.

## Consumers in this repository
`@pleiades/sdk` depends on the package (`file:../local-repo`) and re-exports the core from its `plaintorch`
entry, so every `@pleiades/sdk` import of a store, repository or outcome type keeps resolving; its
`plaintorch/repos/` directory holds PLAINTORCH's policy, dependents, feed and repository set. `@pleiades/sipa`
imports the bindings from `/lit` and keeps two thin subclasses in `components/data/EntityRef.ts`: its `EntityRef`
supplies the `rejected` hook (the platform toast) and its `EntityWatch` the installed core's store, so SIPA's
construction sites did not change. `DerivedRef` and `ReactiveBinder` are re-exported as they are.

## Open
- The error system (server-side validation, an error registry) is deferred; failure values pass through opaque
  and the outcome shapes are not frozen, which is what the `0.x` version says.
- `EntityRef.binder` is exercised through a native `<input>` here; the SIPA editables run it in SIPA's suite.
